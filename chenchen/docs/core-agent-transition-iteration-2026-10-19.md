# Core Agent 状态变更与恢复交付 · 2026-10-19

本轮重点：**结果没存清楚，就先停止后续操作；已经存好的结果，断线重连能找到原件。** 继续只做 Core 主链路，保留所有旧版本和旧测试记录。

## 已完成的核心接口

| 情况 | 本轮行为 |
| --- | --- |
| 用户撤回了任务，但撤回记录保存失败 | 不再把旧的“已批准”状态交给后续执行，任务暂停核查 |
| Risk 拒绝或人工审批保存不确定 | 保留可核查编号，阻止再提交另一份决定覆盖它 |
| 模拟执行的结果没确认保存 | 同一任务暂停；共用这个资金计划的其他任务也暂停，不再沿用旧余额 |
| 修改房租等资金用途后保存不确定 | 阻止继续使用旧计划和原批准 |
| 结果已经存好，仅返回消息丢了 | 重启后找回同一份模拟回执，资金只占用一次 |
| 风控交接已发出，本地保存却失败 | 保留未决登记，重启后不自动重复派发 |
| 假签名或缺签名 | 仍然拒绝，且不会创建新的变更登记 |

沿用现有请求和冻结 Schema。内部新登记不是 Memory，也不是新的风控规则；不重新计算 Quant、不赋予执行权限。异常继续使用既有 503 / REVIEW_SERVICE_UNAVAILABLE，明确 retryable:false；不把旧 workflow 当成当前结果返回。创建模型任务原有登记保护继续保留。

## 需要团队进一步落实

1. **Core/Backend 与 Risk：确认来源编号的消费位置。** Handoff 顶层多余别名已移除，来源编号仍在 `reviewed_input.source_task_id` 和原工作流记录中；如果正式消费者必须读取顶层字段，需要双方另行升级版本，不能重新塞回冻结 Schema。
2. **模型服务、Risk 与身份接入：确认正式回执编号、接收地址、签名回写和审批身份。** Core 现在会读取供应商返回的 `id`、`response_id` 或请求追踪响应头；供应商完全不返回编号时仍保留为空，当前 Risk 会拒绝这种证据，线上也未形成正式同任务闭环。
3. **模型服务：对齐真实供应商回执编号并落实百炼开通、预算授权。** 不填假编号，不进行未经授权的付费调用。
4. **UI/调用方：遇到 retryable:false 时显示“记录待核查”，保留编号。** 不自动重发、不换键新建任务绕过阻断；共用资金计划时可能需要等原任务核查完。
5. **Backend 与 Risk：确定未决任务的人工核查权限和流程。** 本轮提供可追踪登记及复现证据，没有增加强制释放按钮。信息不足保持暂停，不能为了演示恢复成功而删记录。

## 使用限制与回退

[实现说明和复跑方法](../experiments/transition-recovery-v1/README.md)。本轮新增一次前置存储提交和读取检查，以安全阻断换取额外存储操作；未测公网吞吐和延迟。未决登记不会自动过期，因此确实会降低受影响任务的可用性，必须经后台核查。没有宣称外部服务 Exactly Once 或多地区灾备。
