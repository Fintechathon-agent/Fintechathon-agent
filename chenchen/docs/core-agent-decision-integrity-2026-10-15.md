# Core Agent 第三轮：一次审批就是同一个人、同一个理由、同一份方案

## 先看结论

这轮不增加首页文字，集中修复两类主链路问题：重复提交不能悄悄换人或换理由；已取消的任务不能被迟到的回调恢复。

## 修改前实际复现了什么

新增5个回归测试在修改前全部失败：

- 直接并发调用公共工作流的 Risk 回调和取消时，最终状态可能由 CANCELLED 被旧快照覆盖为 PENDING_APPROVAL，取消审计也会丢失。
- 同时收到两份完全相同的回调时，第二份可能误报已有 Risk 决定，而不是返回 DUPLICATE。
- 旧 Risk/审批接口只比较 APPROVE/REJECT，没有完整比较人员和理由。提交相同决定但更换人员或理由，会返回成功而不是告知冲突。
- 重复提交缺少理由或超长理由可能逃过校验；人员/理由原先会被静默截断到500字符。

这些是本地公共工作流的复现结果。Cloudflare 公网入口原本已经串行处理请求，本轮没有证据表明线上曾发生取消被覆盖；不能把本地复现写成线上事故。

## 现在怎样处理

| 情况 | 响应与效果 |
| --- | --- |
| 完全相同的有效判定/审批重试，任务未终结 | 200，返回已有记录；不多生成决定或审计事件 |
| 同一任务/方案，换人、换理由或改决定 | 409，保留原判定/审批，增加阻断审计 |
| 缺少人员/理由，空白或超过500字符 | 422，关联到原任务的输入错误留下审计；不静默截断 |
| 已记录的 Risk callback 完全相同地重发 | DUPLICATE，返回当前任务状态；如果已取消就仍是CANCELLED |
| 已取消任务收到新的 Risk 判定/审批 | 拒绝，不恢复任务；模拟执行也被阻断 |

人员/理由去掉首尾空白后比较；decision延续原大小写归一规则；task_id、proposal_sha256仍必须匹配原记录。终态拦截规则没有放松。

回调内写入 Risk 决定及回执不再在中途让出执行权，避免本地其他操作插入并被旧快照覆盖。它解决单进程内公共工作流的并发问题，不是新增跨服务器事务能力。公网持久化仍由原有 Durable Object 排队和原子保存负责。

## 统一 Contract 与兼容性

- 不新增接口、不新增必填字段。`model-review.v1` 补上人员/理由的非空、500字符约束及重复请求语义。`risk-handoff.v1` 字段不变。
- 409冲突沿用 `RISK_DECISION_IMMUTABLE` / `APPROVAL_IMMUTABLE`；输入不合法为 `INVALID_WORKFLOW_INPUT`，HTTP 422。
- 错误响应保留原 task/run/audit 追踪和workflow；已记录任务的这些拒绝可在 `audit.events` 找到 `workflow.operation_blocked`。
- 旧数据不迁移、不改写，终态不会重新进入审批。只是重复提交更严格：调用方要原样重发原人员与理由，而不是生成新的理由。
- 本轮只加强**判定和审批重试**；没有新增“创建任务”的幂等键。重复提交同一task_id创建任务仍按原规则返回409，网络丢响应后应先查询任务。
- 人员字段仍是演示标签，不是身份认证。不能将“重复请求一致性”称为“身份安全已完成”。

## 测试与证据

- 原有103项测试，新增10项后共113项通过；包括5个原始复现、先取消后回调、冲突回调、500字符边界、真实本地HTTP入口和云端Worker内存替身重启持久化。
- [离线完整证据](decision-integrity-local-2026-10-15.json)来自实际脚本输出，模型为明确的合成测试替身。运行 `node scripts/verify-decision-integrity.js` 可复现。
- 实际本地Workflow/Handoff共4份及有效请求2份通过Schema校验；4份空理由/超长理由请求被Schema拒绝。
- 公网验证独立记录，使用真实模型、虚构资金计划、演示Risk/审批；不涉及真实交易。

## Owner 配合与职责边界

- Risk / Approval Owner：确认409、422与完全相同重试语义；接入正式认证后，人员身份必须由受信任服务产生，不能只相信前端字符串。
- Backend Owner：如改用多实例服务，需继续提供事务/串行保障；本地同步段不能替代分布式并发控制。
- UI Owner：冲突时提示“已有记录，请核对后再操作”，不要生成新理由去重试。
- Core Agent本轮不重算Quant、不改Memory规则、不绕过Risk，真实执行保持false。
