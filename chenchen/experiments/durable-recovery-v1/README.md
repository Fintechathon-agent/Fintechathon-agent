# Core 任务持久登记与故障恢复验证 v1

这是 Core 后端的离线故障验证，不新增用户界面，不接银行或模型供应商。旧实验保留。

## 为什么需要

模型调用发生后，最终记录可能尚未保存就遇到故障。只在内存中记住“已调用”，重启就会忘记。现在 Core 先写持久登记，再调用模型；最终工作流和登记完成标记一起提交。

登记使用内部 `review-reservation.v1`，不是新的公共任务状态，也不写入长期 Memory。只保存任务/请求/会话编号、原始规范请求的摘要、幂等键的哈希与时间；不保存正文、密钥或身份资料。完成时补充真实工作流的运行与审计编号。

内部 COMPLETED 仅表示模型阶段的成功或失败记录已经持久化，不表示 Risk 批准、业务完成或执行成功。真实业务状态仍读取原工作流记录。

- 同一请求是否调用成功不确定：保留登记，返回既有 `REVIEW_SERVICE_UNAVAILABLE`，`retryable:false`；不推理、不审批、不执行。
- 数据已经提交、但成功响应丢失：相同幂等键和相同输入取回已有结果。
- 请求内容改变：409 冲突，不复用旧授权。
- 只有成功持久化的最终记录才可作为工作流返回。未保存的模型结果不能伪装成可查询证据。
- 登记不是模型调用证明。模型调用前也可能中断，不能根据 RESERVED 推定调用过、收费过或已收到响应。

## 运行

在 `chenchen` 目录，需要 Node.js 22.21+（本轮 v22.21.0）。SQLite 在此版本会提示实验特性，这是测试工具的依赖；生产 Worker 不导入 SQLite 模块。

```powershell
node --test tests/review-storage-recovery.test.mjs
node experiments/durable-recovery-v1/verify.mjs --output <新的证据文件.json>
```

验证器在系统临时目录创建 SQLite 文件，启动 4 个独立进程。分别在最终提交前和提交后、响应返回前强制退出，再由新的进程恢复。使用实际 Core Worker 请求处理器；供应商响应是明确的合成数据，共 2 次替身调用，没有外部推理。

两条进程级验证分别断言：未提交的任务在重启后仍阻断；已提交的任务恢复原 run/audit 编号，均不增加模型调用次数。具体证据见 [本轮磁盘恢复记录](../../docs/core-agent-durable-recovery-2026-10-19.json)。

这是本地 SQLite 存储适配器，不是 Cloudflare 运行时模拟器；未在公网服务上注入宕机或数据库故障，也不证明跨地域故障恢复。

## 接入方必须遵守

使用现有 `POST /api/review`，每项操作生成并保存稳定的 `idempotency_key`；相同请求重试沿用原键。不得遇到错误就换键重发。若不提供幂等键或固定 task_id，服务端无法识别两个匿名请求是同一操作。旧 `/legacy` 适配器不转交幂等键，不承诺其匿名重复请求被合并。

不确定状态可按错误中的 `trace.task_id` 请求 `GET /api/review/task/{task_id}`；登记存在但最终记录缺失时返回可追踪的 503，不是无记录的 404。错误中的 run/audit/handoff 没有已持久证据时保持 null，不编造编号。数据库整体不可读时也无法保证即时查询成功。

此保护依赖现有单一 ReviewService 协调器的串行队列和原子多键写入。不要将模块独立接到多个不协调的写入进程；没有声称实现分布式锁。模型内部既有重试上限保持不变；这里阻止的是故障后重启新一轮推理，不等于一个任务只会发出一次供应商 HTTP 尝试。

## 运维与历史

未完成登记不会按时间自动释放。运维须用任务编号核查最终 run/task 索引、登记及已授权的供应商日志，再由负责人决定后续处理；本轮没有增加“强制继续”、删登记或重新执行接口。若响应未保存且供应商不能找回，不能还原或捏造原回答。

旧 Worker 版本保留，但旧代码不识别这些登记。存在未完成登记时，不能直接回滚旧代码后放开模型入口；应先停住新调用，核查并处置未完成任务，再决定兼容回退。不能靠清空数据库恢复服务。
