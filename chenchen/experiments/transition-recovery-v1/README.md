# Core 状态变更保存保护 v1

范围：Cloudflare ReviewService 的内部存储协调，复用既有串行队列，不改 Risk、Memory 或公共接口。不是新的业务审批规则。

## 解决的问题

模型创建记录已有登记保护，但后续撤回、审批、Risk 回调、派发和模拟执行没有同样的保护。若操作处理完后保存失败，旧记录仍可能显示“可模拟”或“等待风控”，后续请求就可能继续使用旧状态。本轮为这些变更先写内部登记，最后在同一次存储提交中保存业务结果与完成标记。

内部键：`review-transition:task:{task_id}` 和 `review-transition:funding:{plan_id}`，版本 `review-transition.v1`。内部 PENDING/COMPLETED 不属于公开任务状态。登记含操作路径、已有追踪编号、时间和请求摘要，不保存请求正文、审批理由或签名密钥。

- 一个任务的状态变更未确认时，按 task、run、handoff、幂等键查询，以及再次审批、执行、派发都受阻。
- 模拟执行同时登记任务与资金计划。未决时，其他绑定该计划的任务、计划读取及修订也受阻；其他独立计划不受影响。
- 修改资金用途时也先登记计划，防止修改未确认后继续使用旧用途。新建独立演示计划没有旧计划可保护，本轮不为它增加任务登记。
- 验签发生在登记前，无效签名不能留下任务锁。
- 可确认的业务拒绝和对应审计一起保存，结束该次登记；保存本身失败则保持未决。
- 一旦已进入最终提交，捕获错误后不会再写一份旧快照覆盖可能已成功的提交。

对外继续使用 `503 REVIEW_SERVICE_UNAVAILABLE`、`retryable:false`，不返回可能过期的 workflow。任务变更带原 task/request/run/audit/handoff 编号；纯资金计划修订不伪造任务编号。共享计划阻断可能返回最初未决任务的追踪编号，它不是新请求已执行的证明。

## 恢复边界

若记录、资金占用与 COMPLETED 标记已经一起提交，只是成功响应丢失，之后读取可找回原结果，重复模拟仍是同一份回执。如果仍为 PENDING，不按年龄自动解锁；本轮未提供人工“强制继续”或自动清锁接口。

后台核查应先保留存储快照，核对登记时间、任务/运行编号、既有记录以及上游是否收到了交接。信息不足就继续暂停，不能改旧批准、删登记或新建任务绕过。正式恢复流程和权限仍需 Backend/Risk 共同确认。登记不是实际执行回执，也不能重建物理中断时尚未保存的业务事件。

只覆盖沿用当前 ReviewService 单写入队列和同一存储的路径。绕开该服务直接改数据库、跨独立部署的写入、真实资金网关和多地区灾备不在本轮保证范围内。本地 server.js 仍是演示用内存服务，不因此获得磁盘恢复能力。

## 复跑

在 chenchen 目录：

```powershell
node --test tests/review-transition-recovery.test.mjs tests/review-storage-recovery.test.mjs
node experiments/transition-recovery-v1/verify.mjs --output <新的证据文件.json>
```

需要 Node.js 22 的 node:sqlite。验证器在临时目录创建 SQLite 文件，使用事务、WAL、synchronous FULL，启动 6 个子进程。三组分别是撤回最终提交前退出、模拟最终提交前退出、模拟提交成功但响应前退出。前两组重启后阻断旧状态；最后一组恢复原回执和唯一占用。新证据路径必须不存在，避免覆盖历史。

模型、Risk 决策和审批人为合成测试数据。真实退出进程不等于 Cloudflare 故障注入或生产环境验收。[本轮证据](../../docs/core-agent-transition-recovery-2026-10-19.json)。

## 回退

旧版本不识别状态变更登记。回退前必须暂停新变更并核查所有未决任务/资金计划；不允许在有未决登记时直接回退并恢复执行。不得清空数据库。没有未决记录时仍需考虑回退将重新引入本轮故障边界。更早模型调用登记的回退要求继续适用。
