## 3. 信息形状样例（仅提案）

### 3.1 独立风险展示对象

字段名、枚举、空值与 API 路径均待 Owner 定义。示例表达“比较可用，执行因依据缺失需要修复”，并非本轮产生的风险结果。所有 ID 使用 `example-`，null 表示未提供，不能理解成数值零。

```json
{
  "proposal_only": true,
  "task_id": "example-task",
  "request_id": "example-request",
  "risk_decision_id": "example-risk",
  "check_status": "COMPLETED",
  "policy_version": "fixed-risk-demo.v0.1 (pending team confirmation)",
  "plan_ref": "example-plan-v1",
  "evidence_refs": ["example-snapshot", "example-tool-result"],
  "purposes": {
    "comparison": {"decision": "ALLOW", "reason_ids": []},
    "execution": {"decision": "REVIEW", "reason_ids": ["example-reason-1"]}
  },
  "reasons": [{
    "reason_id": "example-reason-1",
    "rule_id": "R02",
    "code": "REQUIRED_DATA_INVALID",
    "message": "缺少有效依据，相关模拟暂停。",
    "actual": null,
    "limit": null,
    "unit": null,
    "basis": "执行所需参数",
    "window": null,
    "evidence_refs": ["example-tool-result"],
    "acknowledgeable": false,
    "recovery": {"type": "UPDATE_DATA", "owner_module": 3, "condition": "补齐执行参数后重检"}
  }],
  "execution_eligible": false,
  "health_score": null
}
```

`comparison: ALLOW` 在此仅为样例前提：比较所需证据完整、缺失项仅影响执行。实际资格必须由服务返回，UI 不能根据字段缺失自行推断比较安全。

### 3.2 用户意图与可信确认分离

下列是 UI 想提交的动作需求，不包含客户端自报可信用户、APPROVED 状态或授权 token。可信主体由第二板块会话取得；服务端必须验证计划内容、全部版本、检查、可接受原因和有效期，返回确认记录。

```json
{
  "proposal_only": true,
  "task_id": "example-task",
  "plan_ref": "example-plan-v1",
  "plan_content_hash": "example-server-issued-content-hash",
  "risk_decision_id": "example-risk",
  "action": "CONFIRM_COMPLETE_PLAN",
  "accepted_reason_ids": [],
  "expected_versions": {
    "profile": "example-profile-v1",
    "constraints": "example-constraints-v1",
    "data": "example-data-v1",
    "policy": "example-policy-v1",
    "industry_mapping": "example-map-v1"
  }
}
```

这个动作样例独立于 3.1，不应对 3.1 的修复类 REVIEW 开启确认。CONFIRM / REJECT / WITHDRAW 的最终动作名及状态由 Owner 定义。被拒绝、已撤回、已失效、待确认分开展示；接受风险不会把原 REVIEW 原因删除。不要靠用户点击覆盖 BLOCK。

### 3.3 执行未知与审计缺口

```json
{
  "proposal_only": true,
  "task_id": "example-task",
  "execution_id": "example-execution",
  "idempotency_key": "example-key",
  "mode": "PAPER_TRADE",
  "status": "UNKNOWN",
  "receipt_ref": null,
  "completed_step_refs": [],
  "completed_steps_verified": false,
  "recovery": "VERIFY_EXECUTION_STATUS",
  "audit": {
    "event_refs": ["example-event"],
    "persisted": false,
    "gap_reason": "AUDIT_WRITE_FAILED"
  }
}
```

此时不能显示“已成交”或把空 completed_step_refs 解释成确定没有写入。须核查原请求，不自动重复提交。部分成功须保留已经确认完成的事实；执行后日志失败不得重新做交易。

## 4. 需要 Owner 明确的验收行为

| 场景 | 期望界面 / 回传 | 后端验证责任 |
| --- | --- | --- |
| ALLOW、未确认 | 说明已通过检查，完整计划仍待用户确认 | 无可信确认不能执行 |
| 可接受 REVIEW，多原因 | 每条原因单独显示与接受；漏一项不提交完整确认 | 第四验证全部可接受原因和当前版本 |
| 必须修复 REVIEW / ERROR | 没有接受放行按钮，显示责任方和恢复条件 | 故障 / 未知不可默认放行 |
| BLOCK 与 REVIEW 同时存在 | 全部原因可见，执行阻止；合法只读比较可用 | 聚合优先级与双用途资格由第四返回 |
| 集中度双口径 / 行业未知 | 实际值、分母、上限并列；I=0 显示不适用；未知展示下界与未知权重 | 第三计算；第四判断，不让 UI 除零或补零 |
| 逐步改善 | 仅在服务验证例外后显示重点指标与全部剩余风险 | 不新增/加重其他硬超限；未知不能证明改善 |
| 修改计划 / 画像 / 数据 | 旧确认失效，重检重确认；历史结果保留版本 | 第二/四验证影响范围，第三拒绝旧授权 |
| 拒绝 / 撤回 / 重复请求 | 拒绝和撤回后无新回执；重复成功只显示原回执 | 不重复写入；未知先查；内容冲突阻止 |
| 数据源 / 外部文字 | 原样文本与出处，不能生成 HTML 或改变权限 | 第二/四独立防注入与越权 |
| 详细问卷回退 | 保留已填、未知不变零、原始回答与推断分开 | 第二存储，第一/四确定必需依赖 |
| 真实交易请求 | 明确当前只支持模拟 | 任意确认不能开启 L4 |
