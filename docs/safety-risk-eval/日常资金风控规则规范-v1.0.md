# 日常资金风控规则规范 v1.0

日期：2026-10-17（北京时间）。规则版本：`daily-cashflow-policy.v1.0`。

**状态：第四板块可供开发与验收的规范；跨模块契约及接入待团队评审。** 本文固定判断口径、原因代码、默认行为和验收要求，不代表程序已实现、正式 Risk Owner 已接通或真实交易已开放。

维护范围：第四板块 Safety / Risk / Eval。核查代码基线：团队 `main` 的 `eddae8b093813cf8c32ed8aba979a7e9ca51ef08`。

## 1. 一页概览

系统要回答：**“按你确认的工资、学费、房租和生活安排，这次用钱会影响哪笔钱、在哪天缺多少、可以怎样调整？”**

采用三层判断：

1. **事实与硬约束：** 检查实际现金、专款、付款日期、已有占用；明确冲突阻止当前动作。
2. **财务提醒：** 预算比例、储备目标、收入压力等用于解释和建议；默认不阻断。
3. **执行门禁：** 风险检查之外，还要验证权限、完整计划确认、版本、幂等和审计。

| 规则 | 负责判断什么 | 典型结果 |
| --- | --- | --- |
| D01 | 资料、来源、时效、口径与计算是否足够可靠 | 缺必需资料需补充；必要核验失败则停止 |
| D02 | 本次安排是否占用专款、必要预留或硬性最低现金 | 已知冲突阻止；正常按原用途付款消耗其预留 |
| D03 | 各付款日是否有钱，先后顺序是否明确 | 已知到期缺口阻止；假设压力情景单独提示 |
| D04 | 同一资金是否被其他任务占用、是否重复记账 | 真实争用阻止；待对账补资料；服务失败停止 |
| D05 | 消费预算、比例参考和计划是否偏离 | 默认警告；明确启用接受策略才需复核 |
| D06 | 专门可用的应急储备是否低于个人目标 | 默认警告；硬性保底仍由 D02 检查 |
| D07 | 投资或转账的资金是否能在用款日前真正可用 | 已知不匹配阻止；依赖规则缺失则补证据 |
| D08 | 确认、版本、权限、幂等、网关与审计是否有效 | 未满足执行条件就不开启执行 |

规则检查对象是**安排及动作**，不将用户归类为贫穷、富裕、挥霍，也不生成缺乏验证的百分制风险总分。原投资 R01—R10 的集中度、行业、历史回撤等检查继续独立适用。

## 2. 范围与规范用语

- “必须”是本版的开发与验收要求；“建议”是解释或可选目标；“可”表示有条件支持。
- 首版规范的计算范围为单用户、明确资金池、人民币整数分，支持只读分析、未来条件方案和模拟执行前检查。
- 本轮交付规范、配置登记和声明式验收案例，不实现执行程序。当前真实交易继续禁止。
- 本版没有新增正式公网接口。后文英文名称是**逻辑字段提案**；共享命名及 Schema 由架构负责人统一，不得直接写入禁止额外属性的旧请求。
- 当前手工数据可以用于明确标识的分析。手工确认、模型归纳和沙箱布尔值不能替代正式身份、真实余额或可信 Memory。

## 3. 四种确认必须分清

| 对象 | 含义 | 不意味着什么 |
| --- | --- | --- |
| 事实确认 | 用户核对“工资何时到账、学费多少、余额是否已含工资” | 不使数据自动成为银行核验事实 |
| 用途／约束确认 | 用户明确一笔资金用途、保护额、期限、软硬属性 | 不批准任何具体付款或投资 |
| 柔性偏离接受 | 用户接受当前版本中需要接受的预算或储备提醒 | 不能覆盖硬冲突、补造证据或更改用途 |
| 完整计划确认 | 用户确认本次金额、费用、动作、日期、模式及风险 | 不能跳过执行前重检、实际权限与审计 |

原始回答、模型提取、系统建议、用户更正与确认分别保存。未知字段保持未知；模型不能用“看起来应该有”补成事实。用户只说“工资 8,000”，不能直接据此计算可投金额。

### 4.2 依赖按阶段判断

| 阶段 | 最小依赖 | 缺失时如何处理 |
| --- | --- | --- |
| 解释已知风险 | 相关已知事实、来源与用户意图 | 可以解释已知冲突，同时明确缺项；不签发执行资格 |
| 比较现在的可选安排 | 现金口径、保护额、占用、本次本金／费用、受影响付款与必要规则 | 必需缺项 `REVIEW`；本金已知可做条件分析，费用未知不能给完整额度结论 |
| 未来条件方案 | 上述信息及未来事件、日期、假设、受影响期限 | 标明条件及未评估范围；预计工资不进入当前可用余额 |
| 模拟执行前 | 最新可信一致快照、版本、权限、有效确认、幂等及审计 | 必要能力未接或失败即保持关闭；不得用离线结果冒充已接通 |

可选的 DTI、净资产、食品分类缺失，只将相应指标标为 `NOT_EVALUATED`；明确零分母或不适用标为 `NOT_APPLICABLE`。它们不是额外的 Risk 结果，也不自动导致整次检查失败。

## 5. 金额与账务计算规范

### 5.1 基本单位和去重

1. 计算用整数分；元到分由适配器按十进制转换，超过两位小数且无已确认舍入规则时请求修正。不能把元字段直接当分。
2. 比率按原始数值或精确交叉比较判断；界面四舍五入不改变是否触发。只支持已统一的币种，不按名义金额混加外币。
3. 以稳定事件 ID 识别同笔义务、预留、占用、扣款、退款；名称相似不构成可信关联。
4. 银行内部转账不创造合并收入或消费；具体付款账户仍须有可及时到账的资金。
5. 信用卡购买记消费和负债；还卡记现金流出及负债减少，不再记一次消费。全额账单和最低还款不是两笔叠加义务；不自动改用最低还款腾额度。

### 5.2 当前新增可安排额度

统一投影变量：

```text
C = 同资金池、同币种、同一时点的账面现金
H = 有效且尚未实付的占用合计
R_i = 每项已确认、现在必须保护的剩余金额
cov_i = H 中可信关联且可覆盖同项用途的金额
U_i = max(0, R_i - cov_i)
E = 未与上述用途或占用重叠的独立硬性保底
F = C - H - ΣU_i - E

可新增安排 = max(0, F)
已有保护缺口 = max(0, -F)
```

每笔占用的覆盖合计不得超过自身金额，每元资金只扣一次。缺口可以为正，F 可以为负；不得删减学费使输入“通过”。

E 是每个状态重新计算的结果，不是永久固定参数：`E = max(0, 已启用硬性最低额 - 当前仍有效的可信覆盖额)`。覆盖额不得超过该最低额，也不得跨用途重复归属。支用覆盖它的应急保护后，原硬底线仍有效时必须恢复相应独立保底；不能沿用支付前的 E＝0 来绕过最低现金。形成确定后续扣款的占用，还须检查相应结算终态。

仅在接口确认 `A = C - H` 且冻结范围完全一致时，可等价使用 `F = A - ΣU_i - E`。否则先对账，不从净可用额再次扣相同冻结。

`required_reserved_now_minor` 与未来 `remaining_due_minor` 不要求相等。例如未来学费尚欠 6,000、现在确认专款 2,000：2,000 进入当前保护，6,000 按真实到期日进入现金流。不能把未来全年账单自动全部锁定；也不能因仅预留 2,000 就在到期日只检查 2,000。

当前保护区间和覆盖范围必须用户确认。未预留的已知账单仍参与 D03；明确“这笔钱全部是学费、不得挪用”时，不能只保护其中一小部分来取得通过。

### 5.3 动作必须按前后状态检查

| 动作 | 账务变化 | 检查重点 |
| --- | --- | --- |
| 新增投资占用 a | H 增加 a，账面 C 暂不减 | a 包含需冻结的本金与费用；转冻结不是再增加一笔本金负担 |
| 立即付款 a | C 减少 a | 付款渠道可用、其他硬保护满足；已计入同笔待付事件时不再投影一次 |
| 原用途付款 | C 减实际付款，同时按可信关联减少对应 R；结算已有 H 时配对解除 H | 不拿 F 直接挡原学费；超过原预留的部分及费用仍需自由额度 |
| 可信取消／释放 | 按原记录减少相应 H | 由执行端提供释放结果，不接受模型自称取消 |
| 入账／退款 | 按实际结果增加 C，关联原事件及用途 | 入账后再重算；预期退款不增加当前现金，已有缺口不阻止可信补资 |

匹配付款的预留消耗固定为 `min(支付前 R, 本次经核验可覆盖该用途的金额)`，不得减出负预留。同笔 `remaining_due_minor` 按实际结算的本金减少，费用另列；部分结算只解除对应占用部分。已入账付款从未来事件中移除或减少，防止到期日再次扣款。若付款超出该账单尚欠额，超出部分必须有独立已确认用途，不能塞进原账单。

原用途付款后，仍必须验证现金可结算、其他独立硬保护未被挪用。多个必要用途已经竞争同一笔不足资金时，不能仅凭“总缺口不增加”自动选一个先付：已知违反其他保护则阻止；归属或付款安排不明则补充确认。保留全部未付义务及缺口，系统不自行取消学费、改成最低还款或建议借款补齐后当作已经解决。

## 6. 日期与现金流规范

1. 起点为 `as_of` 的可信账本。已计入该快照的工资、扣款不再作为未来事件。
2. 窗口覆盖本次动作及所有已确认受影响用款日；不得任意截短以隐藏已知学费。未覆盖部分明确列出，不宣称长期安全。
3. 按实际时间递推 C、H、R；付款减少 C，同时解除其占用、消耗对应预留。预留不是第二笔现金支出。
4. 只有日期而无同日先后时，可以展示“先付后收”的保守情景；若结论依赖先后，返回 `PAYMENT_ORDER_UNVERIFIED`，补证据后再决定，不把保守假设冒充确定事实。
5. 预计收入只在带来源和日期假设的未来视图出现，不能增加现在可执行／可冻结的额度。正面未来预测不能解除 D02 的当前冲突。
6. 未来基线若在用户确认的到账假设下仍出现付款缺口，说明“在当前计划及假设下”的日期和金额；不能说成必然违约。付款日晚于工资日不明时先补资料。
7. 工资延迟、收入下降、费用增加等压力情景单独显示。它们本身只提醒，不自动修改用户约束或生成发生概率；实际确认延迟后更新事实并重检。
8. 交易日、赎回、结算、费用和转账限额由第三板块提供。最早可用日晚于付款日可以证明赶不上；最早日早于付款日不能证明按时可用，须检查有证据支持的最晚可用时间或明确到账事实。区间不能覆盖、时点不明而方案依赖该资金时补充证据。Risk 不自行编造节假日到账或保证基金按市值变现。

## 7. Risk 结果、提醒与执行状态

### 7.1 四态结果

| Risk 结果 | 准确定义 | 执行影响 |
| --- | --- | --- |
| `ALLOW` | 适用范围内必需检查已完成，未触发阻止或待解决复核 | 只允许进入下一道门禁，不代表已授权 |
| `REVIEW` | 缺必需资料、需重检／确认，或用户启用的柔性偏离接受尚未完成 | 相关动作等待；区分补证据与接受提醒 |
| `BLOCK` | 当前拟议动作违反已确认保护、资金或权限要求 | 阻止当前动作，修改后重检；不能勾选绕过 |
| `ERROR` | 必要计算、契约、可信账本、授权核验或审计无法可靠完成 | 检查未完成，停止依赖动作并保留故障 |

聚合顺序：只要有必要检查 `ERROR`，整体为 `ERROR` 并保留已知 `BLOCK`；无 `ERROR` 时 `BLOCK > REVIEW > ALLOW`。全部触发原因都保留，不让一个提醒覆盖硬冲突。

普通 `warnings` 和 `INFO` 不构成第五种结果，可与 `ALLOW` 同时出现。正常分析还未审批时，风险结果可以为 `ALLOW`，执行门禁仍关闭；不把“还没点确认”伪装成金融风险。

### 7.2 复核和接受

- **必须修复：** 必需数据缺失、对账、同日顺序、费用或变现规则不明、旧版本。补证据或重检，不能勾选跳过。
- **可以接受：** 用户事先明确启用的柔性目标偏离接受，以及原 R 规则明定可接受的风险。逐项接受绑定当前版本，再确认完整计划。
- 本版选择**追加核验记录**：原评估的 `REVIEW` 和全部原因不改写；当前版本逐项接受后，重新核验所有适用条件。若无其他待处理项，追加新的评估，当前 `risk_status` 为 `ALLOW`，并关联原评估、接受记录及原原因。当前仍为 `REVIEW` 时执行始终等待。
- 因此 `unresolved_review_count=0` 不是单独放行凭据。没有新核验结果、有效接受、完整计划确认及其他门禁时不能就绪；补证据类不能仅靠接受转为通过。

## 8. 八条规则与固定原因

### D01：数据、口径与计算可用性

- **触发：** 当前动作依赖的余额、费用、保护范围、日期或必要证据缺失；数据过期；必需 Schema、版本关联或计算服务校验失败。
- **结果：** 缺失／已知过期为补资料类 `REVIEW`；必要契约不一致或服务失败为 `ERROR`。用户在输入阶段的笔误先询问修正；不能把业务已有缺口判成坏数据。
- **原因：** `DAILY_DATA_REQUIRED`、`DAILY_DATA_STALE`、`DAILY_DATA_INCONSISTENT`、`DAILY_CHECK_UNAVAILABLE`。
- **提示：** “还不知道学费到期日，本次不能判断投资是否影响缴费。”／“余额核验失败，相关执行暂停。”
- **恢复：** 用户补充并确认；数据 Owner 更新／对账；必要服务恢复后重检。可选指标未评估不阻断无关功能。

### D02：当前资金、专款与硬性保底

- **触发：** 新增可选流出或占用超过 F；付款不能实际结算；已知挪用他项硬保护；剩余独立硬性保底不足。
- **结果：** `BLOCK`。等于额度不超限，超过 1 分也超限。原用途付款按第 5.3 节投影，不直接比较 F 与付款全额。
- **原因：** `PROTECTED_PURPOSE_CONFLICT`、`PAYMENT_CASH_INSUFFICIENT`、`HARD_FLOOR_CONFLICT`。原用途关联未核实先为 `REVIEW / PURPOSE_LINK_UNVERIFIED`。
- **提示：** “本次投资比未分配额度多 6,000 元，会占用你确认的学费。”
- **恢复：** 降低／延后动作、可信补资或独立修改资金安排后重检。用途修订必须保留历史和仍存在的应付义务，不能用勾选接受覆盖。

### D03：到期现金流与先后顺序

- **触发：** 当前计划基线在相关付款日无法覆盖已确认义务；或结论依赖未核实的同日先后。
- **结果：** 证据和顺序完整的基线缺口为 `BLOCK / PAYMENT_DATE_GAP`；顺序缺失为必须修复的 `REVIEW / PAYMENT_ORDER_UNVERIFIED`。基于预计收入的结果必须保留假设限定。
- **提醒：** `FUTURE_CASHFLOW_ASSUMPTION` 说明未来到账依赖；`CASHFLOW_STRESS_GAP` 只显示假设压力下的缺口，不单独变成 `BLOCK`。
- **提示：** “学费 20 日到期，工资预计 25 日到账；按当前安排，20 日差 2,000 元。”
- **恢复：** 修改可选动作金额／日期、核实付款或到账安排、补足可用资金后重算。系统不承诺工资一定到账。

### D04：跨任务占用与账务重复

- **触发：** 同资金池有效占用和本动作合计超额；同笔记录尚未对账；必要共享账本不可用。
- **结果：** 真实争用 `BLOCK / SHARED_FUNDS_CONFLICT`；待对账 `REVIEW / SHARED_FUNDS_RECONCILIATION_REQUIRED`；服务不可用 `ERROR / SHARED_LEDGER_UNAVAILABLE`。
- **提示：** “另一任务已占用 2,000 元，本次需要按最新余额重新检查。”
- **恢复：** 可信核查／释放后原子重检。Risk 返回通过不预占资金；Gateway 必须使用事务或等效 CAS 重读并建立唯一占用，两个并发任务不能共用旧额度。

### D05：预算与比例提醒

- **触发：** 同期间、同类别的去重实际消费及尚未包含的本次消费超过用户软预算；或偏离明确启用的参考模板。
- **结果：** 默认 `WARNING`，Risk 可以保持 `ALLOW`。用户明确将该软目标设为“偏离须逐项接受”且当前接受未完成时，才为可接受类 `REVIEW`；完成后按第 7.2 节追加核验，不覆盖旧评估。教育参考比例本身不产生硬拦截。
- **原因：** `PERSONAL_BUDGET_EXCEEDED`、`BUDGET_REFERENCE_DEVIATION`。
- **提示：** “本月订阅预算还剩 100 元，本次需 160 元，预计超出 60 元。”
- **恢复：** 用户可减少／取消可选消费、调整对应预算或接受柔性提醒；调整只影响对应范围，投资不自动并入订阅。用户另设硬上限时走 D02，不能接受绕过。

### D06：应急储备目标

- **触发：** 付款／安排后的专门可用应急储备低于用户启用的柔性金额或月数目标。
- **公式：** 应急覆盖月数＝可及时使用、未被他项用途占用的应急储备／用户确认的月必要现金支出。未分配现金不自动同时算应急金。
- **结果：** 默认 `WARNING / RESERVE_TARGET_SHORTFALL`；仅明确启用偏离接受策略且当前尚未接受时为可接受类 `REVIEW`，接受后追加核验。未设目标只说明未配置，不生成不足结论；零分母不计算。
- **提示：** “目前专门应急资金覆盖约 2 个月必要支出，低于你选择的 3 个月目标。”
- **恢复：** 讨论逐步补足目标或调整本次可选安排。正常应急用途付款可以消耗对应储备；硬性保底另由 D02 检查，同笔金额不重复扣。

### D07：资金期限与变现

- **触发：** 方案将保护用途资金放入无法及时取出的产品；或本次结论依赖的赎回、结算、转账费用／可用日期缺失。
- **结果：** 已知保护用款无法按时覆盖为 `BLOCK / LIQUIDITY_DATE_MISMATCH`；依赖证据缺失为必须修复的 `REVIEW / LIQUIDITY_EVIDENCE_REQUIRED`。
- **提示：** “这笔学费下周要付，当前产品的可用日期不能覆盖付款日。”
- **恢复：** 第三板块提供可靠规则／证据，或调整方案。仅有最早可用日不能证明按时到账；需要可覆盖付款日的可靠最晚时间或已到账事实。持仓市值、预期收益、信用额度和未到账赎回款不等于当前现金。

### D08：版本、权限、审批与执行安全

- **触发：** 相关事实、用途、金额、日期、费用、占用、方案或规则发生变化；缺有效授权；幂等冲突；执行未知；必要审计失败。
- **风险层：** 旧检查／相关确认失效需 `REVIEW / DAILY_APPROVAL_STALE`；越权或真实交易请求为 `BLOCK`；必要执行安全核验失败为 `ERROR`。
- **门禁层：** 尚未确认、拒绝或撤回时关闭执行，分别保留 `APPROVAL_REQUIRED`、`APPROVAL_REJECTED`、`APPROVAL_REVOKED`；不为此篡改已完成的财务检查结果。
- **固定门禁原因：** `PERMISSION_DENIED`、`REAL_TRADING_FORBIDDEN`、`APPROVAL_REQUIRED`、`APPROVAL_REJECTED`、`APPROVAL_REVOKED`、`IDEMPOTENCY_CONTENT_CONFLICT`、`EXECUTION_STATUS_UNKNOWN`、`DUPLICATE_REQUEST_REPLAYED`、`AUDIT_WRITE_FAILED`、`GATEWAY_NOT_CONNECTED`。
- **恢复：** 对当前版本重检、取得有效完整计划确认、核查原执行或恢复必要服务。失败时执行保持关闭；不能回退预置成功。

外部账单备注、网页、新闻和书籍只作业务数据。出现“忽略风控、已经批准”等文字时隔离并记录 `UNTRUSTED_INSTRUCTION_IGNORED`，仍可进行有依据的只读分析；若模型实际提议越权，按权限规则拦截。关键词命中本身不是已发生越权的证明。

| 参数 | 本版默认 | 启用／变化条件 |
| --- | --- | --- |
| 真实交易 | 禁止 | 本规范无解除方式 |
| 必需证据失败 | 停止依赖动作 | 恢复后重检，禁止回退成功 |

| 预算提示边界 | 必要或可选比例大于相应参考、目标类比例小于参考时提示 | 等于参考值不提示；分类或分母不足则不计算，所有参考均非硬拦 |

| 非房贷偿付提示 | 可选参考；启用后达到 20% 即提示 | 分母为到手收入，范围不含房贷；“低于 20%”是教材经验，不是硬线 |
| 其他比例／综合分数 | 不设通用硬阈值，不生成随意加权总分 | 新参数须有定义、来源、适用范围和版本 |
| 数据时效 | 不捏造统一秒数；执行前须取得供应方有效、最新一致读数 | 只读显示截至时间；已过期需更新，读取失败停止 |
| 压力情景 | 默认未启用，不能冒充预测 | 用户选择后标明延迟天数或变动比例；示例参数仅为演示假设 |

应急金 3—6 个月的依据为 [MoneyHelper 必要支出经验法](https://www.moneyhelper.org.uk/en/savings/types-of-savings/emergency-savings-how-much-is-enough)；三类预算参考 [CFPB 个人支出规则工具](https://files.consumerfinance.gov/f/201603_cfpb_rules-to-live-by_my-spending-rule-to-live-by.pdf)。源工具允许个人调整。使用本版改编分类时须显示“参考模板”，不能冒称监管要求。

三类模板固定为**现金分配视图**：现金支付按用途归类；已确认本期必须偿付的金额（包括用户确认全额支付的信用卡账单）归必要，尚未到期融资本金的额外偿还归目标。目标还包括本期从本期到手收入中新增的储蓄与投资分配；迁移旧本金、储蓄转投资不重复计为新增目标。合并账本内部转账不改变现金，但新收入的首次储蓄分配可在该视图计一次，二者分开显示。

信用卡刷卡在消费结构视图计购买，现金分配模板只在偿付／分配时计一次，不再加入同笔刷卡。来源或去重不明时该比例未评估。实际付款不因动用旧存款或借款而被删去；收入不能覆盖实际付款时如实显示缺口，不强行凑成 100%。这个模板与消费结构统计不能混成一张比例表。

## 10. 补充财务指标怎样使用

| 指标 | 固定口径 | 不可据此自动得出的结论 |
| --- | --- | --- |
| 净现金流 | 同期间实际流入减实际流出，借款／变现单列，合并剔除内部转账 | 月末正数不保证每个付款日安全 |
| 学费积累 | 正的剩余缺口／到期前剩余可储蓄周期；周期 0 直接显示缺口 | 计划每周存 500 不等于已经存入 |
| 标准 DTI | 全部月度偿付／税前月总收入 | 不同贷款限值不能移植成所有人的投资许可线 |
| 非房贷偿付 | 非房贷信用还款／到手收入 | 不与含房贷 DTI 混比 |
| 资产负债率、净资产 | 同时点负债／资产；资产减负债 | 房产或基金市值不等于可结算现金，净资产负数不等于法律破产 |
| 食品烟酒消费占比 | 同期间食品烟酒／同口径消费总支出 | 不用食品／工资替代，不据全国均值判断用户是否可投 |

储蓄和投资比例只作参考，不把“工资的 20%”当成可投额度。金额、日期与证据不足时，参考指标不能补齐执行依据。

## 11. 完整确认、执行与异常规则

### 11.1 确认绑定

完整计划确认必须绑定：用户与权限范围、同一任务及提议哈希、全部动作、本金／费用／额外占用、日期、数据及执行模式、事实／用途／约束／数据／规则版本、需接受的原因与未知项。服务端验证确认人和凭据，前端 `approved=true` 或模型自述不是授权。

相关金额、用途、日期、费用或资金／占用版本变化使旧检查失效；影响确认内容时旧未执行授权也失效。仅说明文字或无关头像等变化不强制重做。相同数据版本的重新读取可用于时效核验，不能借“刷新”改变实质内容后沿用旧批准。

用户拒绝／撤回即停止未执行动作。确认有效期及身份策略必须由授权服务明确提供；未接策略时正式执行关闭。不能将已经批准理解为永久有效。

### 11.2 原子执行门禁

执行端必须在同一事务或等效机制中：

1. 校验当前用户、任务、方案、规则和相关版本，读取最新一致资金及占用。
2. 验证适用 Risk 已完成，无未解决硬冲突／修复类复核，需接受事项均已有效接受。
3. 验证完整计划确认、未拒绝／撤回／失效、当前权限仅允许模拟。
4. 验证幂等键与内容哈希，确认无未查明的旧执行结果。
5. 将执行意图审计成功持久记录，再建立唯一占用或实施相应模拟账务变化。
6. 返回可关联回执并记录结果。这里是待实现的执行要求，不是已有内存账本的能力证明。

只有执行回执确认成功，才能显示“模拟完成”。等待审批、风险拒绝、网关未接和服务错误均不能显示完成。当前 Core 的 `execution_allowed:false` 保持原语义，不因内部检查通过改成真实执行授权。

### 11.3 重复、未知和审计故障

- 同幂等键、同内容已成功：返回原回执，不再写一次；同键不同内容：阻止并使用新方案流程。
- 超时或执行结果未知：保留原执行标识及安全占用，先查询，不自动释放、改键或重试产生第二笔。
- 执行前必要审计失败：`ERROR / AUDIT_WRITE_FAILED`，不执行。
- 执行已获成功回执但结果审计补写失败：保留成功事实、显示审计缺口并暂停后续依赖动作；不把它改成未成交，也不重做交易。
- 取消只按可信取消回执释放；撤回请求与实际执行有竞态时先核查最终状态，不能保证撤回一定先发生。

## 12. 输出与界面规范

每条风险原因至少包含：稳定规则编号、固定代码、中文说明、实际值、阈值或缺口、币种／期间／日期、证据引用、是否可接受、暂停动作、恢复动作和负责模块。没有适用阈值时记录无，不伪造为 0。

界面须分开显示：

1. 当前事实和假设：截至时间、手工／虚构／真实服务、预计收入。
2. 检查结果：`ALLOW / REVIEW / BLOCK / ERROR`，全部原因及未评估项。
3. 财务提醒：预算、储备和情景；普通提醒与必须处理项分开。
4. 确认与执行：未确认、已拒绝、待重检、执行未知、模拟成功等真实状态。
5. 可选修改：具体减少／延后多少、补充什么资料；建议不是自动下单或自动修改用户约束。
6. 运行与审计关联：任务、运行、检查和审计标识；不展示秘密凭据。

固定解释顺序：**发现 → 依据 → 影响 → 可选修改 → 恢复条件**。例如：

> 你目前有 12,000 元现金，已含本月工资。按已确认的学费 6,000、房租 1,500 和生活费 2,500，未分配额为 2,000 元。今天投入 8,000 元会占用 6,000 元必要资金，因此当前计划被阻止。可以降低或延后本次投资，修改后重新检查。2,000 元只是当前用途检查的额度，不是推荐投资额。

## 14. 对接现有 Golden Path

| 位置与负责人 | 按本规范要提供／执行的内容 | 现状与接入边界 |
| --- | --- | --- |
| 用户输入 → Core / UI | 待确认清单、更正、用途确认与阶段标识 | 10 月 17 日清单试验仍未接真实 Memory、未形成可信余额 |
| Context / Memory | 带来源的确认事实、保护版本、身份和可验证引用 | 用户陈述与前端布尔值不能替代正式授权 |
| 数据 / Quant / Backend | 整数分适配、日期与费用、当前账本、占用、变现规则 | Python 工具部分使用元浮点及 `passed/checks`，必须显式适配 |
| Risk Owner | 执行 D01—D08、保留警告和接受义务、返回可追踪结果 | 本文定义要求；正式 Owner 地址、签名及共同验证仍待完成 |
| Core / UI | 展示理由与提示、请求完整计划确认，保持同一任务 | 不重新生成另一套工作台逻辑来假装接通 |
| Action Gateway / Backend | 最新快照、原子占用、幂等、有效确认、执行回执 | 现有演示资金计划不证明跨实例原子性；未接网关阻断保持 |

兼容约定：

- `risk-handoff.v1` 的 `reviewed_input` 权威为 `UNVERIFIED_CALLER_INPUT`；`funding-plan-demo.v1` 明确为虚构沙箱，authority 为 `DEMO_USER_CONFIRMED_NOT_TRUSTED_MEMORY`。
- 现有资金 Purpose 只有 ID、名称、金额，没有完整日期／账单关联；创建时还会拒绝“保护额大于现金”。日常分析必须另有能表示真实缺口的扩展，不能要求用户改小账单。
- Risk 四态与 Core 回调三值分开。只有全部适用检查完成、当前接受义务已解决才可适配 `APPROVE`；它仍是 Risk 回调，不是用户批准。
- 硬阻止可适配 `REJECT`，当前 Core 会进入终态；修改方案按新任务规则处理。补资料类可适配 `REQUEST_MORE_INFO`，按现有协议重建复核任务。
- 可接受复核尚未解决时保持等待；按第 7.2 节追加的当前 `ALLOW` 核验及原复核／接受证据，才可按约定适配。`ERROR` 保留错误与停止，不能直接塞入三值枚举。所需扩展由架构 Owner 审定，禁止一律映射批准。
- 不混用顶层决策计划 `plan_id` 与资金计划 ID。保持 task、run、audit、handoff、提议哈希的原始关联。

## 15. 验收案例与交付门槛

1. 保留 D01—D08 编号；D05、D06 从“柔性偏离一般进入 REVIEW”收敛为默认警告，明确启用接受策略才复核。
