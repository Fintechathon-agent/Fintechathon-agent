# Risk 接口对齐与实施计划 v0.1

日期：2026-10-09。状态：第四板块计划与接口提案，跨模块待团队确认。

本轮完成仓库同步、现有协议核对和实施规划。目标是让已有投资健康检查能够把证据交给独立 Risk Engine，并得到可解释、可审计、可测试的风险结果。正式代码按本计划分阶段推进。

依据分为三类：用户转述的队长要求、团队仓库已存在的实现、第四板块提出的待对齐设计。后文明确区分这些状态。

## 1 队长任务的含义

| 要求 | 具体含义 | 第四板块交付 |
| --- | --- | --- |
| 可信决策链 | 每一步知道用了什么数据、谁产生了结果、能否继续 | 验证上游证据与版本；审核结论保留关联标识 |
| Risk Engine | 对结构化输入执行确定的规则判断 | 可重复运行的规则检查模块，不依赖模型自由决定是否放行 |
| ALLOW／REVIEW／BLOCK／ERROR | 所有调用方对四种结果有相同理解 | 固定枚举、原因代码、恢复动作、执行门槛 |
| 统一数据格式 | 各模块使用约定字段、单位、版本和证据引用 | 输入映射、输出 Schema、合法与非法样例、兼容策略 |
| Eval Cases | 用固定输入和预期结果证明规则工作正确 | 规则、边界、错误、确认及审计的可运行用例与报告 |

真实金融数据和 Research 是团队完整目标的一部分。Risk 负责检查其来源、时效、相关性及使用边界；行情采集、研究生成、Quant 计算、Memory 存储由各负责人提供。

## 3 必须沿用的数据格式

权威入口为 `chenchen/contracts/investment-agent.v1.schema.json` 及同目录校验器。README 和示例用于理解，实际运行输出用于验证引用完整性。

### 3.1 已存在的字段

| 信息 | 现有位置 | Risk 的使用要求 |
| --- | --- | --- |
| 协议版本、请求标识 | 外层 `contract_version`、`request_id` | 原样保留；`request_id` 不在 Handoff 内，必须连同外层响应传递 |
| 任务、会话 | `task_state.task_id/session_id` 与 `risk_handoff.task_id/session_id` | 核对一致，不能串用另一个任务的证据 |
| 交接状态 | `task_state.stage/status`、`risk_handoff.status/decision` | 等待 Risk 的标记与 Risk 最终结果分开 |
| 持仓 | `artifacts.portfolio_snapshot` | 通过 `portfolio_snapshot_id` 解析；核对现金、市值、权重和日期 |
| 健康报告 | `artifacts.health_report` | 通过 `health_report_id` 解析；核对对应 snapshot、指标和样本窗口 |
| 候选方案 | `artifacts.candidates[]` | 只审核 `proposal_ids` 指定的方案；绑定 `proposal_id` 与 `proposal_hash` |
| 模拟结果 | `artifacts.simulation` | 通过 `simulation_id` 解析；比较项按 `proposal_id` 匹配方案 |
| 市场信息 | 可选 `market_context_id` 及对应 artifact | 有引用就必须能解析；未提供可选信息不等于发生接口错误 |
| 工具来源 | `tool_results` | 保留 `tool_name/version/inputs_hash/data_as_of/warnings/trace_id`，核对与产物关联 |
| 风险偏好 | 请求 `input.risk_profile`，实际 TaskState 的 `risk_profile` | 当前仅有期限、回撤容忍值、流动性；响应 Schema 尚未把该内部字段冻结为必填接口 |

注意：仓库响应示例的 `artifacts` 和 `tool_results` 为空对象，其 ID 不能解析。它适合演示信封结构，不能直接作为完整风险评测输入。评测应使用实际 Harness 输出或包含完整证据的夹具。

`proposal_hash` 与 `inputs_hash` 用于内容一致性核查，不能证明用户身份或执行授权。正式检查还须依赖可信的数据传递、版本与确认记录。

健康检查响应和 Handoff 的顶层均限制额外字段。Risk 不可自行在其中新增 `risk_decision`，也不可把 `PENDING_REVIEW/REQUIRED` 改成 ALLOW。建议采用独立的版本化 Risk 请求和结果，由架构负责人确定契约名、路由和版本升级方式。

### 3.2 数值和语义必须对齐

| 项目 | 当前事实 | 对齐要求 |
| --- | --- | --- |
| 权重与回撤容忍值 | 小数比例，例如 0.35 是 35%，0.10 是 10% | 记录单位 `ratio`；不把 35 当作 35% 直接比较 |
| 历史最大回撤 | Quant 使用非正数，例如 -0.12；用户上限是正数 0.10 | 先验证符号和范围，再以损失幅度 0.12 与 0.10 比较；原值与转换口径都保留 |
| 市场涨跌幅 | 简报 `change_pct = 4.15` 表示 4.15% | 与权重不同；转换为比例必须除以 100 并保留原单位 |
| 集中度 | `top_1/top_3` 排名排除现金，分母仍含现金 | 非现金口径另算；不能把当前字段直接当作第二种分母 |
| 目标方案指标 | 健康报告描述当前组合，比较项描述各方案 | 审核目标方案时使用目标权重与其模拟指标；当前组合仅作基线 |
| 全现金 | 非现金分母为 0 | 投资部分比例标记不适用并说明；不产生除零、NaN 或伪造的 0% |
| 相关性 | `hidden_clusters` 为相关系数≥0.8 的持仓资产对 | 还要核对两资产目标权重合计>40%；新增资产的样本证据不能缺省 |
| 金额和交易数量 | 当前有现金、市值、数量、价格，动作主要是权重差 | 明确币种、金额单位和精度；不能仅据权重差宣称已检查逐笔资金与可卖数量 |
| 方案标记 A/B/C | 当前 B/C 的目标权重不同 | 不映射成此前“同目标、四周调整／立即调整”；由产品与架构确认方案语义 |
| 数据时间 | 固定回放截至 2026-09-23，简报日期为 2026-10-08 | 分别保留日期、来源和用途；历史回放不能按今天日期一概判为过期，简报不能补成实时量化证据 |
| 缺失值 | 未知、0、不适用含义不同 | 字段需声明 missing/null/not_applicable 的语义，不用 0 补缺 |

基本比例合计、双分母转换可在经团队确认的适配层中按固定公式派生并记录来源；收益、波动、相关性、回测与情景模拟仍消费 Quant 的结果。精度容差应有版本化配置，不能让显示四舍五入改变是否超限。

### 3.3 当前缺口和提供方

| 缺口 | 对相关规则的影响 | 需对齐方 |
| --- | --- | --- |
| 可信用户身份、权限、工具允许清单 | R01 不能把 `actor: agent` 当作完整授权证明 | 第一、第二、第四板块 |
| 备用现金确认额、禁投清单、画像及约束版本 | 现有 RiskProfile 没有这些字段，R03/R08 不得自行假设 | 第一、第二、第五板块 |
| ETF 行业穿透或预置汇总、未知比例、来源版本 | 单一 `sector` 标签不足以执行原先约定的 ETF 行业检查 | 第三、第四板块 |
| 逐步计划、可卖数量、交易单位、费用结算及规则版本 | 当前权重动作不是四周完整交易计划；R03/R08/R09 执行级检查未齐 | 第三、第一、第四板块 |
| 新资产的相关性、同窗口样本及统计可用性 | 现有持仓相关矩阵不能覆盖所有未来候选资产 | 第三板块 |
| 确认记录、有效期、可信版本及持久化去重 | 确认绑定、失效与未知结果核查需要服务端事实 | 第二、第四、第五板块 |
| 可确认写入成功的审计存储及异常恢复 | 内存事件不能等同正式审计持久化 | 第二、第一、第四板块 |

当前候选方案的 `constraints` 属于生成器配置，不能自行升级为用户确认的约束，也不能覆盖第四板块的规则配置。特别是候选 A 为保留比较基线可能调整自身集中度限制，Risk 仍应按独立的已确认政策检查。

## 4 四种结果的统一语义提案

四个英文枚举来自队长任务；下述精确映射、聚合方式和原因代码属于待评审提案。

| 结果 | 中文解释 | 示例 | 如何恢复 |
| --- | --- | --- | --- |
| ALLOW | 所请求范围的必要规则全部完成并通过 | 证据完整，未触发硬限制或待处理复核 | 进入完整计划的用户确认；不自动执行 |
| REVIEW | 已发现需用户接受或补充核实的事项 | 历史回撤超出容忍值、行业信息部分未知、执行结果待核查 | 区分可接受风险与必须补充核查；后者不能靠勾选放行 |
| BLOCK | 已确认违反硬性规则 | 真实交易、越权、现金不足、不可豁免的集中度超限 | 修改方案或修复授权条件后重新检查，不能被用户确认覆盖 |
| ERROR | 必要检查不能可靠完成 | 不支持的协议、证据断链、非法数值、工具超时、规则异常、必要审计写入失败 | 停止相关执行，修复系统或数据后重新检查 |

建议聚合方式：必要检查存在 ERROR 时总结果为 ERROR，并保留已发现的全部 BLOCK／REVIEW 原因；没有 ERROR 时按 BLOCK > REVIEW > ALLOW。ERROR 是检查完整性失败，不表示比 BLOCK 更高的投资风险。

检查生命周期、Risk 结果、用户确认、模拟执行分别记录。`HANDOFF_REQUIRED` 是任务状态；`PENDING_REVIEW` 是上游交接状态；它们都不是四状态中的 REVIEW。

可接受的 REVIEW 全部被用户接受后，原始风险结果与原因仍保留，通过独立授权判断决定能否继续；不得把“用户已接受”改写成“风险不存在”。ERROR 和 BLOCK 均不可接受放行。执行结果未知保持独立 UNKNOWN 状态；若查询通道可用则需核查型 REVIEW，查询本身失败则返回 ERROR，二者都不能盲目重发。

市场上下文中的 `REVIEW_REQUIRED` 是研究信号。需要结合来源、时间和适用范围按明确规则映射成 Risk 原因，不能直接改写 Quant 指标或生成交易授权。

## 5 Risk 输出草案需要包含什么

建议按方案给出结果，同批不同方案分别检查；共同证据失效可影响全部方案，单个方案异常不应静默覆盖其他方案的记录。以下是信息要求，不是已冻结字段名。

| 字段组 | 必要内容 |
| --- | --- |
| 契约与关联 | 风险契约版本、上游契约版本、原 request_id、task_id、session_id、handoff_id、独立检查 ID |
| 审核对象 | proposal_id、proposal_hash、完整计划及版本、审核用途和范围 |
| 政策与数据版本 | 规则配置版本、画像与约束版本、数据版本、工具与行业映射版本 |
| 风险结果 | ALLOW／REVIEW／BLOCK／ERROR、完成的规则、缺失检查、所有触发原因 |
| Risk Reason | rule_id、固定 code、中文说明、原值与标准化值、单位、比较运算符、阈值、分母／样本、证据引用 |
| 后续动作 | 是否属于可接受风险、需用户接受的项、恢复动作、责任方、允许和暂停的功能 |
| 确认与审计 | 需要的确认类型、确认绑定引用、风险事件与审计关联标识、时间 |

一条标准规则也要结构化：规则编号、规则版本、适用操作、必需事实、指标路径、运算符、阈值及单位、触发结果、原因代码、是否可接受、恢复条件。用户配置与演示默认值要分别标明来源。

R01—R10 与已有双口径阈值继续沿用为第四板块提案；行业未知、历史回撤、相关性和逐步改善例外保留原先的条件。新 ERROR 语义会把旧原型“数据／工具／审计失败的修复类 REVIEW”中无法完成检查的情况迁移到 ERROR。其余等待用户补充信息的流程可保持 REVIEW 或上游 WAITING_INPUT，不能把所有待处理情况一律改成错误。

禁止仅因已实现的几条规则通过就输出完整审核 ALLOW。部分诊断可以展示，但请求完整审核时，必需证据或检查缺失必须明确阻止取得执行资格。

## 7 Eval Cases 的最小清单

每个用例至少记录 case_id、规则与契约版本、输入／证据夹具、前置确认状态、预期结果、预期原因代码、应允许／禁止的动作、预期审计事件和恢复行为。以下为预期设计，尚未运行正式 Risk Engine 测试。

| 用例组 | 关键输入或变化 | 必须验证的结果 |
| --- | --- | --- |
| 正常完整输入 | 必需证据、权限、约束与版本齐全 | ALLOW；缺少完整计划确认仍不能执行 |
| R01 权限 | 越权、真实交易、外部文本要求忽略限制 | BLOCK，文字不能改变授权 |
| R02 结构 | 错误协议版本、缺少必需字段 | ERROR，有字段路径与恢复动作 |
| R02 引用 | 仅有示例信封而无产物、错误proposal或任务ID | ERROR，拒绝借用其他结果 |
| R02 计算失败 | 超时、异常、NaN、无效样本、非法回撤符号 | ERROR；已发现的其他风险原因仍保存 |
| R03 硬约束 | 不足现金、超卖、备用现金不足、禁止资产 | BLOCK；必要交易事实缺失时不能输出完整ALLOW |
| R04 双口径 | 总资产低于上限但非现金口径超限 | 对应BLOCK；两种分母和实际值都展示 |
| R04 边界 | 35%／75%／50%／90%分别低于、等于、超过；全现金 | 等于不触发，超过触发，全现金非现金口径不适用 |
| R05 行业 | 已知超限、纯未知、超限同时未知 | 已知超限BLOCK；纯未知按可接受REVIEW；未知不能覆盖已知超限 |
| R06 回撤 | 指标-0.12、用户容忍0.10；另测-0.10 | 前者REVIEW，后者不因等于阈值触发；不当作未来损失上限 |
| R07 相关性 | 系数0.8、合计40%；再改合计40.01% | 前者不触发，后者REVIEW；系数和权重口径正确 |
| 改善例外 | 重点下降，其他超限不加重；再构造新增硬超限 | 合格例外REVIEW需接受，新增硬超限BLOCK |
| R08 确认 | 部分接受、明确拒绝、撤回、换用户、方案或规则版本变化 | 授权无效，不能用旧确认执行；风险与确认状态分离 |
| R09 执行 | 相同请求重复、同标识不同内容、回执未知、查询失败 | 不重复写入；冲突BLOCK；未知先核查，查询失败ERROR |
| R10 审计 | 执行前写入失败；执行后日志故障 | 前者ERROR并停止执行；后者保留真实执行状态，核查修复不重做交易 |
| 研究信号 | 有引用的市场冲突；缺少可选市场上下文 | 冲突按明确范围进入REVIEW，不修改Quant；可选字段缺省不自动ERROR |
| 多方案与聚合 | 一个方案异常、另一方案有效；共同证据错误 | 方案结果可追溯，聚合按约定；不把批次通过当作每方案通过 |
| 跨模块验收 | 正常确认、拦截、错误恢复各跑一条完整流程 | UI与服务端一致，风险原因、版本、确认和审计可关联 |

每条数值规则均补正常、异常、边界样例；每次修复新增对应回归用例。50项既有原型检查与33个固定页面案例只作为历史原型验证记录，不能计作上述正式风险测试通过。

## 8 一次接口讨论要确认的事项

1. 第一板块：Risk输入从完整响应、证据解析接口还是事件取得；风险契约版本、路由、回写位置及ERROR与HTTP错误的关系。
2. 第二板块：可信用户、画像与约束版本、确认有效性、去重、审计保存和恢复；Memory同意与风险审计的依据分开处理，不让默认记忆写入替代审计。
3. 第三板块：目标方案指标、ETF行业汇总、样本、交易事实和规则版本；金额单位、回撤符号、舍入精度、不可用值；当前A/B/C与四周计划的语义差异。
4. 第五板块：四状态展示、可接受与需修复REVIEW、完整计划确认、失效提示；前端确认数据交给服务端验证。
5. 队长和第四板块：固定规则阈值、逐步改善例外、ERROR聚合策略、首版审核范围及Eval验收门槛。
