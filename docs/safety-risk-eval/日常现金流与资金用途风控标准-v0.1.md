# 日常现金流与资金用途风控标准 v0.1

日期：2026-10-17。状态：第四板块设计提案，供用户和团队确认。本轮只制定标准，不宣称已实现日常风险引擎或正式 Owner 联调。

## 1. 要回答的问题

用户输入工资、学费、生活费、订阅或投资计划后，系统说明：这次安排会影响哪笔已确认用途，在哪天可能缺多少钱，信息是否足够，以及可以怎样修改后重新检查。

检查对象是资金安排和拟议动作。输出具体原因、金额、日期和恢复条件，首版不将用户归为贫穷、富裕等等级，也不合成缺乏依据的百分制风险分数。投资亏损、适当性和组合风险继续由原 R01—R10 及对应模块检查。

## 2. 先整理并确认输入

| 信息 | 最少需要知道什么 | 使用约束 |
| --- | --- | --- |
| 当前余额 | 币种、账户/资金池范围、余额金额、截至时间、是否已反映相关扣款和冻结 | 当前余额不等于总资产；未核实可用性的不直接加入 |
| 工资等收入 | 金额、净到账口径、预计到账日、已到账/预计状态、是否已包含在余额 | 已到账且计入余额的工资不再相加；未来工资只进注明假设的预测 |
| 学费等专用资金 | 金额、用途、使用期限、是否属于当前余额、是否明确禁止挪用 | 先让用户确认用途；专用资金包含在余额中时，不另外再加一笔收入 |
| 待支付项目 | 唯一编号、尚欠金额、到期日、已付/未付、与用途预留的关联 | 已付并反映在余额的支出不再扣；贷款按待还款额计，不重复扣总负债 |
| 生活预算 | 预算区间、区间内已花金额、剩余预算、用户确认状态 | 剩余生活费单独列；不把整月预算和已发生开销重复扣除 |
| 备用资金 | 必须保留的最低额，或仅期望达到的储备目标 | 硬性最低额与柔性目标分开；均记录是否与其他预留重叠 |
| 已有任务占用 | 所属任务、金额、状态、有效期、是否已从余额扣除 | 使用 Backend/执行端记录，模型不能自行声明占用已释放 |
| 本次计划 | 操作类型、本金及必要费用、币种、执行日、涉及资产、可用/可赎回时间 | 未知必要费用须补充后才能给完整执行额度；没有证据的收益与变现时间不能当作保证 |

每项保留原始回答、来源、时间、确认状态和版本。模型归纳或推测单独标注；未知不填成 0，未确认的建议不成为用户硬性限制。用户只说“工资 8,000”时，应追问是否已到账、当前余额是多少，而不是据此判断可投额度。

日常分析需要允许呈现用户已经存在的缺口。必须支出大于余额是风险事实，不等于输入格式错误；不能减少学费金额来让数据通过校验。

## 3. 一套判断，四种结果

| 结果 | 含义 | 下一步 |
| --- | --- | --- |
| `ALLOW` 通过 | 当前评估范围内信息充分、无已触发阻断或复核项 | 继续必要的组合风险检查和用户确认；不代表已获交易授权 |
| `REVIEW` 需处理 | 缺资料、需要重新确认，或存在可接受的预算提醒 | 标清是补资料、改计划还是明确接受提醒；补资料类不能勾选跳过 |
| `BLOCK` 阻止 | 已确认用途/硬约束被违反，或权限与执行条件不满足 | 当前动作不能执行，说明缺口或冲突；用户修改后重新检查 |
| `ERROR` 无法完成检查 | 数据契约、计算、占用状态或必要服务无法可靠核验 | 暂停相关动作；保留已知冲突，恢复后重检 |

有 `ERROR` 时整体不能标为检查完成；没有 `ERROR` 时按 `BLOCK > REVIEW > ALLOW` 聚合。保留全部原因，不让一个可接受提醒覆盖另一项硬阻止。检查结论、用户确认和执行状态分别记录。

## 4. 八条日常规则

编号 D01—D08 是本提案编号，与既有 R01—R10 分开；正式共享名称和接口由架构负责人对齐。

| 编号 | 触发条件与判断依据 | 结果和用户提示示例 | 恢复条件 |
| --- | --- | --- | --- |
| D01 信息与计算可用性 | 本次判断依赖的余额、金额、日期、来源或确认缺失；或版本、单位、计算/服务校验失败 | 缺信息 `REVIEW`：还不知道学费何时支付。校验失败 `ERROR`：本次无法核验余额，执行暂停 | 补充并确认所需信息；修复数据/服务后重检。与本次无关的可选指标缺失不阻断全部功能 |
| D02 专款和必要支出保护 | 新增、未被已有预留覆盖的动作超过扣除确认用途和硬性备用资金后的额度；按原用途付款须核对对应账单和剩余预留 | `BLOCK`：这次投资会占用已确认的学费，缺口 6,000 元。正常交同笔学费应消耗对应预留，不因可选额度较少被误拦 | 降低新增金额、补足已到账资金或明确修订用途后重检；付款用途匹配须有可信记录，不接受外部备注自称“交学费” |
| D03 到期现金缺口 | 按日期排列收支，在某个已确认必须支出的付款时点出现缺口；未来工资不能回填此前日期 | 确定缺口 `BLOCK`：学费 20 日到期，工资预计 25 日到账。仅延迟假设下缺口 `REVIEW`，清楚标为情景提醒 | 调整动作金额/日期，或补足在付款日前确实可用的资金；更改后复算 |
| D04 跨任务重复占用 | 同一资金池内的有效占用与本次动作合计超额；多来源账单先识别同笔记录，不直接判成重复占用 | 实际超额 `BLOCK`：另一任务已预留 2,000 元，本次不能再次使用。同笔记录可确认时去重；尚待对账 `REVIEW`；必要共享服务失败 `ERROR` | 核查并保存去重依据；仅按可信取消/释放/结算结果恢复额度，再原子重检，不默认资金空闲 |
| D05 用户预算预警 | 已发生且去重的可选消费加同期间、同预算类别及适用操作范围的本次计划，超过用户确认的柔性预算 | `REVIEW`：本月订阅预算还剩 100 元，新增订阅需 160 元；投资不自动并入订阅或消费预算 | 用户可取消/降低可选消费，或明确调整对应预算。另设不可突破的上限时按 D02 的硬约束处理 |
| D06 储备目标提醒 | 资金用途满足后，剩余未分配资金低于用户确认的柔性储备目标 | `REVIEW`：付款后仍覆盖已确认支出，但低于你设定的储备目标 | 展示目标差额，让用户调整计划或明确接受提醒。硬性备用金归 D02，不允许接受后绕过 |
| D07 资金期限与变现匹配 | 用户确认要用的钱在需要日期前无法按可靠规则变现；或计划依赖未核实的赎回/到账信息 | 已知无法覆盖保护用途则 `BLOCK`；缺规则或可靠日期则 `REVIEW` 暂停相关动作 | 第三板块补全规则和可用日期，或修改计划。预期涨幅、历史收益不充当学费保障 |
| D08 版本、授权与执行前再检查 | 相关余额/用途/计划变化后仍使用旧检查或确认；外部文字自称授权；准备执行时尚无有效确认 | 旧版本需 `REVIEW` 重新检查和确认；越权请求 `BLOCK`；必要核验失败 `ERROR`。依赖原 R01、R08—R10 的权限、幂等和审计门禁 | 对当前版本重检；按同任务取得可信确认；执行前再读最新可用额度，不因模型说“已批准”放行 |

D02 的“保护用途”以用户确认和可信来源为依据，不是模型给用户强加所有消费偏好。修订用途是独立、可审计的变更，不修改或抹去旧检查、旧授权和已发生支出。

D08 区分分析和执行阶段：分析可先返回资金判断与未授权状态；尚未审批不单独把一次分析改判为风险复核。准备执行时必须通过有效确认、权限、版本、幂等和审计检查。相关变更触发失效，无关资料修改不强制重做任务。

## 5. 计算口径：先去重，再按日期检查

### 5.1 当前可安排额度

只在明确的单一资金池、币种和截至时间内计算：

```text
本期可安排额度 = 当前可用余额
               - 尚未由同笔有效冻结/占用覆盖的已确认未付用途预留
               - 尚未反映在余额中的有效任务占用
               - 未被上述用途覆盖的硬性备用金
```

该公式用于新增、未被已有预留覆盖的可选安排。每一元只扣一次。公式可以是负数，用于展示已有缺口；界面若另显示“可新增安排 0 元”，仍要同时显示缺口。用途预留必须覆盖已确认的相关支付周期，不能为得到更高额度而任意缩短窗口。

按原用途支付时，先以可信用途/账单关联确定可消耗的对应预留，检查实际可支付现金和其他仍受保护的用途；付款与对应预留的消耗、任务占用结算须原子更新。本次总额超出该预留的部分，才使用新增可安排额度。原预留不足、账户现金不足或其他硬保护被违反仍阻止，不因用途名称相似直接放行。

本次需预留的总额为本金、必要费用及与前两者不重叠的额外冻结，分别记录依据。同一笔本金 1,000 元转为冻结 1,000 元是状态变化，不增加为 2,000 元负担。费用未知时可以展示本金口径的条件分析，不能据此签发完整执行资格。

当前额度用于判断现在执行或现在占用资金的动作。未来某日的计划可以展示基于预计收入的条件分析，保留未取得当前执行资格的状态；真正执行前再按实际余额和日期检查。现在就要冻结资金的未来计划，仍按当前资金和占用核验。

工资、学费和生活费分别用唯一事件编号关联来源、预留、冻结和实付。月薪已计入当前余额时不再加；同一学费“预留 6,000”与“20 日应付 6,000”是同一负担，不扣 12,000；预留转为同笔有效占用时，只保留尚未被该占用覆盖的预留差额。覆盖关系必须可信，投资占用不能覆盖另一笔学费保护。同一账户的内部转账不创造收入。

### 5.2 日期检查

```text
某日预测账面现金 = 截至评估时点、未扣尚未结算冻结的账面现金
                 + 该时点之后、截至该日的情景收入
                 - 该时点之后、截至该日的待支付出
                 - 尚未包含在待支付出中的本次计划支出

某日预测可安排余量 = 该日预测账面现金
                   - 该日仍有效的冻结/任务占用
                   - 尚未由同笔有效冻结/占用覆盖的已确认未付用途预留
                   - 未被上述用途覆盖的硬性备用金
```

日期账本明确区分账面现金、冻结/占用、可安排余量：用途支付时只扣一次账面现金，同时减少对应未付预留；占用转实际扣款时同时解除对应占用。未付预留用于说明余量，不再作为额外的实际支付事件。只给出净扣冻结的可用余额时，须先取得可信对账口径；不能从净余额再次扣冻结对应的付款，无法对账则暂停相关完整判断。

未来工资等情景收入须标明预计日期和不确定性；它不进入“当前可用余额”。工资到账假设或压力情景不能解除 D02 的当前资金不足、D07 的期限冲突或其他已知硬阻止。同日先后不明时，按先付后收的保守次序或请求补充，不自行认定工资先到账。负账面现金、保护用途不足和跌破硬性备用金分别说明。

检查窗口至少覆盖本次动作及已确认受影响支出的日期；周期或远期必要信息不足，结论限定范围并请求补充，不给出“以后都没问题”。工资延迟等压力情景仅作明确标识的假设，不伪装成预测概率。

## 6. 具体例子：要保护学费，而不是只比较工资和投资额

以下全部是虚构数据：

| 项目 | 金额/日期 | 本次口径 |
| --- | --- | --- |
| 当前余额 | 12,000 元，截至今天 | 已含本月到账工资，不再增加一次工资 |
| 学费 | 6,000 元，20 日需付 | 未支付、用户确认不得挪用 |
| 房租 | 1,500 元，18 日需付 | 未支付、确认保护 |
| 生活费 | 2,500 元，覆盖本次确认周期 | 尚未花费、确认预留 |
| 其他占用与额外备用金 | 0 元 | 示例明确为零；真实未知不能填零 |
| 拟投资 | 今天 8,000 元 | 尚未执行；本例明确采用演示费用 0 元 |

当前可安排额度为 `12,000 - 6,000 - 1,500 - 2,500 = 2,000 元`。本次拟投资比可安排额度多 6,000 元，D02 返回 `BLOCK`。

建议文案：按你确认的学费、房租和生活费安排，目前有 2,000 元未分配。现在投入 8,000 元会占用其中 6,000 元必要资金。可以降低或延后本次计划；修改后重新检查。2,000 元只是本次资金用途检查的额度，不代表建议投资 2,000 元或已经通过其他风险与审批。

若将投资改为 2,000 元，在已确认周期、无其他变化且日期检查也满足时，资金用途这一项可通过；D05、D06 等提醒、原投资风险、用户确认和执行门禁仍各自判断。没有新增备用金并不等于系统保证突发支出也能承受。

## 7. 输出必须可解释和可复核

每条结果保留规则编号、固定原因代码、中文说明、实际值/阈值/币种/期间、影响的用途和日期、数据引用、确认与版本、允许/暂停动作、恢复方法、是否允许接受。

原因代码提案：`DAILY_DATA_REQUIRED`、`DAILY_CHECK_UNAVAILABLE`、`PROTECTED_PURPOSE_CONFLICT`、`PAYMENT_DATE_GAP`、`SHARED_FUNDS_CONFLICT`、`PERSONAL_BUDGET_EXCEEDED`、`RESERVE_TARGET_SHORTFALL`、`LIQUIDITY_DATE_MISMATCH`、`DAILY_APPROVAL_STALE`。正式名称由架构统一；原权限/审计原因继续沿用原注册表。

建议采用固定解释模板：

1. **发现：** 哪笔安排、哪天、缺多少或还缺什么信息。
2. **依据：** 用户确认的哪些输入，以及对应时间、版本和计算。
3. **影响：** 影响学费、房租、生活费还是柔性目标。
4. **可选修改：** 降低/延后本次可选动作、核对数据或明确调整预算；不自动取消必要支出、不替用户借款/卖出资产。
5. **恢复：** 哪些信息或版本更新后可以重检。

Agent 理解语言、提问和解释；金额、日期、去重与判断由程序计算。模型置信度不替代资金证据，模型也不能修改规则或批准自己的提议。

## 8. 现有代码怎样复用，哪些仍需补齐

基线：团队 `main` 提交 `6985ca2`；本轮核查 `chenchen/integrations/funding-plan.js` 和相关合同。

- 已有 `cash_minor`、`protected_purposes`、计划版本与占用；金额使用整数分，拟议动作绑定原计划和版本。资金检查会在模拟前重新做，已有演示占用保护可复用。
- 现有用途主要是编号、名称、金额；工资到账日、学费到期日、已付状态、重复事件关联、软预算/硬约束区分需要跨 Owner 扩展，不能直接塞进禁止额外属性的旧 Schema。
- 现有计划创建不接受“预留大于余额”。日常分析必须另有可表示真实缺口的输入路径，不能先让用户数据满足演示计划校验再判断风险。
- 当前资金计划是独立虚构沙箱，不等于跨真实账户、跨计划的统一资金池；D04 依赖 Backend/Execution 提供可信共享占用、并发校验与释放结果。
- `scenario=FUNDING_CONFLICT/SUBSCRIPTION_REVIEW` 可辅助路由，不作为授权；标准输出须与统一 `risk-handoff.v1`、Owner Bridge 和审计关联。
- Core 回调目前只接受 `APPROVE/REJECT/REQUEST_MORE_INFO`：满足证据及版本要求的 `ALLOW`、`BLOCK` 分别适配前两者；补资料类 `REVIEW` 可适配 `REQUEST_MORE_INFO`，当前协议要求新建复核任务。可接受提醒仍需确认处理流程，不能自动当成批准；`ERROR` 保留暂停与错误审计，不提交批准。共享映射由 Owner 对齐，不能直接把四种内部结果原值发给 Core。
- 当前 `confirmed=true` 和 `reviewed_input` 均不能替代正式用户身份或可信 Memory；演示计划明确为 `DEMO_USER_CONFIRMED_NOT_TRUSTED_MEMORY`，上游输入权威标记为 `UNVERIFIED_CALLER_INPUT`。
- 由第四板块给出规则与所需证据，Core/Memory 对齐来源和确认，Backend/Execution 对齐余额及占用，第三板块给变现规则，第五板块展示警告和恢复动作。

## 9. 第一轮验收清单

以下是待实现程序的可判断用例，本轮仅做文档口径检查，不宣称程序测试已通过。

| 用例 | 预期 |
| --- | --- |
| 只提供月薪，未提供当前余额及到账状态 | D01 `REVIEW`，不计算可投金额 |
| 上述虚构案例投 8,000 元 | D02 `BLOCK`，缺口 6,000 元 |
| 上述案例改投 2,000 元且日期条件满足 | D02 不超限；其他规则和确认仍独立检查 |
| 学费 20 日到期，工资 25 日才预计到账，20 日余额不足 | D03 `BLOCK`，不因月底总收支为正放行 |
| 工资已在当前余额内，输入又提到工资 | 保留来源关联，不重复相加 |
| 学费同时有预留与账单；或房租已付且余额已扣 | 各笔只影响一次，不双扣 |
| 上述案例按可信关联支付原学费 6,000 元 | 不因新增可安排额度只有 2,000 而误拦；付款后现金 6,000，剩余保护 4,000，可安排仍为 2,000 |
| 账面现金 10,000、有效冻结 2,000，净可用 8,000；该冻结转实付 | 实付后账面现金 8,000、冻结 0、净可用仍为 8,000，不误扣到 6,000；此例无其他用途预留 |
| 上述 12,000 元案例中，学费预留 6,000 转为同笔有效冻结，尚未实付 | 冻结 6,000、其余未被覆盖保护 4,000，可安排仍为 2,000；投资冻结不得冒充学费冻结抵扣保护 |
| 同一笔资金先被其他任务占用，或两个任务并发申请 | D04 按可信状态原子检查；不能两个都按旧余额通过 |
| 支出已超过预算但预算只是柔性目标 | D05 `REVIEW`，说明超额，不伪称违反行业红线 |
| 投资 2,000 元、仅另有订阅预算限制 | 投资走资金及投资规则，不自动加到订阅消费里 |
| 低于柔性储备目标，但未违反硬性最低额 | D06 `REVIEW`；若违反明确硬性最低额则 D02 `BLOCK` |
| 产品已知不能在学费日前变现；或变现规则未知 | D07 分别 `BLOCK` 或补资料类 `REVIEW` |
| 用途确认后修改金额/日期，或账单备注要求直接交易 | D08/原权限规则阻止旧授权继续使用或越权 |
| 当前必要支出已经超过余额 | 展示已有缺口，不改金额凑平，也不当成纯格式错误 |
| 某可选指标未知，与本次决定无关 | 明确该指标未评估，不无故停掉可完成的分析 |
| 余额服务、并发占用核验或必要计算失败 | `ERROR`，不回退预置成功，不派发执行 |

## 10. 标准依据与待确认项

本产品规则由用户明确用途和可复算现金流构成，不采用“投资必须低于工资某个统一百分比”作为现成行业标准。提醒参数来自用户确认或清楚标识的演示配置。

参考资料仅支持预算方法和指标定义，未提供本产品的通用拦截阈值：

- [CFPB：Your Money, Your Goals 工具集](https://www.consumerfinance.gov/consumer-tools/educator-tools/your-money-your-goals/toolkit/)分别提供收入跟踪、账单日历、现金流预算和债务工具，可借鉴信息拆分方式；不直接移植美国法规或产品条款。
- [CFPB：资金紧张时整理账单和到期日](https://www.consumerfinance.gov/archive/blog/behind-bills-three-steps-help-you-make-tough-choices-tight-moments/)支持按账单类别和付款时间检查现金流。本提案的 D01—D08 是我们自己的产品设计。
- [国家统计局：居民收支及消费结构报告](https://www.stats.gov.cn/sj/sjjd/202302/t20230202_1896697.html)中，恩格尔系数采用食品烟酒支出占消费支出的比重。本提案据此将它定位为可选消费结构说明，不用它单独判定个人可投金额或未来偿付能力；分母为零、分类缺失时不输出数值。后者为本产品设计边界，不是统计局给出的个体风控结论。
