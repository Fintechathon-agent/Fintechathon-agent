## 1. 如何阅读覆盖状态

| 标记 | 含义 |
| --- | --- |
| 源码可见 | 指定分支或附件中存在判断代码；没有据此推断它已部署。 |
| 部分覆盖 | 有相关检查，但字段、适用范围、信任边界或判定语义与本规则不一致。 |
| 未见对应实现 | 本次核查的指定来源未找到对应代码；不推断其他未共享系统也不存在。 |
| 历史联调证据 | 已有带日期和范围的报告；不是本轮同版本 staging 验收。 |
| 待联合验证 | 缺少同一部署版本、可信用户、账户和任务的端到端证据。 |
| 不适用 | 当前功能明确不执行该类动作；不能据此宣称其执行规则已通过。 |

规则定义文件的 `MODULE4_PROPOSAL_PENDING_TEAM_REVIEW`、日常登记表的 `runtime_implemented:false` 是原规格元数据；本表分别引用实际引擎代码判断源码覆盖，不把规格 JSON 当作运行证据，也不擅自把其审批状态改成“团队已确认”。

### 共同处理语义

1. 正式 Risk 结果保持 `ALLOW / REVIEW / BLOCK / ERROR`；审批、执行、HTTP 状态分别记录。尚未产生 Risk 结果时可记录 `risk_decision:null`，这不是第五种 Risk 结果。
2. 适用检查无法完成使用 `ERROR` 并关闭相关执行；当前引擎汇总顺序为 `ERROR > BLOCK > REVIEW > ALLOW`，保留全部触发原因。不能把计算失败降为可勾选接受的风险。
3. `ALLOW` 只表示本次检查通过，不授予执行权。等待审批、拒绝、撤回、过期、相关版本变化及结果未知时均不得新执行。
4. `REVIEW` 分为：**可接受风险**（只接受当前检查明确列为可接受的风险项）与**必须修复事项**（缺数据、对账、版本、权限等）。可接受风险应逐项接受、重检并绑定新确认；不能覆盖硬阻止。
5. 投资组合集中度规则不直接套用于工资、房租或消费分类。日常预算／应急参考也不自动成为银行适当性标准。
6. 以下比例是既有队内虚构演示配置，不是核实后的行业或监管阈值；用户资金用途、最低现金等采用明确确认的配置。比较符号和口径必须与对应规则版本一起展示。

## 5. 用例与覆盖的验收方法

1. JC01—JC20 覆盖集成场景；JC16 的分项向量覆盖 R04—R07 边界、合格／不合格改善、D05／D06 软提醒及 D07 流动性。它们仍是待执行设计，不是已经构成可成交的真实组合；完整组合的一致性需金融工具独立验证。
2. R04／R05 至少检查等于上限、刚超上限、两口径结论不同、非现金分母为零、未知行业、改善与加重另一指标。任何未完成分项保留 `NOT_RUN`，不能用一条 ALLOW 样例宣称覆盖全部规则。
3. 每个场景收集：来源／规则／部署版本、适用规则及不适用原因、观察值／分母／阈值、全部固定原因、恢复动作、审批与执行状态、任务与审计 ID、共享账本前后版本和唯一资金效果。
4. 对需要工具或数据但未取得证据的规则，记录 `NOT_EVALUATED` 或明确暂停；不能把“无数据”“接口未接”“调用失败”写成 PASS。
5. 先验证源码／契约，再跑本机替身，最后在同版本 staging 使用虚构资金验证。报告必须分列模型替身、真实模型调用与纯程序测算，纯规则判断不得冒称模型成功。

### 评审完成条件

- [ ] R01—R10、D01—D08 在当前接入入口逐项标明适用范围，主聊天只读规则不被误标为整套统一规则。
- [ ] 每项规则的字段、口径、原因代码与拦截责任能对应接口差异表和联合用例。
- [ ] P0-G01—P0-G06 的 Owner、目标版本与阻断依赖获团队确认。

- [ ] 同一 staging 版本完成必需正负例；当前执行关闭不被修改为“演示成功”。
