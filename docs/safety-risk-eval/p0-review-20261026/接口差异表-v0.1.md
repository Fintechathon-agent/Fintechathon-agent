## 1. 先统一三个边界

1. **模型输出只是提议。** 用户文字中的余额、身份、权限和“已经批准”都不能直接成为可信执行事实。
2. **服务签名不等于用户批准。** HMAC 证明某服务发出了消息，最终用户身份及其对本次完整计划的授权仍须单独验证。
3. **三种账本必须分开。** Finance 的用户现金、Core 的 `funding-demo`、主聊天模型 API 费用预算不是同一资金池，不能互相替代。

本轮跨场景缺口采用提案编号：`P0-G01` 可信用户／账户身份、`P0-G02` 唯一资金账本及原子资金、`P0-G03` 任务—完整提议—审批绑定、`P0-G04` 故障与未知结果失败关闭、`P0-G05` 就绪状态真实报告、`P0-G06` 前端与审计关联。它们是接线验收分组，不替换既有 R01—R10／日常规则编号。

### 接口名字相同，不代表能互换

`Finance /api/review`、`Core /api/review`、`Risk /api/review` 的服务器、输入、鉴权及返回语义不同。调用配置必须同时登记**服务、基础地址、方法／路径、契约版本、源 SHA、部署 ID**；只贴一个 `/api/review` 不足以接线。

## 3. 金额、日期和资金池对应

| 现有事实／单位 | Risk 采用方式 | 错误或缺失时 | 用例 |
| --- | --- | --- | --- |
| Finance 明确为 CNY 元的付款、费用、现金字段 | 十进制原文精确转整数分：`"8000.00" → 800000`；已有安全整数分只校验，不再乘 100 | 单位／币种不明、精度超出、非有限数或溢出则 ERROR，暂停依赖计算；不猜单位、舍入或补 0 | JC13 |
| `null` 余额或待付金额 | 保留未知；只能给出基于已知事实的局部说明 | 业务事实待补可 REVIEW；若结构／计算自身无效则 ERROR。均不可宣称资金足够 | JC13、JC16 |
| 账面现金、已有占用、用户确认的保护用途、额外最低现金 | 各自独立字段，由账本／已确认约束计算可用额；明确是否重叠 | 不把投资市值当现金，不重复扣同一保护用途，也不重复加已入余额的工资 | JC06、JC12、JC13 |

| 比例、历史回撤、份额、月份 | 保持各自单位，不走元／分转换 | 不把百分数乘 100 当金额；历史回撤不是未来损失上限 | JC13、JC16 |
| H01 模型费字段 | 只进模型费用账本。交接包外部配置有人民币分、内部结算有人民币微元，均须按其费用契约转换 | 不拿模型余额、tokens 或预算剩余额抵扣用户的现金保护额 | JC18 |

## 4. Risk 四态到 Core 回调的现状

| Risk 原始结论 | Core 风险回调 | 用户审批／执行状态 | 暂停与恢复 | 用例 |
| --- | --- | --- | --- | --- |
| `ALLOW` | `APPROVE` | 只表示风险意见；需要批准的资金动作仍等待完整计划确认 | 完成可信用户批准及最新执行前检查后，才可能进入受控模拟 | JC01、JC02、JC16 |
| `REVIEW` | `REQUEST_MORE_INFO` | 不等于“已批准”；可接受类与必须修复类分开 | 按原因补资料、修方案或明确接受可接受风险；已发送的首次回调不覆盖，修订走新任务／新 Handoff | JC04、JC13、JC16 |
| `BLOCK` | `REJECT` | 阻止，不接受“我愿承担”覆盖硬条件 | 修改动作或约束后重新检查；不直接把原拒绝改通过 | JC03、JC06、JC11、JC12、JC16 |
| `ERROR` | **不发送业务决定回调**，保留原 ERROR | 检查未完成；走故障状态，执行 false | 修复必要服务、数据和审计后重检；不得映射成 ALLOW 或用 REVIEW 冒充检查完成 | JC09、JC15、JC16 |

现有冻结回调只有以下十字段：

```text
handoff_id, task_id, request_id, run_id, audit_id,
reviewer, reason, callback_version, proposal_sha256, decision
```

`callback_version=risk-callback.v1`；`decision` 只有 `APPROVE/REJECT/REQUEST_MORE_INFO`。`subject_id/account_id/account_version/nonce` 不能擅自塞入此对象。Risk 的详细原因、检查编号、规则与数据版本应先记录在受信任审计侧车，扩展方式由 Core Owner 和架构负责人统一。

传输鉴权失败发生在 Risk Engine 前时，记录“入口拒绝／Risk 未运行”，不要伪造一份 Engine `BLOCK` 报告。网络、审批、Risk 和执行应有独立状态：健康 UP 不清除业务错误；批准待核查不显示模拟完成。

尚未运行检查时可以用 `risk_decision:null` 加独立的未运行状态表示，`null` 不是第五种 Risk 结论；已运行结果仍只允许 `ALLOW/REVIEW/BLOCK/ERROR`。

## 5. P0 可信绑定字段提案

以下是**新增统一上下文需求，不是现行 API 已接受的 Schema**。共享合同名称、签名格式、期限和存储仍待团队确认；在旧接口不兼容时，应在边界暂停，不能自行降级丢字段。

| 字段／集合 | 可信提供方 | 绑定与验证要求 | 当前差异／用例 |
| --- | --- | --- | --- |
| `subject_id`、会话验证方式 | 主聊天／身份服务 | 服务端验证会话后生成；传播到审批、Risk、账本；浏览器自填同名字段拒绝 | H01 只有访客 owner 机制，统一主体合同未定；JC03、JC14 |
| `account_id`、账户归属 | Finance 账户服务 | 服务端证明主体拥有该账户；换账户必须重新生成上下文 | 本机访客目录不能直接充当跨服务托管账户；JC03、JC06 |
| `task_id`；`request_id/run_id/handoff_id/audit_id` | Core 与对应记录服务 | 保留主任务和来源任务映射；同一次审批、检查、执行都能回到同一 Core 主任务 | 新主聊天的局部 ID 不能覆盖 Core ID；JC01、JC07、JC08 |
| `proposal_sha256` | Core 持久提议 | 摘要覆盖完整动作、金额、币种、用途、期限、费用、数据模式等经冻结内容；批准前后比对原提议 | `input_hash/tool_hash/review_hash/plan_hash` 分别保留，不能替代该摘要；JC04、JC08、JC17 |
| `account_version`、预留状态 | Finance 唯一资金账本 | 快照、检查、审批、执行关联同一账户版；执行前原子校验并预留，版本冲突重检 | 偏好版和 Core 演示 revision 均不可冒充；JC05、JC06、JC10 |
| 已确认用途及 `constraints_version` | 用户确认记录／Finance | 学费、房租等用途由用户确认后生效，保留确认来源和版本；多个任务共享同一保护约束 | 模型归纳不能自行放宽已确认约束；JC04、JC12 |
| `risk_check_id`、`decision`、`rule_version`、证据版本 | Risk Engine | 检查内容和提议、账户版、约束版匹配；保留全部原因及未知项 | H01 的金额只读规则覆盖范围不等于 R01—R10；JC13、JC16 |
| `decision`、`verified_at`、`nonce`、验证方式 | 用户审批服务 | 明确这是用户审批 decision，与 Risk decision 分属不同对象；绑定主体、账户、任务、提议、账户版；验证时效和单次使用／幂等 | 具体有效期为可配置提案，不编造行业标准；JC02、JC03、JC07、JC14 |
| `execution_id`、`idempotency_key`、账本回执与审计 ID | 唯一执行网关＋Finance | 同一动作只产生一次资金效果；原请求重试读原回执；内容变更同 key 明确冲突 | 源码两套局部模拟入口还需 Owner 确定责任边界；JC06—JC10、JC15 |

### Risk 原因摘要的最小提案

账户版本还须区分外部变更与本任务自身的原子预留推进：批准绑定决策快照，reserve比较该版本并返回可信预留凭证及新版本，commit按确认后的账本合同验证同一预留。不能把任意版本变化忽略掉，也不能因本任务合法reserve推进版本而形成永远不能commit的流程。此状态迁移合同待账本及审批Owner确认，见JC01、JC05、JC06、JC10。

每条原因至少包含 `rule_id/code/message/evidence_refs/recovery/acceptance_allowed`；涉及数值时附 `actual_value/unit/denominator/threshold`，不适用则明确空值及原因。阈值须有规则来源和版本，不从模型文字临时创造。

对用户显示中文说明；固定代码供程序判断。原始备注、新闻和模型文字只作为不可信证据，不能写入权限、签名者、审批或规则配置。
