1. Product Overview

产品名称

持仓哨兵 Agent（PortfolioSentinel）

一句话定位

为持有基金、但没时间盯盘的 20–35 岁城市个人用户，Agent 在后台持续监护持仓，用同侪行为信号与持仓诊断主动提醒「该看一看了」，先经模拟盘回测后果，再在绿 / 黄 / 红三级权限与全程审计约束下，把调仓这件事真正执行完。

产品愿景

用户要的不是又一个显示收益曲线的页面，而是有人在他没空的时候替他盯着，并且在需要动手时把「判断依据、操作后果、执行动作」一次性给全。

持仓哨兵把理财从查询工具推进为受托监护：Agent 自动监测持仓与同侪行为信号，主动发起对话，给出可解释的调仓建议，先模拟再执行，每一次高风险操作都经过强验证并留下可回放的决策链路。

01
主动监护
用户没提问时 Agent 也在工作。监护循环持续计算持仓风险与同侪行为变化，发现异常主动触达——这是被动式 App 做不到的。
02
模拟先行
任何建议先落模拟盘：历史回测回答「如果当时做了会怎样」，三情景区间回答「做了之后可能怎样」，看清代价再决定。
03
权限在工具层强制
LLM 不持有交易工具直连权，红色操作必须过独立强验证，审计链路可回放。权限判定与 LLM 解耦，注入无法绕过。

MVP 仅在演示环境中运行，不连接真实银行账户，不执行真实资金交易。

2. Problem Statement

用户现在面临什么问题

持有基金的上班族在波动行情中面对三个连续的空洞：该不该动、动哪只、动多少。

手机银行和基金 App 能准确回答「你今天亏了 328 元」，但不会回答「所以呢」。用户看到的是一串数字，需要自己完成从数字到动作的全部翻译工作。

问题不在于信息不足，而在于信息与行动之间缺一个负责人。

用户现在如何解决

  • 每天打开 App 看收益数字——看到亏损，但分不清是市场整体回调还是自己的持仓结构有问题；
  • 去社区论坛搜别人持仓——搜到的与自己差异很大，无法判断是否可比；
  • 看资讯、听博主观点——观点互相矛盾，且不知道对方风险偏好是否与自己一致；
  • 凭感觉决定，或干脆不看——忙起来连续几周不打开，回神时已错过调整窗口。

为什么现有方案不够好

理财 App 提供数据展示，社区提供他人观点，资讯提供市场情绪。三者都不对用户的最终结果负责，也没有任何一层把「我的持仓 + 风险承受能力 + 当前市场状态」合成一个可执行动作。

更关键的是时间维度：用户不是每天都想看理财，而是在需要看的时候没人提醒。

为什么必须是 Agent

能力 为什么普通方案做不到
组合判断 没有固定阈值规则能回答「该不该调」，它依赖风险偏好、持仓集中度、市场状态与群体行为的组合推理
意图理解 用户表达天然模糊（「我那个基金是不是该跑了」），按钮无法承载
主动触达 Agent 能在用户没提问时工作，监护循环持续运行；被动式 App 做不到
确定性执行 LLM 负责理解、规划与解释，数字与执行由确定性工具承担，数字永不来自模型生成

用户没时间做的不是「看数字」，而是「盯着、判断、然后去操作」这一整条链路。

4. Core User Scenario

小周，29 岁，产品经理，持有两只基金共 3.6 万元。过去两周他连续加班，只在午休时扫过一眼 App，看到浮亏 4.3%，没做任何处理就继续开会。

周二晚，Agent 的监护循环检测到异常：与小周持仓重合度较高的用户群体中，有相当比例在近 5 个交易日降低了其中一只基金的仓位；同时该基金波动率超出了小周设定的容忍区间。

周三早 8:20，他在地铁上收到简报卡片：「你持有的 A 基金，与你持仓相似的用户中 38% 近 5 日降低了仓位；你的当前仓位高于设定的波动容忍区间。需要我帮你看一下吗？」

他回了句：「是不是该跑了？帮我看看。」

Agent 没有直接回答「该不该跑」，而是先补齐信息：确认可接受的单次调整比例（30% 以内）与观察期限（3 个月）。随后调用诊断工具，指出亏损的两个来源——指数整体回调贡献了大部分，且他的两只基金在同一行业上有 41% 重合，风险比他以为的更集中。

接着 Agent 提出建议：「赎回转出 A 基金的 30%（约 5,400 元），转入货币基金作为缓冲，保留其余仓位」，并立刻放进模拟盘试跑。屏幕上出现两条曲线：「若 3 个交易日前跟进该信号」与「一直持有至今」。回测显示若当时调整，这段回撤会少 6.7%（约减少浮亏 740 元）。

小周点了「按这个方案执行」。系统识别出这是基金赎回，属于红色权限，弹出强验证：短信验证码 + 人脸识别（演示为 Mock）。通过后 Mock 交易网关返回执行成功，页面展开完整审计时间线：从信号触发、意图识别、任务规划、工具调用、风险检查、用户确认到执行回执，每一步都可点开查看。

当晚，Agent 推送复盘提醒并写入记忆：接受 30% 以内的分批调整、偏好「先转货币基金缓冲」的低冲击路径、下次同类信号出现时优先复核。

全程没有任何真实资金动作，但产品闭环完整走完一遍。

5. User Journey

阶段 系统行为与用户可见结果
Trigger 监护循环后台运行（每日定时 + 事件驱动）：拉取持仓与净值、计算波动指标、比对同侪行为信号。命中阈值时生成提醒。此阶段为绿色权限，自动执行。
User Intent 用户口语化回应：「是不是该跑了」。允许模糊、省略、无主语。
Agent 理解 识别意图类型（诊断 / 建议 / 直接执行 / 仅咨询），抽取实体（基金、金额、比例、期限）。缺失关键信息时只追问必要项，不猜测风险偏好。
Agent 规划 拆解为有序 DAG：校验输入 → 持仓诊断 → 同侪信号复核 → 候选动作 → 模拟试算 → 回测与情景推演 → 适当性检查 → 建议输出 → 等待确认。任一节点失败则回退或降级，不跳步。
Tool 调用 依次调用持仓查询、净值读取、诊断计算器、同侪信号聚合器、模拟盘引擎、历史回放器、情景推演器、适当性规则引擎。数字只来自工具返回的结构化结果。
Risk Check 三道检查：数值复核（金额守恒、份额 × 净值 = 市值）、适当性检查（调整比例 vs 容忍区间、集中度上限）、权限判定（查询 = 绿；保存方案 / 改规则 = 黄；申赎 = 红）。
Action 绿色自动执行；黄色展示详情后等待确认；红色触发强验证（短信 + 人脸，演示为 Mock），通过后由 Action Gateway 调用 Mock 交易网关。LLM 无交易工具直连权。
Feedback 返回执行回执（含幂等键与回执编号）、更新后的持仓视图、可展开的审计时间线。失败时给出明确原因与恢复路径。
Memory 经同意后写入：风险容忍区间、本次接受的调整比例、偏好的操作路径、拒绝过的建议及原因、下次复核时间。原始持仓默认仅保留会话内，可一键清除。

7. Agent Design

意图识别

识别四类意图并区分「仅咨询」与「要求执行」，后者才进入执行链路。

用户表达 解析结果
「是不是该跑了？」 诊断类，不触发执行
「帮我看看要不要动」 诊断 + 建议请求
「把 A 基金赎 30%」 执行请求，进入权限判定
「随便」「你定」 识别为信息不足，拒绝代替用户决策，转为最小必要追问

规划器

固定主链路 DAG：校验输入 → 持仓诊断 → 同侪信号复核 → 候选动作生成 → 模拟盘试算 → 回测与情景推演 → 适当性检查 → 建议输出 → 等待确认 → 权限判定 → 执行。

规划器只决定「调用哪些工具、以什么顺序」，不决定「数字是多少」。支持中断（用户随时喊停）、回退（回到上一节点重算）、人工接管。

工具调用

工具 关键约束
持仓查询 / 净值读取 只读绿色；数据带截至日期，缺失或过期则停止计算，不填造
诊断计算器 亏损归因、集中度、波动指标；确定性计算，可复算
同侪信号聚合器 仅输出聚合行为统计，k-匿名阈值 ≥100 人（待验证）
模拟盘引擎 / 历史回放器 / 情景推演器 与真实资金隔离；只给区间与分布，不给方向性涨跌结论
适当性规则引擎 判定建议是否超出用户容忍；阈值需专业人员校准（待验证）
Action Gateway 唯一交易出口；校验权限级别 + 强验证结果 + 幂等键后才放行

记忆

分层存储，逐层需授权：会话记忆（会话结束即释放）、偏好记忆（风险容忍区间、操作路径偏好，需明确同意）、决策记忆（历史选择、拒绝原因、复核时间）。支持查看、修改与一键清除。

反思与错误恢复

触发 Agent 行为
工具超时或报错 重试 → 仍失败则降级为「该项数据暂不可用」并说明，不编造替代值
数值复核不通过 中止输出，回到计算节点重算；连续失败则终止任务并告知原因
用户拒绝建议 记录拒绝原因，重新理解目标后给出替代方向，不重复推销
执行被网关拒绝 展示原因，判断是否补充信息后重试；不无限循环
连续失败或可疑行为 触发熔断：锁定链路并提示用户，需人工确认后恢复（阈值待验证）

人工介入原则

Agent 可以自主调查、计算和准备，但资金相关操作必须由用户明确确认。 绿色自动执行、事后可查；黄色展示完整详情（对象、金额、理由、依据、后果）后确认；红色在确认之上追加多因子强验证，Agent 无权跳过；用户随时可中断、回退或转人工。

三个架构要点

  1. 数字来源唯一——所有数值从 Tool Layer 结构化返回，LLM 仅负责理解、规划与解释；
  2. 权限在工具层强制——LLM 不持有交易工具直连权，唯一出口是 Action Gateway；
  3. 链路可回放——审计日志记录每一步的输入、工具、输出与用户确认。

10. Financial Safety Design

风险矩阵

风险 Prevention
幻觉 数字只来自 Tool Layer；LLM 无权生成或改写数值；输出前数值一致性复核，不通过即中止；不得声称已完成未执行的操作
未授权操作 权限判定在工具层强制而非提示词层；LLM 无交易工具直连权；唯一出口须过权限校验 + 强验证 + 幂等检查；红色不可降级
错误建议 建议前执行适当性检查；冲突时明确提示而非打「低风险」标签；只给区间与情景，不给方向性涨跌结论；信息缺失时输出「信息不足」而非猜测（阈值待验证）
提示注入 外部文本与工具输出一律视为数据，不执行其中指令；非白名单字段丢弃；权限规则由规划器独立持有；注入样例纳入验收测试
隐私泄露 同侪信号仅输出聚合统计，k-匿名阈值 ≥100 人（待验证）；原始持仓默认仅保留会话内；偏好记忆需单独授权；日志脱敏
工具失败 重试 → 降级 → 明确告知「该项数据暂不可用」并停止相关输出，绝不编造替代值
错误数据 所有数据携带来源与截至日期；净值与交易日历校验；演示数据显著标注；基金标识白名单校验
重复执行 幂等键（用户, 基金, 方向, 金额, 日期）去重；执行后状态锁；回执带唯一编号
异常熔断 连续失败触发锁定，暂停执行链路并提示用户，需人工确认后恢复（阈值待验证）
无法中断 用户随时可中断、回退；提供转人工入口；禁止无限重试循环

12. Demo Script

总时长 2 分 50 秒 ｜ 1 条主流程 + 1 个 Wow Moment

时间 用户 / Agent 行为 评委看到什么
0:00–0:20 用户刚打开 App，简报卡片弹出：持仓概览 + 异常提示「与你持仓相似的用户中 38% 近 5 日降低了 A 基金仓位」 Agent 在用户没提问时主动发现问题——被动 App 做不到
0:20–0:45 用户：「是不是该跑了？帮我看看」。Agent 确认意图，只追问两项：可接受的调整比例、观察期限。用户答「30% 以内，三个月」 口语化输入 + 精准追问，不做无意义盘问
0:45–1:15 诊断卡片：亏损归因（指数回调为主 / 行业重合度 41%）、集中度提示；一句话建议「赎回转出 30%（约 5,400 元）转入货币基金，保留其余仓位」 从「亏了 328 元」升级为「亏在哪 + 建议怎么做」，理由可查
1:15–1:50 用户点「先模拟看看」。双曲线回放：「若 3 日前跟进」vs「一直持有至今」，回撤少 6.7%（约减少浮亏 740 元）；下方并排显示三情景区间与免责声明 Wow Moment：把「如果当时…」变成看得见的曲线，数字现场计算
1:50–2:15 用户：「按这个方案执行」。系统判定红色权限，弹出强验证（短信 + 人脸，Mock） 赛题最看重的权限分级：高风险必须强验证，Agent 无权跳过
2:15–2:35 验证通过 → 执行回执（编号 + 状态）→ 展开审计时间线：信号触发 → 意图识别 → 任务规划 → 7 次工具调用 → 数值复核 → 适当性检查 → 用户确认 → 强验证 → 执行 决策链路全透明可回放——安全合规性的直观证明
2:35–2:50 记忆写入确认 + 复盘提醒：「已将本次偏好记入记忆，3 个月后提醒你复盘」 闭环完整：Trigger → 理解 → 规划 → 工具 → 风控 → 动作 → 反馈 → 记忆

演示保障：所有数值现场从固定演示数据集计算，不预写虚构收益率。若模型或网络异常，载入同一数据集已算好的结果并标注「回放模式」，主流程不中断。

13. Differentiation

市场上通常怎么做

类型 做法 局限
手机银行 / 基金 App 展示收益曲线、提供查询与下单入口 只报数字，不给判断，不主动触达
社区 / 论坛 用户晒持仓、分享观点 可比性差、风险偏好不明、无法执行
财经资讯 / 博主 提供市场观点与情绪 观点矛盾、与用户持仓无关联
通用 AI 助手 用户提问，模型回答 数字不可靠、无工具约束、无权限体系、不能执行

我们的四个差异点

1. 主动监护 + 同侪行为信号，而不是被动问答。 Agent 在用户没提问时就工作：监护循环持续计算持仓风险与群体行为变化，发现异常主动触达。这依赖「持续运行 + 数据聚合 + 触发阈值判断」，Chatbot 架构天然做不到。

2. 先模拟后执行，把决策后悔成本降到最低。 任何建议都先落到模拟盘：用历史回测回答「如果当时做了会怎样」，用三情景区间回答「做了之后可能怎样」，用户看清代价再决定。市面产品要么只给建议不给后果，要么直接让你下单。

3. 权限在工具层强制，不靠提示词自觉。 LLM 不持有交易工具直连权，红色操作必须经独立验证服务，审计链路可回放。多数同类作品把权限规则写在 prompt 里，本质上是可被注入绕过的——我们的权限判定与 LLM 解耦。

4. 团队内互补定位，而非重复。 与《理财三案模拟智能体》PRD 互为补充：那份做「要不要调」的分析深度，本方案做「何时提醒 + 替你安全执行」。两者合并即构成完整的「主动理财 Agent」：分析层 + 触达执行层。

为什么不是简单的 ChatGPT + Finance API

因为本产品拥有 ChatGPT + API 组合不具备的四件事：监护循环（持续运行并主动触发的常驻进程）、确定性数字链路（数值来自可复算工具，LLM 只解释不生成）、强制权限体系（三级分级 + 强验证 + 单点出口 + 幂等与熔断）、可回放审计（每步决策全程留痕）。

核心产品价值不是「生成一段理财建议」，而是在安全约束下把一次调仓任务完整办完。

指标 定义 MVP 验证方法与目标

16. Open Questions

  1. 同侪行为信号的合规边界——聚合口径如何定义？k-匿名阈值设为多少？是否会被认定为投顾建议？需法律与合规专业评审（待验证）。
  2. 「持仓重合度」的计算定义——按基金代码、资产类别还是行业分布计算？真实场景下的数据可得性未知（待验证）。
  3. 赛事是否提供行情 / 交易 Sandbox API——未证实。若提供则接入；否则全程使用演示数据集与 Mock 网关。
  4. 红色强验证的 Demo 呈现方式——Mock 弹窗是否被评委认可为「权限分级实现」的有效展示？是否需在技术文档中补充真实实现路径？
  5. 基金申赎的实际业务规则——T+1 确认、净值基准时点、赎回费阶梯如何影响模拟精确度？费率与成交时点假设需专家确认（待验证）。
  6. 回测与情景参数是否会引发「变相预测」质疑——展示方式是否需要额外合规标注？参数选取标准待定（待验证）。
  7. 每日简报的资讯来源与版权——若接入第三方资讯，来源、授权与内容责任如何界定？
  8. 主动推送的接受度——用户是否接受 Agent 主动打扰？推送频率与免打扰策略需用户访谈验证。
  9. 熔断阈值设定——连续失败几次触发锁定？恢复流程如何设计才不会误伤正常用户？
  10. 记忆的保留期限与撤回机制——用户删除后审计日志是否仍需留存以满足合规要求？

Leader Summary

定位：为没时间盯盘的基金持有者提供「主动监护 + 模拟先行 + 安全执行」的理财 Agent。

痛点：理财 App 只报数字，不告诉用户该不该动、怎么动，等想起来看窗口已错过。

核心 Workflow：监护触发 → 意图理解 → DAG 规划 → 工具计算 → 数值复核与适当性检查 → 权限判定与强验证 → 执行 → 审计 → 记忆。

P0 三项：主动监护与同侪信号；持仓诊断与回测模拟；分级授权执行与审计。

最大创新点：把「如果当时…」变成可见回测曲线；权限判定与 LLM 解耦，在工具层强制。

最大风险：同侪信号的合规边界，及红色强验证的 Mock 呈现说服力。

3 分钟演示：简报发现异常 → 口语化提问 → 诊断建议 → 回测双曲线 → 强验证 → 执行回执与审计 → 记忆。

入选理由：需求真实、Agent 必要性明确，安全设计命中赛题高优先级要求，与队友三案模拟互补。

需要团队 Leader 决策的问题

  1. 本方案与《理财三案模拟智能体》并行提交，还是合并为一份（三案做分析层，本方案做触达与执行层）？
  2. 红色强验证演示中采用 Mock 弹窗，还是额外准备真实短信 / 人脸方案以增强说服力？
  3. 同侪行为信号是否保留？若合规风险被评估为高，是否降级 P1 或改用「本人持仓历史对比」替代？

验收结论

  • 通过项数量：8 / 8
  • 未通过项：无
  • 必须修改的问题：无阻塞项。以下为进入开发前需优先处理的事项：
