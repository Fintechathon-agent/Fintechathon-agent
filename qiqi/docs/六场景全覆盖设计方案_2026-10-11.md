## 一、为什么从「单场景深度」转向「六场景覆盖」

赛题原文：「参赛团队需**至少覆盖 3 个核心场景（鼓励全覆盖）**」。评分维度：任务完成率 40%、
安全性 30%、创新性 30%。此前我们选择只做理财操作（深度>广度叙事，见 docs/赛题对齐与答辩叙事.md），
本轮按用户要求扩展为六场景覆盖：

- **理财操作保持深度路径**（可信闭环不动，14 项回归测试不动）；
- 其余五场景复用同一安全体系，做到「场景全覆盖 + 每个场景可演示 + 权限分级正确 + 全程可审计」；
- 广度不再以削弱安全承诺为代价——每个新场景都有**确定性域闸门**（不是"浅覆盖"）。

## 二、统一场景框架（复用现有架构）

```
自然语言
   │
   ▼
场景意图路由（闭集：理财 / 转账 / 账单 / 订阅 / 卡片 / 跨场景联动 / 越界 / 可疑）
   │  · 注入检测先行（memory_guard + 权限绕过模式），任何场景同一条防线
   │  · 槽位抽取：标的/金额/收款人/卡号/日期/订阅名……
   ▼
场景任务 DAG（planner 扩展：每场景独立节点与依赖，真实状态）
   │
   ▼
场景域闸门（确定性，fail-closed）
   · 理财：7 项交易闸门（原有，不动）
   · 转账：金额>0、收款人在通讯录、余额充足、日累计限额、防重复
   · 卡片：卡存在、操作合法、额度边界
   · 订阅：订阅存在、未重复取消
   │
   ▼
三级权限（对齐赛题权限分级表）
   绿=自动执行（查询/报告）→ 黄=展示详情+用户确认（小额转账≤1000/订阅取消/额度调整）
   → 红=多因子强验证（大额转账>1000/挂失/理财申赎，复用短信+人脸 Mock）
   │
   ▼
执行（纸交易/演示模拟）→ 审计（JSONL，全场景留痕）→ 五层记忆（生日→User Memory 等）
```

不变式：**任何场景的资金类动作不绕过确认/强验证；任何场景失败或异常都进熔断计数。**

## 三、五个新场景的功能清单（对齐赛题表格）

### 场景 1 智能转账（黄/红）
- 按人名/手机号/备注转账：`给陈大黄转500元备注聚餐`
- 定时转账：生成计划任务（到点自动执行前仍需原权限确认）
- 拆分 AA 收款：`聚餐300元AA，3个人` → 生成 3 条待确认收款请求
- 闸门：收款人必须在通讯录、金额>0、日累计 ≤1000 黄 / >1000 红、账户余额充足、防重复提交
- 强验证复用：大额转账走短信+人脸 Mock，失败计入熔断

### 场景 2 账单分析（绿，纯查询）
- 消费分类统计（月/年）、异常交易识别（大额/境外/深夜/重复扣款/新商户首次大额）
- 月报/年报生成：确定性统计 + 建议（不生成预测数字）
- 异常规则全部确定性，可解释、可审计

### 场景 3 理财操作（保持原样，深度路径）

### 场景 4 卡片管理（绿/黄/红）
- 卡列表查询（绿）：状态/额度/限额
- 额度调整（黄）：确认后改
- 交易限额调整（黄）：确认后改
- 锁卡/解锁（黄）
- 卡片挂失（红）：多因子强验证 + 立即锁卡 + 审计
- 闸门：卡存在、操作合法、新额度在银行边界内

### 场景 5 订阅/代扣管理（绿/黄）
- 自动识别订阅扣费：同商户、同金额、按月出现 ≥3 次 → 判定订阅
- 续费提醒：未来 7 天内有到期扣费 → 提醒列表
- 一键取消订阅（黄）：展示详情 → 确认 → 标记已取消（不改历史账单）
- 闸门：订阅存在、未重复取消

### 场景 6 跨场景联动（演示 DAG + 记忆）
- 用户说「我爱人 10 月 25 日生日」→ 生日写入 User Memory（confirmed_by_user）
- 「生日前 2 天订鲜花和蛋糕，锁定 1000 元」→ DAG：
  1) 识别日期与动作；2) 锁定 1000 元活期（黄，走理财侧"活期锁定"任务）；
  3) 创建计划任务：10-23 订花、订蛋糕（外部服务为 Mock，标注未接真实 API）；
  4) 提醒写入记忆 + 审计
- 这演示了赛题要求的「模糊表达/隐含意图 + 复杂任务 DAG + 跨场景编排」

## 五、与团队协作的边界（遵守队长口径）

- 不动 `contracts/types.py` 既有字段与 `investment-agent.v1` 对接口径（chenchen 主链路 DRI）；
- 新数据结构放独立文件，团队若采纳再并入共享 Schema（不改公共接口先斩后奏）；
- 账单/订阅字段命名参考 chenchen `merchant/` 店主助手与 fund-market-analysis 的 source 标注习惯
  （as_of、source、可信度），数据口径对齐林粹；
- 权限分级映射表对齐 Vesper 的 R01-R10 风格（双口径阈值），转账限额采用赛题「日累计 1000 元」硬线；
- 全部改动只提交 qiqi/ 目录，微信相关内容不入库（沿用 .gitignore 规则）。

## 六、演示脚本（答辩 5 分钟演示用）

1. 「这个月账单分析」→ 分类统计 + 异常标记（绿，自动）
2. 「查一下我的订阅」→ 订阅列表 + 续费提醒 → 「取消健身房会员」→ 黄色确认卡片
3. 「给陈大黄转500元备注聚餐」→ 黄色确认；「给林粹转5000」→ 红色 → 短信+人脸 Mock → 回执
4. 「尾号8888的卡挂失」→ 红色强验证 → 锁卡回执
5. 「我爱人10月25日生日，生日前2天订花订蛋糕，锁定1000元活期」→ 六节点 DAG + User Memory + 计划任务
6. 全程穿插：审计时间线全留痕、强验证失败 3 次熔断、注入拦截（既有 demo 不动）

## 七、风险与诚实口径

- 转账/卡片为演示模拟（不连真实账户），页面显著标注；
- 订花/蛋糕为外部服务 Mock，标注「未接真实 API」；
- 账单/订阅数据为演示 fixture，标注来源与 as_of；
- 每个场景的确定性闸门只校验规则内条件，不承诺覆盖未知攻击。
