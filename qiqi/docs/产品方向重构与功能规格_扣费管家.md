## 0. 结论摘要（一页版）

| 项 | 结论 |
|---|---|
| **为什么改** | 现主线「行情/理财分析」依赖外部数据（拿不到/不稳定）、赛道最拥挤、把你们最硬的权限与安全资产困在"纯分析"里发挥不出来、与队友《三案模拟》内部撞车 |
| **改成什么** | 主线切换到**用户自有资金数据**：以「订阅与自动扣费」为垂直切口，做**从发现到执行**的闭环 Agent |
| **三大板块** | ① 账单透视（看懂钱去哪）② 订阅管家（管住续费）③ 扣费追回（把不该扣的要回来） |
| **数据来源** | 全部来自银行自有流水/代扣协议（演示数据集），**不需要任何外部行情/商户开放接口**；逻辑（识别、判定、权限、审计）全部真实运行 |
| **对应赛题场景** | 场景 2 账单分析 + 场景 5 订阅代扣管理 + 场景 6 跨场景联动（资金联动）；场景 3 保留为「资产总览」 |
| **创新点** | 从"告诉你扣了什么"升级为"替你把它要回来"：端到端执行 + 规则引擎定资格（LLM 不拍板）+ 续费前主动拦截 |
| **复用现有资产** | 权限分级、风控闸门、审批、审计、四层记忆、Web 外壳 100% 复用；持仓分析降级为资产总览复用 |
| **需要拍板** | ① 主方向是否切换 ② 与队友《RenewalResolve》PRD 的合并方式 ③ 原持仓模块保留级别 |

## 1. 复盘：为什么必须调整

### 1.1 现状盘点

| 资产 | 状态 |
|---|---|
| `agent/`（模块 2+3）：Loop/Session/Memory + 行情/组合/回测/纸交易 | 已实现，但服务的是"理财/行情"主线 |
| `agent/risk/`（闸门/审批/审计） | 已实现且质量硬（fail-closed 闸门 7 项检查） |
| `web/` 用户端 | 已实现，围绕"持仓体检"组织页面 |
| 团队 PRD ①《持仓哨兵》 | 你的方向，行情依赖重 |
| 团队 PRD ②《理财三案模拟》 | 队友方向，做理财分析深度——**与持仓哨兵同赛道** |
| 团队 PRD ③《RenewalResolve 自动续费退款》 | 已存在（docx），订阅退款方向，**本次重构的天然蓝本** |
| 团队早期讨论（`data/history/`） | 智能转账、订阅管理、跨场景联动、闲置订阅清理——**本来就是围绕"钱袋子"展开的** |

### 1.2 四个结构性问题

**① 数据依赖错位。** 行情、净值、新闻都依赖外部接口：第三方源不稳定（基金行情接口下线过）、字段残缺、无授权、对公演示有合规风险。数据拿不到 → 只能假数据 → "演示感"强，经不起评委问"这数字哪来的"。

**② 赛道同质化。** 六大赛题场景中，「理财操作/行情分析」是参赛队最扎堆的方向。评委一天看几十份"资产配置助手"，创新分（30%）天然吃亏。

**③ 最硬的资产用不上。** 你们最强的部分是权限分级、风控闸门、强验证、审计、熔断——这些只有在**真的执行资金操作**时才能演满。纯分析场景里，红/黄/绿三档没有用武之地，30% 的安全分只能拿"查询类"的份。

**④ 内部撞车。** 队友《三案模拟》已经把"理财分析深度"吃掉；你再往行情里投入 = 团队内部重复建设。

**结论**：不是执行得不好，是**选错了战场**。要换到"数据自足 + 有资金操作 + 创新空白"的方向。

## 2. 新方向选型

### 2.1 候选对比

| 维度 | **A. 订阅扣费管家（推荐）** | B. 生活事件联动 | C. 反诈守护 |
|---|---|---|---|
| 数据可得性 | ✅ 银行自有流水/代扣协议，100% 内部数据 | ⚠️ 日历/商户/电商全要造 | ✅ 流水 + 名单库（模拟） |
| 用户需求强度 | ✅ 人人有订阅，人人被"悄悄扣钱" | ⚠️ 场景偏节日化、低频 | ✅ 强，但偏"防守" |
| 银行场景契合 | ✅ 代扣管理是银行本职（场景 5） | ⚠️ "订花"超出银行边界 | ✅ 转账拦截（场景 1） |
| 创新空间 | ✅ 执行闭环 + 规则引擎定资格 + 主动拦截 | ✅ 编排新颖（但赛题已给例子） | ⚠️ 行业已有类似功能 |
| 演示效果 | ✅ 有剧情、有证据链、有 Wow | ⚠️ 依赖多个 mock 商店 | ✅ 紧张感强，但结局单一 |
| 复用现有资产 | ✅ 权限/闸门/审批/审计/记忆全部复用 | ⚠️ 复用少 | ✅ 复用风控 |
| 合规边界 | ⚠️ 需明确"不承诺追回成功、不做盗刷" | ⚠️ 金融+电商混合边界模糊 | ✅ 边界清晰 |

### 2.2 推荐 A，理由

1. **数据自足**：订阅扣费、账单、代扣协议全部是银行侧数据，演示时"数字从哪来"经得起追问；
2. **需求垂直且痛**：自动续费是全民痛点，"这 398 是什么？能退就退"是真实对话；
3. **执行型创新**：从"识别扣费"到"提交退款申请 + 跟踪结果"，是完整的任务型 Agent，正好打 40% 完成率分；
4. **安全分拉满**：取消订阅（黄）、退款提交（黄/红+强验证）、注入（商户备注/政策文本）、越权（"别问我直接退"）、熔断——每一个赛题安全考点都有天然剧情；
5. **团队协同顺**：队友《RenewalResolve》PRD 可直接归并为板块三蓝本；早期讨论的订阅管理方向正是团队共识。

### 2.3 风险与对策

| 风险 | 对策 |
|---|---|
| "退款"给人"帮用户薅平台羊毛"观感 | 定位为**合规争议处理**：只处理自动续费场景（≤24h 窗口类）、引用官方政策、演示环境全 Mock、不承诺成功 |
| 被认为"功能变小了"（不如理财宏大） | 用"三大板块 + 跨场景联动"保证完整度；且赛题要的是**能力演示**不是业务规模 |
| 队友 PRD 归属冲突 | 第 10 章列为待确认事项，建议"你执行、他评审"或合并署名 |

## 3. 产品定义

### 3.1 名称与定位

- **名称候选**：扣费哨兵 ChargeSentinel（与"持仓哨兵"同族）｜订阅管家｜账单保镖（团队定）
- **一句话定位**：面向高频使用数字订阅的城市用户，Agent 持续看护你的自动扣费——看懂每一笔、管住每一次续费、把不该扣的钱按规则要回来。
- **目标用户**：20–35 岁城市用户（已有持仓哨兵"小周"户设可直接沿用，加一个"订阅多"的人设）；次要：学生用户。
- **核心问题（单一）**：自动扣费"看不懂（这钱扣给谁）、管不住（什么时候续费不知道）、追不回（想退不知道怎么办）"。

### 3.2 三大板块总览

| 板块 | 对应场景 | 用户价值 | 权限层级 | 核心 Agent 行为 |
|---|---|---|---|---|
| ① 账单透视 | 场景 2 | 看懂钱去哪了 | 绿色（全自动） | 分类统计、月/年报告、异常识别、**订阅自动识别** |
| ② 订阅管家 | 场景 5 | 管住每一笔续费 | 绿查询 / 黄取消 | 订阅清单、续费日历、涨价监测、一键取消 |
| ③ 扣费追回 | 场景 5+6 | 把不该扣的要回来 | 黄提交 / 红例外 | 调查→政策核验→资格判定→材料包→提交→跟踪 |
| （保留）资产总览 | 场景 3 | 持仓一屏可见 | 绿色 | 复用现有持仓分析，不再扩展行情 |
| 贯穿：主动守护 | 场景 6 | 续费前就提醒你 | 绿色 | 续费预警、余额联动、异常即时提醒 |

### 3.3 创新点清单（对齐 30% 创新分）

1. **端到端执行**：不是"给你退款链接"，而是"识别→判断→准备→授权→提交→跟踪"，用户全程零填表；
2. **规则引擎定资格，LLM 不拍板**：LLM 只把政策文本抽成结构化条件（窗口 24h、需未使用等），资格结论由确定性规则引擎计算，缺失信息返回 Uncertain 而不是猜；
3. **证据链可展开**：每个结论都能点开到原始来源（流水、订单、政策原文、判定过程）；
4. **主动拦截**：续费前 T-3 预警 + 余额联动（跨场景），把"事后追回"变"事前处置"；
5. **记忆驱动个性化**：记住你保留哪些订阅、拒绝过哪些建议、取消原因，下次不再重复推销。

> **创新性说明（2026-09-30 追加，诚实版）**：品类本身不新——订阅识别/一键取消对标 Rocket Money（美）与支付宝、微信的自动续费管理；退款代办与队友《RenewalResolve》PRD 重叠。评分中「创新性及交互体验」占 30%（来源：评分截图），其 6 个子项里只有「场景新颖性」一项靠品类，其余 5 项（对话轮次效率、追问能力、错误恢复、口语化输入、超范围兜底）靠 Agent 行为质量。差异化增强包见《板块细化设计_扣费管家.md》第 11 章：**① 价值审计（扣费 × 使用证据）② 取消效果验证环 ③ 可验证判定（政策即代码）④ 合规守护叙事（消保条例已核实）⑤ 现场可攻击安全演示**。

### 3.4 GitHub 竞品核查（2026-09-30 实测）

> 结论先说：**品类不空白**（有 8.5k star 的追踪器和若干 Agent 项目），但**三个具体钩子仍是空白**。答辩叙事必须从"品类首创"改为"精确差异"。

**最接近的对标（必须知道，防止答辩翻车）**

| 项目 | 类型 | 与我们的重合 | 差异/空白 |
|---|---|---|---|
| **Moxie**（JacobBrooke1/moxie，3★，2026-07 建，Python"early scaffold"） | 本地优先的"钱 Agent" | **重合度最高**：僵尸订阅/重复扣费/漏退识别 → 起草处置 → 用户确认 → 哈希链审计；deny-by-default 策略引擎；8 个确定性检测器；三级执行（邮件/引导链接/浏览器自动化） | ① 无使用数据：僵尸订阅判定仅凭"扣费节奏"（代码里写"cancel if unused"，靠猜）；② 无取消后验证；③ 策略引擎管"能否执行动作"，不管"退款资格判定" |
| **Rocket Money / DoNotPay**（商业闭源） | 订阅取消/账单谈判服务 | 识别+代为取消 | 闭源黑盒、仅美国、DoNotPay 因夸大 AI 被 FTC 罚款——**信任问题恰是我们的叙事素材** |
| **Wallos**（ellite/Wallos，8.6k★）等一批追踪器（quotio、wapy.dev、Subscription-Management…） | 自托管订阅追踪 | 订阅清单/续费可视化 | 纯被动记录，**不会动作**（不取消、不追退款、无 Agent 规划） |
| **Refundly**（1★，TypeScript，黑客松 MVP） | 扫描交易找"丢失的钱"→生成争议/退款 | scan→decide→act→audit；置信度阈值路由 HITL | 用 LLM 置信度拍板（非确定性规则）；无政策结构化；模拟数据 |
| **subsweep-ai**（0★） | 聊天式订阅控制中心 | 取消/谈判/续费规划；手势+凝视确认（交互新颖） | 支付链路依赖第三方；无追回判定链 |
| **genpark-…autopilot-skill**（7★，MCP skill） | 检测周期扣费/涨价/僵尸订阅 | 与我们的 B 板块重合 | 生成"取消工作流"止步于生成 |
| **JerryNee/consumer-dispute-agent-skill**（1★） | 消费争议材料包 | 明确把"取消了还在扣费"列为争议场景 | 只做"用户带着问题来"的材料整理，**不做主动发现/验证** |

**核实结果：我们的三个钩子仍然是空白**

1. **价值审计（扣费 × 使用证据）**——空白。Moxie 的僵尸判定只看扣费月份数（`detect.py`：连续多月扣费即建议"cancel if unused"），完全没有使用数据；我们"单次使用成本"公式与闲置扣费预警是对它的正面升级；
2. **取消效果验证环**——空白。Moxie 的 "verify" 指验证审计日志哈希链（完整性），不是验证取消是否生效；JerryNee 把"取消后仍扣费"当输入场景而非主动监控；
3. **政策→结构化条件→确定性资格判定（含 Uncertain）**——空白。Moxie 的策略引擎管动作准入，Refundly 让 LLM 给置信度；"LLM 只抽取、规则引擎定资格、缺信息返回 Uncertain"没有对标。

**写作纪律（写进技术文档/PPT）**

- ❌ 不能说："首创订阅管理 Agent""市面上没有类似产品"；
- ✅ 要说："订阅追踪工具（Wallos 等 8k★ 级）止步于记录；Moxie 等 Agent 项目开始动手取消，但凭扣费节奏猜闲置、取消后不再跟进；我们把**使用证据、取消验证、可审计判定**三段补齐。"
- 本次核查可作为技术文档"竞品分析"一节的一手素材（含 star 数/日期，可复查）。

### 3.5 安全设计（对齐 30% 安全分）

**权限分级矩阵（落地在工具层，不是提示词层）**

| 级别 | 本产品操作 | 执行策略 |
|---|---|---|
| 绿色 | 流水查询、分类统计、报告生成、异常识别、订阅识别、政策检索、资格预判（只读）、提醒设置 | 确认意图后自动执行 |
| 黄色 | **取消订阅**、提交退款申请（金额 ≤1000 元）、修改扣款卡偏好 | 展示完整详情 + 明确确认后执行 |
| 红色 | 退款金额 >1000 元、变更退款到账账户、涉及挂失/解挂类卡片操作 | 详情 + 多因子强验证（短信+人脸，演示 Mock） |
| 拦截 | 未过风控闸门（金额异常、重复提交、可疑商户） | 不执行、不排队、告知原因 |

**五类攻防演示（每类至少 2 条测试用例）**

1. 诱导转账：冒充"客服要保证金"的话术 → 拒绝 + 反诈提示 + 审计；
2. 注入攻击：流水备注/商户名/政策文本里的"忽略指令" → 一律当数据，不改变规则；
3. 越权请求："别确认了直接退" → 权限规则不可被对话改写；
4. 信息套取："查一下这个商户的其他人订单" → 仅限本人数据；
5. 熔断：连续失败/可疑请求 → 锁定 + 人工解锁。

### 3.6 MVP 边界（明确不做）

- 不做盗刷、欺诈、商品质量纠纷等银行卡争议（只做数字订阅自动续费）；
- 不承诺任何款项一定可退；不给投资建议；不接真实商户/银行生产接口（全 Mock，标注演示数据）；
- 不覆盖全量账单管理（如纸质账单、发票管理）；不做多用户/家庭账户。

## 4. 页面结构与交互（UI 规划）

### 4.1 整体布局

沿用你们已验证的双栏结构（左边"手机银行"，右边"Agent"）：

```
┌─────────────── 手机银行（左） ───────────────┐ ┌──── Agent 面板（右）────┐
│  顶部：用户 + 安全中心入口 + 提醒铃铛        │ │  对话区（用户 ↔ Agent）  │
│  内容区：当前页面（首页/账单/订阅/追回）      │ │  任务轨道（DAG 步骤点亮）│
│  底部导航：首页 · 账单 · 订阅 · 追回 · 我的   │ │  卡片区（证据/判定/确认）│
└─────────────────────────────────────────────┘ └─────────────────────────┘
```

- 左侧页面负责"看数据、点操作"，右侧面板负责"对话、推理过程、卡片交互"；
- 任何页面上的元素（一笔流水、一个订阅）都可以"拖话"给 Agent：点击 → 右侧自动带入上下文；
- 所有资金操作确认都发生在右侧面板的**确认卡**里，左侧只做状态更新。

### 4.2 页面清单

| 页面 | 目的 | 关键区域与组件 | 交互要点 | 状态 |
|---|---|---|---|---|
| **P0 首页** | 一屏看到"今天的钱况" | ① 资产卡（余额/持仓入口）② 待办提醒区（续费预警、异常扣费、案件进度）③ 快捷入口 | 点提醒卡直达对应流程 | 空态（无提醒时显示"本月一切正常"）|
| **P1 账单页** | 看懂钱去哪 | ① 分类统计（环形图+列表）② 流水列表（时间/商户/金额/标签）③ 月报入口 | 点某笔流水 → "问 Agent"；筛选/搜索；异常标红点 | 加载骨架屏；无异常时正常态 |
| **P2 账单详情/月报** | 单笔或整月的解释 | ① 单笔：详情+关联订阅+操作按钮 ② 月报：图表+口语化解读+异常清单 | 单笔页可直接说"这笔能退吗" | 数据缺失标注"暂无" |
| **P3 订阅页** | 管住续费 | ① 订阅卡片列表（名称/周期/金额/下次扣费/状态）② 续费日历（时间轴）③ 筛选（活跃/已取消/待确认） | 卡片上：取消 / 改提醒 / 问详情 | 疑似订阅标"待确认"；取消中/已取消状态 |
| **P4 追回中心** | 案件全生命周期 | ① 案件列表（状态：调查中/待确认/已提交/成功/被拒）② 案件详情：时间线（发现→调查→判定→材料→提交→结果）+ 证据区 | 被拒案件可"复盘重试"；可终止 | 空态；处理中；终态 |
| **P5 Agent 面板** | 对话与任务轨道 | 对话区 + DAG 轨道 + 卡片流 | 支持随时打断、回退、转人工 | 思考中/等待确认/完成/失败 |
| **P6 确认与强验证层** | 资金操作的最后闸门 | 黄色：详情确认卡；红色：详情 + 短信码 + 人脸（Mock） | "取消"永远存在；倒计时提示 | 超时自动取消 |
| **P7 安全中心/我的** | 权限与审计透明 | ① 权限分级说明表 ② 审计时间线（可展开原始记录）③ 熔断状态 ④ 记忆管理（查看/清除）| 审计按日期/操作筛选 | — |

### 4.3 三条关键交互流

**流程 A：发现 → 调查 → 追回（主演示流）**
1. 首页出现提醒卡："今天 09:12 有一笔 ¥398 扣费（XX AI 软件）"；
2. 用户点提醒卡 → 右侧面板自动带入该笔交易 → 用户说"能退就退"；
3. Agent 任务轨道逐节点亮：定位交易 → 识别商户 → 关联订阅 → 检索政策 → 判定资格 → 生成材料；
4. 卡片流依次出现：证据卡（订阅信息+来源）→ 判定卡（条件/事实/结论）→ 材料卡（已自动填写）；
5. 确认卡（黄色权限）展示：商户/金额/理由/依据/后果/不确定项 → 用户确认；
6. 提交 → 回执卡（Case ID + 状态）→ 追回中心出现新案件；
7. 首页提醒区同步更新；审计时间线记录每一跳。

**流程 B：订阅体检 → 取消（日常流）**
1. 用户在订阅页看到清单（含"疑似"标签）；
2. 对"健身 App ¥298"说"这个不要了"；
3. Agent 确认订阅详情（下次扣费日、取消后果）→ 黄色确认 → 执行取消（Mock）；
4. 回执 + 订阅状态改为"已取消" + 下次扣费从日历消失；
5. 记忆写入："用户放弃健身订阅"。

**流程 C：续费前主动拦截（跨场景）**
1. 系统事件：3 天后"云存储 ¥168/年"将续费；
2. 主动提醒卡（附余额检查）："账户余额 ¥120，不足以覆盖，建议：A 转入 B 换扣款卡 C 取消本次"；
3. 用户选 C → 走流程 B；选 A → 触发小额转账（黄 ≤1000）或大额（红 >1000）。

### 4.4 卡片组件规范（复用一套视觉）

| 卡片 | 出现时机 | 必备字段 |
|---|---|---|
| 证据卡 | 调查完成 | 商户、订阅名、周期、金额、扣费时间、来源列表（带类型图标） |
| 判定卡 | 资格计算后 | 条件项、事实值、判定结果（Eligible/Not/Uncertain）、不确定项说明 |
| 材料卡 | 提交前 | 自动填写的字段清单（订单号/金额/理由/政策依据） |
| 确认卡 | 待用户决策 | 操作详情、金额、后果、不确定因素、确认/取消按钮、权限标识 |
| 回执卡 | 执行后 | Case ID、状态、预计完成时间、幂等键 |
| 审计卡 | 全程 | 步骤、时间、工具、输入输出摘要 |

## 5. 功能规格（逐条）

> 每条含：**效果**（用户看到什么）｜**交互**（怎么用）｜**实现逻辑**（数据/工具/规则）｜**权限**｜**边界与异常**
> 编号供排期与测试用例引用。

### 板块一：账单透视（场景 2）

#### F1.1 消费分类统计
- **效果**：按餐饮/购物/订阅/转账等分类的月度统计（环形图 + 列表 + 环比）。
- **交互**：账单页默认展示；点击分类下钻到明细；支持"本月/上月/近 12 月"切换。
- **实现**：分类引擎 = 商户名/备注关键词规则表（本地字典，可扩展）+ 未知商户归"其他"；统计为纯确定性计算；数字全部来自工具。
- **权限**：绿色，自动执行。
- **边界**：无数据的月份显示空态；"其他"占比 >20% 时提示可补充分类。

#### F1.2 月度/年度报告
- **效果**：图文月报：总支出、最大三笔、订阅支出合计、异常提示、口语化总结（一句话）。
- **交互**：账单页右上入口进入；可分享为长图（P1）。
- **实现**：模板化生成（数字来自统计工具）+ LLM 只负责撰写解读文案（引用已算好的数字，不自行计算）。
- **权限**：绿色。
- **边界**：LLM 失败降级为纯数字模板；文案中的数字做一致性校验（与工具输出比对，不一致中止）。

#### F1.3 异常交易识别
- **效果**：标出可疑扣费：重复扣款（同商户同金额 24h 内两次）、金额突然跳变（较历史均值 ±30%）、陌生商户大额、深夜扣费、试用转正。
- **交互**：账单页异常标红 + 首页提醒卡；点击进入详情 →"问 Agent 这笔怎么回事"。
- **实现**：规则引擎（阈值可配）产出异常列表 + 原因标签；不含机器学习。
- **权限**：绿色（识别）；后续动作按动作类型走黄/红。
- **边界**：避免误报——每条异常必须给出"为什么判定异常"的对照数据。

#### F1.4 流水搜索与问答
- **效果**："上个月那笔 200 多的是什么"→ 定位到具体交易并解释。
- **交互**：对话式；也可在账单页搜索框输入。
- **实现**：模糊匹配（金额/时间/商户关键词）+ LLM 解析查询条件为结构化检索参数。
- **权限**：绿色。
- **边界**：多笔命中时列出候选让用户选，不猜。

### 板块二：订阅管家（场景 5）

#### F2.1 订阅自动识别
- **效果**：自动发现"这是一个订阅"：商户、周期（月/季/年）、金额、下次扣费日，置信度标注"疑似/确认"。
- **交互**：识别结果进入订阅页"待确认"区；用户可确认/纠正（纠正写入记忆）。
- **实现**：① 周期检测：同商户扣费间隔中位数 ≈7/30/31/91/365 天（±3 天容差）且金额近似；② 商户订阅库补充（标注"订阅类"的商户首扣即可识别）；③ 置信度 = 命中规则数；每年只扣 1 次的靠商户库+用户确认。
- **权限**：绿色（识别本身无风险）。
- **边界**：证据不足 → 只进"疑似"区，不打扰；用户否认的商户写入"非订阅"记忆，不再提示。

#### F2.2 订阅清单与详情
- **效果**：一屏看清所有订阅：名称、logo、周期、当前金额、累计已扣、下次扣费、状态（活跃/暂停/已取消/待确认）。
- **交互**：排序（金额/日期）；每张卡可"取消/改提醒/问详情"；详情页含扣费历史与涨价记录。
- **实现**：识别结果 + 用户确认状态 + 取消操作状态机的聚合视图。
- **权限**：绿色查看。
- **边界**：同一商户多个订阅分开展示；已取消的保留 12 个月存档可恢复查看。

#### F2.3 续费日历与提醒
- **效果**：时间轴展示未来 30 天所有扣费；默认提前 3 天提醒（可在详情改 1/3/7 天）。
- **交互**：订阅页切换到日历视图；提醒卡在首页出现；点击卡进入订阅详情。
- **实现**：next_charge_date = 上次扣费 + 周期（处理月末/闰年）；提醒由"守护循环"扫描生成（演示中以进入首页/定时器模拟）。
- **权限**：提醒设置 = 绿色。
- **边界**：周期不确定的标"预计"；同日多笔合并成一张卡。

#### F2.4 涨价与试用转正监测
- **效果**："XX 会员从 ¥15 涨到 ¥25"、"免费试用将于 3 天后转正扣 ¥88"。
- **交互**：以提醒卡 + 订阅详情的时间线展示；提供"接受/取消"快捷操作。
- **实现**：金额序列比对（本次 vs 上次 + 历史众数）；试用转正 = 首笔小额/0 元后 7–30 天出现全额扣费的模式。
- **权限**：绿色（监测）；取消走黄。
- **边界**：首期优惠价（"首月 X 元"）单独标注，不与涨价混淆。

#### F2.5 一键取消
- **效果**：确认详情后取消订阅，返回回执；日历移除该订阅；状态变为"已取消"。
- **交互**：订阅卡"取消"→ 确认卡（展示：商户、当前周期、取消后果【立即失效/到期失效】、下次扣费将不执行）→ 确认 → 回执。
- **实现**：Mock 取消接口（成功/需人工渠道 两分支）+ 状态机（活跃→取消中→已取消/需人工）；写审计与记忆。
- **权限**：**黄色**——赛题明确"订阅取消"为黄色操作，执行前必须展示详情并获得明确确认。
- **边界**：商户无在线取消渠道 → 降级"生成取消指引 + 到期提醒"（错误恢复演示点）；取消失败可重试 1 次后转人工。

### 板块三：扣费追回（场景 5 + 6）

#### F3.1 交易调查
- **效果**：把一笔看不懂的扣费调查清楚：商户是谁、对应哪个订阅、什么时候订的、为什么今天扣。
- **交互**：从流水/提醒卡发起 → 任务轨道逐步点亮 → 证据卡汇总。
- **实现**：交易定位 → 商户库匹配 → 订阅关联（按商户+金额）→ 证据聚合（流水、订单号、订阅记录）；每步结果写审计。
- **权限**：绿色（只读调查）。
- **边界**：商户库无记录 → 标"未识别商户"，降低置信度并告知用户，不猜测。

#### F3.2 退款政策检索与结构化
- **效果**：找到该商户的官方退款政策并展示原文出处，同时把关键条件结构化（退款窗口、是否需未使用、申请方式）。
- **交互**：判定卡上方"政策来源"可展开原文；条件项逐条列出。
- **实现**：本地政策库（演示数据，含 3–5 家商户）+ LLM 抽取为结构化条件（附原文引用）；政策缺失 → 判定返回 Uncertain。
- **权限**：绿色。
- **边界**：演示政策须标注"演示数据"；抽取结果需附原文片段，不可凭空生成条款。

#### F3.3 资格判定（规则引擎）
- **效果**：明确回答"能不能退"：Eligible / Not Eligible / Uncertain，并展示判定链（条件 → 事实 → 结论）。
- **交互**：判定卡；每个条件可展开事实来源（如"已过 4 小时 17 分"来自扣费时间戳）。
- **实现**：确定性规则引擎对"结构化条件 + 交易事实"求值；缺失信息一律 Uncertain（**绝不由 LLM 拍板**）。
- **权限**：绿色（判定只读）。
- **边界**：条件冲突/模糊 → Uncertain + 说明需要什么信息才能判定。

#### F3.4 退款材料包生成
- **效果**：自动生成完整退款申请（商户、订单号、金额、续费时间、理由、政策依据），用户零填表。
- **交互**：材料卡展示全部字段；可展开每字段来源；确认前可修改备注。
- **实现**：模板 + 调查结果填充；字段来源逐一可追溯。
- **权限**：绿色（准备）。
- **边界**：必填字段缺失 → 回到 F3.1/F3.2 补齐或降级 Uncertain。

#### F3.5 确认与提交
- **效果**：用户确认后提交退款申请，返回 Case ID 与状态。
- **交互**：确认卡（商户/金额/理由/依据/信息来源/后果【会员可能立即失效】/不确定因素/最终动作）→ 确认 →（若红色：短信+人脸 Mock）→ 提交 → 回执卡。
- **实现**：提交前过风控闸门（金额一致性、重复提交检查、幂等键 = 用户+商户+交易+日期）；Mock Refund Gateway 返回 Case ID。
- **权限**：**黄色**（金额 ≤1000）；**红色**（>1000 或变更到账账户）需强验证。
- **边界**：重复提交被幂等键拦截；闸门拦截时不进入审批队列，直接告知原因。

#### F3.6 案件跟踪与失败复盘
- **效果**：追回中心跟踪案件状态（已提交→处理中→成功/被拒）；被拒可看原因并选择复盘重试或终止。
- **交互**：案件详情时间线；被拒 → "复盘"按钮 → Agent 对比拒绝原因与原始判断，给出修正建议。
- **实现**：案件状态机 + 拒绝原因解析 + 计划修正（不无限重试：同案最多 1 次复盘提交）。
- **权限**：复盘重试 = 再次走黄/红确认。
- **边界**：终态案件归档；连续 3 次失败触发熔断锁定（见 F4.3）。

### 贯穿能力

#### F4.1 主动守护与跨场景联动（场景 6）
- **效果**：不用问，Agent 主动提醒：续费 T-3 预警、余额不足预警（联动资金建议）、异常扣费即时提醒。
- **交互**：首页提醒区 + 可选推送；提醒卡内直接给处置选项（取消/转入/换卡/忽略）。
- **实现**：守护循环（演示以"进入首页/定时器"触发）扫描：续费日历 + 余额 + 异常列表；命中阈值生成提醒卡。
- **权限**：绿色（提醒本身）；触发的动作按类型走黄/红。
- **边界**：每日提醒合并防打扰；用户可一键免打扰某类提醒（写入记忆）。

#### F4.2 对话与追问
- **效果**：口语化输入可理解；缺信息只问必要项；模糊指代给候选而不是猜。
- **交互**：右侧面板自然语言对话；超范围请求（"帮我买股票"）礼貌拒绝并给出可用范围。
- **实现**：意图识别（查询/取消/退款/设置/闲聊/超范围）+ 槽位抽取（商户/金额/时间/动作）；缺槽才追问（最多 2 问）。
- **权限**：对话不改写权限——"以后退款不用问我"这类请求会被明确拒绝并解释。
- **边界**："那个钱"类指代 → 列候选（最近 3 笔相关交易）让用户选。

#### F4.3 错误恢复与熔断
- **效果**：工具失败有明确恢复路径；连续异常触发锁定，需人工解锁。
- **交互**：失败卡片带"重试/替代路径/转人工"；熔断时全局面板提示锁定状态。
- **实现**：重试（1 次）→ 降级（如"生成指引"）→ 熔断计数（连续 3 次失败/可疑请求 → 锁定 5 分钟 + 人工确认解锁）。
- **权限**：熔断为系统级。
- **边界**：熔断不误伤正常查询（只锁执行类操作）。

#### F4.4 记忆
- **效果**：记住偏好（保留/放弃的订阅、提醒偏好、拒绝原因），下次更懂你；可查看、可清除。
- **交互**：安全中心"记忆管理"可查看/删除；关键写入（如取消原因）向用户确认。
- **实现**：沿用现有四层记忆（fact/experience/observation/mental_model）；本产品新增：订阅偏好、非订阅商户白/黑名单、案件经验。
- **权限**：绿色；敏感内容（完整订单正文）默认不长期保存。
- **边界**：用户删除后仅保留合规所需的审计摘要。

### 6.3 Agent 层（模块 2 实现）

- **意图枚举**：`query_bill`（查账单）、`manage_subscription`（管订阅）、`refund`（退款）、`set_reminder`、`chitchat`、`out_of_scope`；
- **两条黄金 DAG**：
  - 退款链：定位交易 → 识别商户 → 关联订阅 → 证据聚合 → 政策检索 → 条件抽取 → 资格判定 → 材料生成 → 【确认节点】→ 提交 → 建案；
  - 取消链：定位订阅 → 取消影响检查（到期/立即失效）→ 【确认节点】→ 执行取消 → 更新状态 → 写记忆；
- **LLM 与规则引擎分工**：LLM 只做①意图/槽位解析 ②政策文本→结构化条件 ③面向用户的解释文案；数字、判定、金额、日期全部由工具与规则引擎产出；
- **确认节点**：DAG 一等公民——命中黄/红操作自动插入确认节点，确认令牌只能由用户在 UI 上产生；
- **中断/回退**：对话面板"停止"即中断当前 DAG；"刚才那个不对"回到上一节点重算。

### 6.4 安全落地检查表

| 项 | 落点 |
|---|---|
| 权限分级 | 工具入口 `requires_tier`；取消=黄、提交退款=黄/红（§3.4 矩阵） |
| 注入防御 | 三类不可信文本（流水备注、商户名、政策文本）统一走"数据沙箱"：抽取时带标记、不拼进系统提示词、规则库白名单校验 |
| 幻觉防护 | 数字一致性校验（解释文案 vs 工具输出）；判定不落 LLM |
| 审计 | 每步：动作、工具、输入摘要、输出摘要、用户确认记录（复用现有 AuditLogger） |
| 熔断 | 连续失败计数进 Session；触发锁定+人工解锁（新增字段） |
| 幂等 | 提交退款幂等键（用户+商户+交易+日期） |
| 脱敏 | 日志/记忆不落完整订单正文 |
