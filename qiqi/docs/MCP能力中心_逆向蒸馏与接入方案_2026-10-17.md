# 业务系统逆向蒸馏为 MCP Server 能力中心 · 接入前端 Agent 平台

> 日期：2026-10-17
> 参考：B 站「人月聊IT」《业务系统逆向蒸馏为MCP Server能力中心-接入前端Agent平台》（BV1LieC6TETM，4:53）
> 说明：该视频没有公开字幕与文字简介，本文按视频标题/封面主题，结合 MCP 规范与本项目业务系统落成；不是对视频原话的逐字复述。

## 1. 一句话结论

不新造一个 Agent，而是把已有的银行 AI 业务系统**逆向建模**成一组带契约、带权限、带审计的原子能力，
用 MCP Server 统一发布；前端 Agent 平台通过 `initialize → tools/list → tools/call` 发现并调用能力，
所有资金/敏感动作只生成待确认事项，**确认权留在人审界面**。

这条链路解决的是「Agent 平台接不动业务系统」的三个老问题：

| 老问题 | 本方案的回答 |
|---|---|
| 业务系统只有页面/内部函数，Agent 不知道怎么调 | 逆向盘点 → 抽取原子能力 → JSON Schema 契约 |
| 每个 Agent 各写一套调用与风控，口径漂移 | 能力中心单一事实源，复用既有闸门与权限分级 |
| Agent 能调工具就能自批资金操作 | 不提供 `confirm` 工具；确认/强验证只在前端人审界面 |

## 2. 方法论：六步逆向蒸馏

### 第 1 步：逆向盘点业务入口

从「用户能做什么」倒推系统真实能力，而不是从数据库表出发。

本项目的盘点对象：

- 自然语言统一入口：`agent/banking/router.py#route`（六场景闭集路由）
- Web 业务服务：`web/banking_service.py`（overview / run / confirm / pending / cancel）
- 领域函数：转账、账单、卡片、订阅、跨场景各自模块
- 页面动作：`/compare` 任务台、`/team/` 工作台、`/api/scenarios/*`

盘点结果不是「12 个页面」，而是「12 项原子能力」——页面只是能力的组合视图。

### 第 2 步：能力蒸馏（UI 流程 → 原子能力）

蒸馏规则：

1. **一屏不等于一能力**：任务台页面包含查询、发起、确认、取消四种语义，必须拆开；
2. **查询与动作分离**：查询自动执行（绿），动作只入队（黄/红）；
3. **同步与异步分离**：立即转账、定时转账、AA 收款是三种状态机，不能混成一个工具；
4. **计划是结构化输出**：跨场景联动返回 DAG、子步骤、待确认项，而不是一段自然语言；
5. **保留原始入口**：`banking_scenario_run` 保留「一句话办业务」能力，避免为了结构化而丢掉业务系统原有的自然语言体验。

### 第 3 步：契约化

每项能力必须回答八个问题：

- 叫什么（稳定工具名，`banking_*` 前缀）
- 给谁看（title / description，写给模型看，不写内部黑话）
- 入参是什么（JSON Schema，含类型、枚举、范围、必填）
- 出参是什么（结构化结果 + 人类可读 message）
- 权限几级（green / yellow / red）
- 有没有副作用（`readOnlyHint` / `destructiveHint`）
- 要不要人确认（`requiresHumanConfirmation`）
- 从哪来（`source`：文件#函数，保证可追溯）

实现位置：`mcp_center/capabilities.py` 的 `Capability` 与 `CAPABILITIES` 注册表。

### 第 4 步：治理挂载（能力中心不是绕过通道）

MCP 工具调用必须复用业务系统原有防线，不能另建执行旁路：

```
tools/call
  → 能力注册表（参数校验）
  → run_scenario / 领域函数（原有注入检测、闭集路由、确定性闸门、权限分级）
  → 待确认队列（资金/敏感动作）
  → 审计 mcp_tool_call（工具、级别、结果、客户端、耗时）
  → 熔断器（锁定后动作工具直接拒绝，查询保留）
```

关键设计：**审批能力不进入工具面**。MCP 只提供：

- 查询：账户、账单、订阅、卡片、待确认队列、审计、能力目录
- 发起：转账/AA、订阅取消、卡片操作、跨场景计划、自然语言入口

不提供 `confirm` / `approve` / `verify` 工具。工具返回 `pending_ids` 与
`confirmation_endpoint=/api/scenarios/confirm`，由前端平台弹出人审界面完成确认；
红色权限还需短信 + 人脸（演示 Mock）。这样 Agent 无法「自建自批」。

### 第 5 步：发布 MCP Server

采用标准 JSON-RPC 2.0，零新增依赖（只用 Python 标准库），同时支持：

- **stdio**：`python -m mcp_center.server --stdio`，供 Claude Desktop 等本地客户端；
- **HTTP**：`POST /mcp`，供前端 Agent 平台/远程编排器；
- **发现接口**：`GET /api/mcp/manifest`、`GET /api/mcp/tools`；
- **能力中心三件套**：`tools`（可调用能力）、`resources`（只读上下文）、`prompts`（引导式流程）。

协议版本：`2025-06-18`（兼容 `2025-03-26`、`2024-11-05` 协商）。

### 第 6 步：接入前端 Agent 平台

平台侧只需三件事：

1. 启动时 `initialize` + `tools/list`，渲染能力目录（带权限徽标）；
2. 用户/模型选择能力后 `tools/call`，展示 `message` 与 `structuredContent`；
3. 若返回 `status=pending_confirmation` 或 `scheduled`，把 `pending_ids` 交给用户，
   跳转任务台确认；**不得把 pending 当作成功，也不得自动确认**。

参考实现：`web/static/mcp/index.html` + `mcp.js`（独立路由 `/mcp`，不改动已冻结的主 UI）。

## 3. 能力清单（12 项）

| 工具名 | 类型 | 权限 | 说明 | 逆向来源 |
|---|---|---|---|---|
| `banking_account_overview` | query | 绿 | 余额、卡、订阅、待确认、熔断 | `web/banking_service.py#scenario_overview` |
| `banking_bill_analyze` | query | 绿 | 月/年账单聚合、异常、Top 商户 | `agent/banking/bills.py#analyze_period` |
| `banking_subscription_list` | query | 绿 | 订阅识别、下次扣费、续费提醒 | `agent/banking/subscriptions.py#detect_subscriptions` |
| `banking_card_list` | query | 绿 | 卡片状态/额度/限额，可按尾号 | `agent/banking/cards.py#find_card` |
| `banking_pending_list` | query | 绿 | 待确认队列与定时任务 | `web/banking_service.py#pending_list` |
| `banking_audit_timeline` | query | 绿 | 最近审计事件 | `agent/risk/audit.py#AuditLogger` |
| `banking_capability_catalog` | query | 绿 | 能力目录与确认策略 | `mcp_center/capabilities.py#CAPABILITIES` |
| `banking_scenario_run` | action | 黄 | 一句话进六场景统一路由 | `agent/banking/router.py#route` |
| `banking_transfer_prepare` | action | 黄/红 | 转账、定时、AA 收款（只入队） | `agent/banking/transfers.py#handle_transfer` |
| `banking_subscription_cancel` | action | 黄 | 按商户取消订阅（只入队） | `agent/banking/subscriptions.py#find_subscription` |
| `banking_card_action` | action | 黄/红 | 查询/锁卡/解锁/额度/挂失/解挂 | `agent/banking/cards.py#handle_card_action` |
| `banking_cross_scene_plan` | plan | 黄 | 生日 → 记忆 → 锁活期 → 订花蛋糕 | `agent/banking/cross_scene.py#build_cross_scene_plan` |

说明：`banking_scenario_run` 的实际权限由内部路由决定（账单查询是绿、转账是黄/红），
工具元数据标黄是**保守上限**，不是固定权限。每个动作结果里的 `tier` 才是本次真实级别。

## 4. 一次转账的完整链路

```
Agent 平台
  │ tools/call banking_transfer_prepare {payee:"王芳", amount:500}
  ▼
MCP Server（mcp_center/server.py）
  │ 1. 参数校验（金额、收款人、预约时间）
  │ 2. 熔断检查（锁定则直接拒绝）
  │ 3. 能力 handler（mcp_center/capabilities.py）
  ▼
业务系统（原有入口）
  │ 4. 注入检测 / 闭集路由
  │ 5. 通讯录核验 + 余额 + 限额确定性闸门
  │ 6. 权限分级（≤1000 黄；>1000 红）
  │ 7. 写入待确认队列（不扣款）
  ▼
返回 {status:"pending_confirmation", tier:"yellow", pending_ids:["p_..."]}
  │
  ▼
前端人审界面（/compare 任务台）
  │ 8. 展示操作详情
  │ 9. 黄色：用户确认；红色：短信 + 人脸强验证
  │ 10. 复核闸门通过后执行（演示模拟扣款）
  ▼
审计：mcp_tool_call（调用）+ banking_action_executed（执行）
```

## 5. 安全边界与对抗性设计

| 风险 | 处理 |
|---|---|
| Agent 自建自批 | 不暴露 confirm/approve 工具；确认只在前端人审接口 |
| 提示词注入绕过风控 | 复用 `router.route` 的注入检测与权限绕过正则；命中即熔断计数与审计 |
| 工具描述投毒 | 工具描述只来自本地静态注册表，不抓取远程内容；`source` 可追溯 |
| 参数走私 | JSON Schema + handler 二次校验（类型/范围/枚举/长度） |
| 越权卡片/账户 | 复用原有确定性闸门（余额、通讯录、限额、卡片状态） |
| 熔断期间继续操作 | 动作/计划工具在 `breaker.is_locked()` 时直接 `isError`；查询保留 |
| 审计缺失 | 每次 `tools/call` 写 `mcp_tool_call`；审计失败不改变业务结果，但会记录异常 |
| 把演示数据当真实数据 | 所有响应带 `provenance.source=demo_fixture` 与 `simulation_notice` |
| 重放/重复请求 | 复用待确认队列的 request_key 去重；返回 `deduplicated` |

**不做的三件事**（避免过度承诺）：

1. 不做 Agent 自主确认，即使模型声称「用户已同意」；
2. 不在 MCP 层直接改卡片/扣款，所有副作用回到业务系统入口；
3. 不把 `/api/scenarios/confirm` 包装成 MCP 工具。

## 6. 运行与接入

### 6.1 启动 Web（含 MCP HTTP）

```bash
python web/app.py --port 8765
# 打开 http://127.0.0.1:8765/mcp
```

新增路由：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/mcp` | MCP 能力中心控制台 |
| POST | `/mcp` | JSON-RPC 2.0（单条/批量） |
| GET | `/api/mcp/manifest` | 能力清单 + 确认策略 + 逆向映射 |
| GET | `/api/mcp/tools` | `tools/list` 的 HTTP 便捷入口 |

### 6.2 stdio（Claude Desktop 等）

```bash
python -m mcp_center.server --stdio
python -m mcp_center.server --manifest   # 打印能力清单
```

客户端配置示例：

```json
{
  "mcpServers": {
    "finance-lab": {
      "command": "python",
      "args": ["-m", "mcp_center.server"],
      "cwd": "D:/黑客松大赛冲刺版"
    }
  }
}
```

### 6.3 HTTP 调用示例

```bash
curl -s http://127.0.0.1:8765/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

```bash
curl -s http://127.0.0.1:8765/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{
        "name":"banking_transfer_prepare",
        "arguments":{"payee":"王芳","amount":500,"memo":"聚餐"},
        "_meta":{"clientInfo":{"name":"demo-agent","version":"1.0"}}}}'
```

返回关键字段：

```json
{
  "status": "pending_confirmation",
  "tier": "yellow",
  "pending_ids": ["p_..."],
  "next_action": "human_confirmation_required",
  "confirmation_endpoint": "/api/scenarios/confirm",
  "confirmation_policy": "确认/强验证只能由前端平台的人审界面发起；MCP 不提供 confirm 工具。"
}
```

### 6.4 前端 Agent 平台接入要点

- 渲染能力目录时读取 `_meta.tier` 与 `_meta.requiresHumanConfirmation`；
- `readOnlyHint=true` 的能力可以直接展示结果；
- 动作类结果必须区分「已创建待确认」与「已执行」，前者不能显示成功；
- 将 `pending_ids` 传给任务台，确认后再刷新账户总览；
- 记录 `_meta.clientInfo`，便于审计归因（HTTP 无会话，客户端可每次携带）。

## 8. 与赛题/答辩的对应叙事

- **不是新做一套系统**：能力中心是既有六场景安全体系的外化层，复用同一套闸门、权限、审计与熔断；
- **不是让 Agent 接管资金**：Agent 只能发起与查询，确认权在人；
- **不是演示壳**：MCP 是标准协议，Claude Desktop / 任意 MCP 客户端可直接连；
- **平台化故事**：银行把内部业务能力发布为能力中心，外部 Agent 平台按权限消费，
  这比「再做一个聊天框」更接近企业真实落地路径。

答辩一句话：

> 我们把银行已有的六场景业务系统逆向蒸馏成 12 个 MCP 能力，查询自动执行、
> 资金动作只入队；Agent 平台通过标准协议发现和调用，但永远拿不到确认权。

## 9. 已知边界与下一步

当前边界（如实说明）：

- 演示数据，不连接真实银行核心；外部订花/蛋糕为 Mock；
- HTTP 传输为无状态单次请求，未实现 SSE 流式与服务端会话绑定；
- 未接 OAuth / mTLS / 租户隔离，生产化需补认证、限流、工具级 allowlist；
- `banking_scenario_run` 的自然语言解析仍是规则 + 既有路由，不额外调用大模型。

下一步（按优先级）：

1. 给团队前端 Agent 平台提供 `manifest` 消费者与待确认回调；
2. 增加 HTTP 会话与 `Mcp-Session-Id`，支持 SSE；
3. 工具级 RBAC：不同 Agent 只看到被授权的工具子集；
4. 能力版本化：`banking_transfer_prepare.v2` 与弃用策略；
5. 用 OpenAPI/内部接口清单批量导入，形成可复用的「逆向蒸馏流水线」。
