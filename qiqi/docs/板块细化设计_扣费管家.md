## 1. 全局约定

### 1.1 布局与导航

沿用你们已有的双栏外壳（左"手机银行"、右"Agent 面板"）：

```
┌──────────────── 左：手机银行（约 62%） ────────────────┐ ┌──── 右：Agent 面板（约 38%） ────┐
│  顶栏：问候 + 数据日期 + 🔔提醒 + 安全中心             │ │  对话区（消息气泡 + 卡片流）      │
│  ┌─────────────────────────────────────────────────┐  │ │                                  │
│  │  当前页面内容（首页 / 账单 / 订阅 / 追回）          │  │ │  任务轨道（DAG 节点逐一点亮）      │
│  └─────────────────────────────────────────────────┘  │ │                                  │
│  底部导航：首页 · 账单 · 订阅 · 追回 · 我的             │ │  输入区（文本框 + 快捷短语 + 打断） │
└────────────────────────────────────────────────────────┘ └──────────────────────────────────┘
```

- 左侧负责"看数据、点操作"，右侧负责"对话、推理过程、卡片交互"；
- 任何左屏元素（一笔流水、一个订阅、一个案件）都可以"带入对话"：点击 → 右侧输入框上方出现上下文芯片（如 `[¥398 · XX AI 软件]`），用户直接说话；
- 资金操作的确认与强验证只发生在右侧卡片里；左侧只做状态更新。

### 1.2 五条开发铁律

1. **数字唯一来源**：界面与文案中的所有数值来自工具输出；LLM 只写解释文案，且文案中的数字要做一致性校验（提取数字与工具结果比对，不一致则中止并降级为模板文案）。
2. **卡片是唯一交互单元**：右侧面板以"卡片流"推进（证据 → 判定 → 材料 → 确认 → 回执 → 审计），每张卡有固定的字段与状态。
3. **资金动作三件套**：确认卡 → 确认令牌（ConfirmToken）→ 工具层校验。令牌只能由用户在 UI 上产生，一次性、5 分钟过期；工具入口校验不通过直接拒绝执行。
4. **不可信文本只作数据**：流水备注、商户名、政策原文三类文本进入 LLM 前打标记（`<data>`），不得拼入系统指令区；从中抽取的任何规则要过"条件白名单"校验。
5. **每页四态**：任何页面/卡片都要实现 加载（骨架）→ 正常 → 空态 → 错误（含熔断锁定态）。演示数据统一标注"演示数据"角标。

### 1.3 通用组件清单

| 组件 | 出现位置 | 关键字段 | 主要状态 |
|---|---|---|---|
| 提醒卡 Alert | 首页、铃铛 | 类型图标、标题、详情、"处置选项"按钮组、忽略 | 未读 / 已读 / 已忽略 / 已处置 |
| 证据卡 | 追回调查、订阅详情 | 商户、订阅名、周期、金额、扣费时间、来源列表（带类型图标） | 收集完成 / 部分缺失 |
| 判定卡 | 追回 | 条件行表（条件/要求/事实/结果）、结论徽章、不确定项、政策来源 | 通过 / 不通过 / 不确定 |
| 材料卡 | 追回提交前 | 字段清单（每字段带来源与是否可改）、退款理由 | 完整 / 缺字段 |
| 确认卡 | 黄/红操作 | 操作详情、金额、后果、不确定因素、勾选框、确认/取消 | 待确认 / 已确认 / 已取消 / 超时 |
| 强验证层 | 红色操作 | 短信码输入、人脸 Mock（长按 2s） | 未验证 / 验证中 / 通过 / 失败 |
| 回执卡 | 执行后 | Case ID / 操作编号、状态、时间、幂等键、后续步骤 | 成功 / 处理中 / 失败 |
| 审计行 | 安全中心 | 时间、动作、工具、输入输出摘要、结果 | 可展开原始 JSON |
| 任务轨道 | Agent 面板 | 节点名、状态（待执行/进行中/完成/失败/跳过） | 随 DAG 实时更新 |

### 1.4 金额与颜色规范

- 支出 `-¥398.00`（深色），收入 `+¥18,000.00`（深色加粗）；本产品不采用股市"红涨绿跌"语义；
- 风险/异常 = 红；通过/确认 = 绿；进行中 = 蓝；禁用 = 灰；
- 金额一律两位小数、千分位；日期 `YYYY-MM-DD`，时间 `HH:MM`。

### 1.5 全局异常与熔断

| 状态 | 表现 | 恢复路径 |
|---|---|---|
| 工具失败 | 卡片内红字"该项数据暂不可用（原因）" | 「重试」按钮 → 仍失败则「替代路径／转人工」 |
| 连续失败 ≥3 次 | 全局面板顶部横幅"已暂停执行类操作（5 分钟）"，执行类按钮禁用 | 等待倒计时 或 安全中心「人工解锁」按钮 |
| LLM 失败 | 对话区提示"我先用规则模式继续"，流程不中断 | 自动降级 |
| 会话超时 | 30 分钟无操作清空对话上下文（长期记忆保留） | 重新提问 |

### 2.2 流水详情抽屉（A-3）

展开后展示字段：商户（归一化名 + 原始名）、金额、时间、分类、渠道、备注、关联订阅（如有，可跳转）、是否异常（如异常附原因）。

操作按钮（点击后带入右侧对话，附上下文芯片）：
- 「这笔是什么」 → 触发交易调查（C1 前置）
- 「能退吗」 → 直接进入追回流程（C1）
- 「这是订阅吗」 → 触发订阅识别确认（B1 的待确认项）

### 2.3 月报弹层（A-2）

生成内容（全部字段来自工具，LLM 仅写两句总结）：

| 区块 | 内容 |
|---|---|
| 概览 | 本月总支出、环比、较上月差额 |
| 订阅 | 订阅支出合计、活跃订阅数、本月新增/取消 |
| TOP3 | 最大三笔支出（商户、金额、日期） |
| 异常 | 异常笔数与总览（可跳转账单页异常区） |
| 总结 | 两句话：本月钱花在哪、一个提醒 |

生成过程在右侧面板显示三步任务轨道：统计 → 分析 → 撰写；约 2 秒内完成。
**降级**：LLM 失败 → 直接输出纯数字模板（去掉总结段的润色）。
**校验**：总结文案中的每个数字与工具输出比对，任一不一致 → 用模板文案替换该句并记录告警。

### 2.4 功能细化

**A1 消费分类统计（对应 F1.1）**

- 效果：环形图 + 分类列表 + 环比；点击下钻。
- 交互：默认本月；切月重算；分类点击筛选。
- 实现：分类引擎 =「商户归一化映射表 + 关键词规则表」，规则优先级：订阅商户库 > 精确商户映射 > 关键词 > 默认"其他"。
  初始规则表（写在 `agent/tools/billing.py`，可扩展）：

| 分类 | 命中规则示例 |
|---|---|
| 餐饮 | 美团外卖、饿了么、肯德基… |
| 交通 | 滴滴、高德、12306、加油… |
| 购物 | 淘宝、京东、拼多多… |
| 订阅 | 商户表 `is_subscription=true` 的商户 |
| 转账 | 渠道=转账 或 备注含"转账/还款" |
| 其他 | 兜底 |

- 权限：绿。
- 边界：单月"其他"占比 >20% 时，分类卡下方提示"有 X 笔未归类，可点击修正"（点击可选分类，修正写入记忆，下次同商户自动归类）。
- 验收：演示数据集上分类覆盖率 ≥90%，"其他"占比 <15%。

**A2 月报生成（对应 F1.2）**

- 交互细节：点击 → 右侧任务轨道三步 → 弹层内容渐显 → 可「保存长图」（P1，不做也不影响）。
- 实现：`get_monthly_report(month)` 一次返回全部数值；LLM prompt 只允许引用返回的数字。
- 边界：无数据月份禁用按钮；文案数字校验失败降级（见上）。

**A3 异常交易识别（对应 F1.3）**

规则表（`detect_anomalies(period)`，阈值可配置）：

| 类型 | 触发条件 | 输出标签 | 误报防护 |
|---|---|---|---|
| 重复扣款 | 同商户 + 同金额，24h 内 ≥2 笔 | "重复扣款" | 排除订阅正常周期扣费 |
| 金额跳变 | 较该商户历史均值上下 >30%，且历史 ≥3 笔 | "金额跳变" | 排除首期优惠价 |
| 陌生商户 | 首次出现且金额 >200 元 | "陌生商户" | 近 90 天未出现才算"首次" |
| 深夜扣费 | 23:00–06:00 且金额 >100 元 | "深夜扣费" | 订阅已知扣费时段豁免 |
| 试用转正 | 首笔 ≤10 元后 7–30 天内出现 ≥50 元扣费 | "试用转正" | 同一商户仅报一次 |

- 每条异常输出：类型、原因一句话、对照数据（历史笔数/均值/前一笔时间）、建议动作。
- 交互：异常卡片「查看」→ 展开对照数据；「问Agent」→ 带入右侧（默认问句"这笔怎么回事"）。
- 权限：绿（识别本身）。
- 验收：演示数据集 5 类异常全部命中、0 误报（数据集中预埋反例：正常周期订阅、首期优惠价不报）。

**A4 流水搜索与问答（对应 F1.4）**

- 交互：搜索框直接搜 或 对话说"上个月 200 多那笔"。
- 实现：LLM 把自然语言解析为结构化查询参数 `{amount_range, date_range, merchant_kw, category}` → 调 `list_transactions`；结果 1 条 → 直接展开；多条 → 候选卡列表。
- 边界：0 条 → "没找到，要不要放宽条件？"并给出放宽建议。
- 验收：5 条自然语言查询示例（见第 8 章）全部正确定位。

## 3. 板块 B：订阅管家

**定位**：管住每一笔续费。查询绿色、取消黄色。
**页面**：B-1 订阅页（列表/日历双视图）｜ B-2 订阅详情 ｜ B-3 取消确认流程

### 3.1 订阅页布局

```
┌─────────────────────────────────────────────────────┐
│ [全部|活跃|待确认|已取消]            [列表|日历]       │
│ 本月订阅 ¥1,286 · 活跃 6 个 · 7 天内将续费 2 个        │
├─────────────────────────────────────────────────────┤
│ 🤖 XX AI 软件    年付 ¥398  下次 2027-09-28   [详情]  │
│    剩 362 天 · 已确认          [提醒3天] [取消]        │
│ 🎬 XX 视频       月付 ¥25   下次 10-05  ⚠涨价 [详情]   │
│    剩 5 天（原 ¥19）           [提醒3天] [取消]        │
│ ❓ XX 健身         季付 ¥298  待确认                   │
│    疑似订阅（仅 2 次扣费）      [是订阅] [不是]         │
│ ✅ XX 音乐        月付 ¥11   下次 10-12       [详情]   │
└─────────────────────────────────────────────────────┘
```

日历视图：未来 30 天时间轴，按日分组，同日多笔合并为一张卡（"10-05：XX视频 ¥25、XX阅读 ¥18 合计 ¥43"）。

### 3.2 订阅识别算法（B1，对应 F2.1）

```
detect_subscriptions():
  对每个商户（归一化后）取全部扣费序列 charges：
    1. 若商户表 is_subscription=true 且 ≥1 笔 → 置信度「已确认」（首扣即识别）
    2. 计算相邻间隔的中位数 median_gap：
       median_gap ∈ {7±2, 30±3, 31±3, 91±5, 365±10} 天
       且 金额波动 ≤5% 且 笔数 ≥3 → 置信度「已确认」
       笔数 == 2 且周期匹配 → 置信度「疑似」
    3. 其余 → 不识别
  输出 Subscription{cycle, amount, next_charge_date, confidence}
```

- 用户否认（点"不是"）→ 写入记忆（该商户非订阅），并加入白名单不再提示；
- 用户确认（点"是订阅"）→ 升级"已确认"并补全周期信息；
- 周期无法确定（如年付单笔）→ 只在商户库命中时识别，否则不打扰。
- 边界：同一商户多个订阅（如家庭组）→ 同金额系列各成一档，分开展示。
- 验收：数据集内 6 个订阅 5 个"已确认"、1 个"疑似"；用户否认后不再出现。

### 3.3 续费日历与提醒（B3，对应 F2.3）

- `next_charge_date = 上次扣费日 + 周期`；月末边界：1-31 起算的月付在 2 月顺延至 28/29 日；闰年 2-29 顺延至 3-1（写出单元测试）。
- 周期不确定的订阅：日期前加"预计"。
- 提醒档位：1 / 3 / 7 天（默认 3）；修改即生效并写审计。
- 提醒触发（演示中由"进入首页"与定时器模拟守护循环）：生成 RENEWAL_UPCOMING 提醒卡 → 首页提醒区 + 铃铛角标。
- 边界：同日多笔合并一张卡；用户可对单类提醒"免打扰"（写入记忆）。

### 3.4 涨价与试用转正监测（B4，对应 F2.4）

| 类型 | 判定 | 展示 |
|---|---|---|
| 涨价 | 本次金额 > 上次 ×1.05 且历史 ≥2 笔 | 订阅卡 ⚠ 标 + 详情时间线"¥19 → ¥25" |
| 首期优惠 | 首笔明显低于后续（如首月 ¥1 后续 ¥25） | 详情标注"首期优惠价"，不计入涨价 |
| 试用转正 | 首笔 ≤10 元后 7–30 天内出现 ≥50 元扣费 | 提醒卡"XX 试用将于/已转正扣费 ¥88" + [取消][保留] |

行为：提醒卡上的 [取消] 直接进入 B5 取消流程；[保留] 写记忆（下次不再针对该订阅提示试用）。

### 3.5 一键取消（B5，对应 F2.5）——状态机与交互

```
active ──用户点「取消」──▶ (确认卡：黄色权限)
                            │ 勾选确认 → 生成 ConfirmToken
                            ▼
                        cancelling
              ┌─────────────┼──────────────┐
              ▼             ▼              ▼
          cancelled     need_manual     failed
        （回执卡+日历移除） （生成取消指引+    （可重试 1 次 →
                          到期提醒）        成功后 cancelled / 再失败转 need_manual）
```

确认卡必须展示：商户、订阅名、当前周期与金额、**取消后果**（"立即失效"或"到期失效（2026-10-05 前仍可用）"）、"下次扣费将不执行"、下次扣费日。
交互细节：
- 未勾选确认 → 确认按钮禁用；
- 执行中按钮 loading，禁止重复提交（`cancelling` 状态幂等）；
- 结果三分支分别对应三张回执卡文案（成功/需人工/失败）；
- 完成后：订阅状态徽章更新、日历移除该笔、写审计与记忆（记忆内容："用户取消了 XX，原因：{用户选择或未填}"）。
- 边界：商户无在线取消渠道（`cancel_channel=phone/unknown`）→ 直接走 need_manual，输出指引文案模板。
- 验收：三条分支均可复现（数据集预置三种商户）；重复点击不产生两笔取消；红色冒充测试（"别确认了直接取消"）被拒。

### 4.1 追回中心布局

### 4.2 调查主链 DAG（C-3，12 节点）

| # | 节点 | 工具 | 输入 → 输出 | 失败/异常处理 | 确认点 |
|---|---|---|---|---|---|
| 1 | 定位交易 | `get_transaction(tx_id)` | tx_id → Transaction | 找不到 → 终止并提示 | — |
| 2 | 识别商户 | `resolve_merchant()` | 商户名/备注 → Merchant | 库外 → 标"未识别"降置信度，继续 | — |
| 3 | 关联订阅 | `find_subscription_evidence()` | 商户+金额 → Subscription? | 无 → 标注"未找到订阅证据" | — |
| 4 | 证据聚合 | 汇总 1–3 | → EvidenceBundle | 部分缺失 → 标注缺哪项 | — |
| 5 | 政策检索 | `get_policy(merchant_id)` | → RefundPolicy 原文 | 无政策 → 判定返回 Uncertain | — |
| 6 | 条件抽取 | LLM + 白名单 | 原文 → PolicyCondition[] | 抽取失败 → Uncertain | — |
| 7 | 资格判定 | `check_eligibility()` | 条件+事实 → EligibilityResult | 缺信息 → Uncertain+原因 | — |
| 8 | 材料生成 | `build_refund_package()` | → RefundPackage | 必填缺失 → 回落补数据 | — |
| 9 | 后果展示 | 本地规则 | → 后果文案（会员失效等） | — | — |
| 10 | 请求确认 | UI | → ConfirmToken | 超时 5 分钟作废 | ✅ 黄色 |
| 11 | 提交 | `submit_refund()` | 包+令牌+幂等键 → 回执 | 幂等拦截/闸门拦截 → 告知原因 | （红色先强验证） |
| 12 | 建案跟踪 | `create_case()` | → RefundCase + 回执卡 | — | — |

任务轨道把 1–12 显示为节点序列（6/7 合并显示为"核验规则"、10 显示为"等待确认"）。

### 4.5 案件跟踪与复盘（C-6/对应 F3.6）

- 案件详情 = 垂直时间线（发现→调查→判定→材料→确认→提交→状态更新），每步可展开；

- 连续 3 次失败（跨案件）→ 熔断（见 1.5）。

class SubscriptionStatus(Enum):
    ACTIVE = "active"            # 活跃
    SUSPECTED = "suspected"      # 疑似（待确认）
    CANCELLING = "cancelling"    # 取消中
    CANCELLED = "cancelled"      # 已取消
    NEED_MANUAL = "need_manual"  # 需人工渠道
    FAILED = "failed"            # 取消失败

class EligibilityVerdict(Enum):
    ELIGIBLE = "eligible"
    NOT_ELIGIBLE = "not_eligible"
    UNCERTAIN = "uncertain"

class CaseStatus(Enum):
    DRAFT = "draft"
    AWAITING_CONFIRMATION = "awaiting_confirmation"
    SUBMITTED = "submitted"
    PROCESSING = "processing"
    APPROVED = "approved"
    REJECTED = "rejected"
    FAILED = "failed"

@dataclass
class Transaction:
    tx_id: str
    date: str                    # YYYY-MM-DD
    time: str                    # HH:MM
    merchant_name: str           # 原始商户名（不可信文本）
    merchant_id: str = ""        # 归一化后（未识别为空）
    amount: float = 0.0          # 正=收入 负=支出
    direction: str = "debit"     # debit / credit
    category: str = "其他"
    memo: str = ""               # 备注（不可信文本）
    channel: str = ""            # 卡/账户标识
    subscription_id: str = ""    # 关联订阅（如有）
    scenario: str = ""           # 数据集标注（测试用）

@dataclass
class Merchant:
    merchant_id: str
    name: str                    # 归一化名
    aliases: list[str] = field(default_factory=list)
    category: str = "其他"
    is_subscription: bool = False
    cancel_channel: str = "unknown"   # in_app / website / phone / unknown
    policy_id: str = ""

@dataclass
class Subscription:
    sub_id: str
    merchant_id: str
    name: str
    amount: float                     # 最近一次金额
    cycle: str = "monthly"            # monthly / quarterly / yearly / weekly
    last_charge_date: str = ""
    next_charge_date: str = ""
    status: SubscriptionStatus = SubscriptionStatus.SUSPECTED
    confidence: str = "suspected"     # confirmed / suspected
    charge_history: list[dict] = field(default_factory=list)  # [{date, amount}]
    cancel_effect: str = "end_of_period"  # immediate / end_of_period
    reminder_lead_days: int = 3

@dataclass
class PolicyCondition:
    key: str          # 白名单：refund_window_hours / unused_required / apply_channel / renewal_type
    label: str        # 人话文案
    op: str = "<="    # >= / <= / == / in
    value: object = None
    source_span: str = ""   # 原文引用片段（必须非空）

@dataclass
class RefundPolicy:
    policy_id: str
    merchant_id: str
    title: str
    raw_text: str = ""        # 原文（不可信文本）
    source_url: str = ""
    conditions: list[PolicyCondition] = field(default_factory=list)
    updated_at: str = ""

@dataclass
class EligibilityRow:
    condition: str
    requirement: str
    fact: str
    fact_source: str          # 事实来源：tx / subscription / usage
    passed: Optional[bool] = None   # None = 不确定

@dataclass
class EligibilityResult:
    tx_id: str
    policy_id: str
    verdict: EligibilityVerdict = EligibilityVerdict.UNCERTAIN

    missing: list[str] = field(default_factory=list)   # uncertain 时缺什么

@dataclass

```json
{
  "tx_id": "TX-20260930-0912",
  "policy_id": "POL-AISOFT",
  "verdict": "eligible",
  "rows": [
    {"condition": "退款窗口", "requirement": "≤24 小时", "fact": "已过 4 小时 17 分", "fact_source": "tx", "passed": true},
    {"condition": "未使用服务", "requirement": "未使用", "fact": "未检测到登录记录", "fact_source": "usage", "passed": true}
  ],
  "missing": []
}
```

**权限在工具层强制**：`requires_tier` 装饰器校验令牌（动作匹配、未过期、未使用、red 需 strong_verified），不通过抛 `PermissionDenied`——对话与提示词无法绕过。

## 11. 创新增强包（2026-09-30 追加）

> 背景：创新分（30%）中，只有「场景新颖性」一项靠品类；本品类对标已存在——订阅识别/取消对标 Rocket Money（美）与支付宝、微信的自动续费管理；退款代办与队友《RenewalResolve》重叠。本章给出 4 个可演示、低成本的差异化钩子 + 1 组可选项，作为答辩与材料中的创新主叙事。评分对应：场景新颖性（11.1/11.2/11.3）、安全演示化（11.4）；交互体验其余 5 项由 W1–W2 意图/规划工程承载。

### 11.1 价值审计（Value Audit）——「不是管理扣费，是审计价值」

一句话：把「扣了多少钱」升级为「这钱花得值不值」，用使用证据回答。**对标核查（2026-09-30 GitHub 实测）**：追踪类产品（Wallos 等 8k★ 级）只记录不判断；最接近的 Agent 项目 Moxie 检测僵尸订阅仅凭扣费节奏，代码文案自称 "cancel if unused"（即"闲置"靠猜），无使用数据——本钩子为空白，见 v1 文档 §3.4。

- 新增数据：`usage_records`（演示数据；真实路径：用户授权导入系统屏幕时间报告或手动标记，**待验证**）
- 价值公式（确定性计算）：`单次使用成本 = 周期费用 ÷ 周期内使用次数`；评级阈值 <¥5 值得 / ¥5–20 边缘 / >¥20 浪费（可配置）
- 新组件 **价值审计卡**：订阅名｜年费｜近 90 天使用次数｜单次使用成本｜评级｜建议（保留/降级/取消）
- 交互：订阅详情加「价值」页签；月报加「浪费榜」区块（"年浪费 ¥X，Top2：…"）；守护循环新增提醒类型 **闲置扣费预警**（"你 98 天没用过 XX，下周将扣费 ¥298"）
- 权限：绿；建议取消时衔接 B5 取消流
- 演示钩子：¥298 健身 App、90 天使用 2 次 → 单次成本 ¥149 →「浪费」→ 一键取消

### 11.2 取消效果验证环（Cancel Verification）——「取消不是终点，停了才算」

- 问题：取消后仍被扣费是真实高频场景；竞品都止步于「提交取消」（Moxie 的 "verify" 指校验审计日志哈希链，非取消生效验证；JerryNee 的 dispute skill 把该场景当已有问题输入，不做主动监控——2026-09-30 核查确认空白）
- 机制：取消成功 → 建验证任务 → 原下次扣费日 +2 天检查该商户是否仍有扣费 → 无 → 静默（verified_ok）；有 → `breach_found` → **自动生成争议案件**（证据 = 取消回执 + 新扣费记录）→ 提醒卡"已为你准备好争议材料" → 用户黄确认提交
- 状态：`verification_pending / verified_ok / breach_found → escalated`
- 演示：数据集预置 1 个「取消失败仍扣费」商户，可现场走升级流程
- 创新叙事：单次工具做不到的**常驻看护**——"别人帮你取消，我们盯到真的停"

### 11.3 合规守护叙事（银行侧价值）——含已核实法规依据

- **已核实**：《中华人民共和国消费者权益保护法实施条例》（国务院令第 778 号，2024-07-01 施行）第十条第二款：**"经营者采取自动展期、自动续费等方式提供服务的，应当在消费者接受服务前和自动展期、自动续费日期前，以显著方式提请消费者注意。"**
  一手来源：https://www.gov.cn/zhengce/zhengceku/202403/content_6940159.htm
- 准确表述：义务主体是**商户**；银行侧做「续费前显著提醒 + 争议一站式处理」= 帮用户行使权利、从源头减少代扣类投诉——对银行评委（消保/投诉是日常 KPI）直击价值
- 附带用法：争议材料中把「商户是否履行显著提醒义务」列为举证点/谈判理由（演示文案，不承诺结论）
- 落地：提醒卡脚注（演示版）；技术文档加「合规对齐」一节

### 11.4 「你可以现场攻击」演示模式

- 位置：安全中心「攻击演示」按钮组：8 条预设攻击（v1 文档 §7.2）一键注入、可连续演示；另备自由输入框供评委手打
- 行为：注入 → 拒答卡 + 审计行高亮 → 一键重置可重复
- 目的：把安全 30 分从"我们声称安全"变成"评委亲眼看到拦得住"
