## 三、原站与赛题的关键冲突（按三层拆分）

A. 视觉设计层：优秀，无需推翻。唯一问题是品牌名 "FINANCE LAB / 双场景" 的文案叙事。
B. 业务场景层（核心冲突）：
- 原站是 "TWO SCENARIOS"：个人投资顾问 + 店主财务助手。赛题是「AI 代人操作银行（安全 + 体验）」，团队已锁定产品为**安全银行任务执行台**（方案 A，见《产品重审与竞赛评审报告_2026-10-12.md》）。
- 「店主财务助手」（巷口咖啡、应收应付、采购分析、现金日历）是**小店经营场景，不是银行个人业务**，与赛题错位最严重；但"看懂账单→现金安排→成本解释"这套核对式交互可复用到账单/订阅场景。
- 「个人投资顾问」（持仓健康检查+三方案模拟）对应六场景中的**理财深度路径**，可保留为主线的深度业务模块，但原站把它当两个并列主角之一，需要降级叙事。
- 原站完全没有赛题要求的核心场景：转账（黄）、卡片挂失（红）、订阅代扣、跨场景联动、注入拦截与熔断的可见演示。
C. 数据可信度层：
- versions/api.js 在浏览器内拦截 window.fetch，内置 harness 模拟智能体四阶段（VALIDATE_INPUT→DIAGNOSE→GENERATE_CANDIDATES→SIMULATE），固定种子模拟、固定日期（2026-09-23）与固定价格；merchant 是"巷口咖啡"虚构账单（金额单位分）。
- 没有任何真实后端；页面上的"AI 诊断"是浏览器里的 JS 工厂函数。
- 优点是它**已经很诚实**（多处"虚构演示"标签）；缺点是没有任何环节在真正执行赛题要的安全机制（权限分级、注入防御、审计、熔断）。

## 五、数据与交互改造路径

1. 单一接缝：两个工作台的页面只通过 `api("/api/...")` 取数，全部走 versions/api.js 的 fetch 拦截层。改造 = 把 harness 替换为真实 HTTP 客户端，指向团队后端（web/app.py，本机 127.0.0.1:8765 / 内网 172.27.253.10）。
2. 接口映射：投资页 `/api/health-check/run`→后端 `/api/review`（自然语言理财体检）+`/api/decide`（纸交易确认）+`/api/audit`（审计）；merchant 页对应账单/订阅场景 `/api/scenarios/run`、`/api/scenarios/confirm`、`/api/scenarios/pending`；新建主工作台直接消费六场景接口（boot/run/confirm/cancel/pending/breaker_reset）。
3. 保留静态演示版：原 GitHub Pages 无后端可调，作为「设计展示/门面」保留；改造后的接真版本放进团队 web/static（由 web/app.py 同源服务，无 CORS 问题），作为比赛演示入口。两条轨道不互相删除。
4. 演示数据的诚实标注：后端本身是 demo fixture + 模拟执行（source=demo），UI 上每个资金动作旁固定显示"演示模拟 · 未发生真实资金转移"+ 数据日期（as_of）+ 来源（source），与团队 P0 计划一致。
5. 明确不做：不假装真实银行、不接真实短信/人脸、不接外部下单；LLM 只解释结构化结果，金额/余额/权限由 Python 闸门决定。
