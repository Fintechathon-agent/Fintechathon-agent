# 创新方案自我否决机制 · 完整记录

> 2026-10-12 ｜ 七七（Data / Web 用户端）｜ 依据：赛题原文（data/contest/赛题要求.txt）、
> 现有代码与测试的真实状态、黑盒实测结果。
>
> 本文档回答三件事：**我们否定了哪些方案、为什么；哪些假设有证据、哪些没有；
> 最终方案经得起怎样的反例。** 所有「已落地」的结论都已转化为代码与测试，
> 不是文案。

## 〇、结论先行

现有方案（六场景全覆盖 + 理财深度路径 + 统一安全防线）**在否决压力下存活**，
但黑盒验证暴露了它最脆弱的假设：**关键词路由扛不住真实用户的语言**——
16 句最自然的用户表达有 6 句失败（37.5%）。这不是文案问题，是演示事故级风险。
本轮把 6 句失败全部修复并固化为 18 个回归测试，同时补齐理财场景与赛题表的
两处对齐缺口（申购/赎回动词、额度调整确认链路丢参 bug）。

**没有新增任何"听起来创新"的功能。** 本轮的全部产出是：让现有承诺在真实
用户语言下站得住。

## 一、第一步：真正不同的候选方案（6 个）

| 方案 | 定位 | 与现状的关系 |
|---|---|---|
| A | 六场景全覆盖 + 理财深度路径 + 统一安全防线（确定性路由 + 闸门 + 绿黄红 + 五层记忆 + 审计熔断） | **现状方案** |
| B | 单场景做深：只做理财操作的完整可信闭环 | 早期被放弃过的方案 |
| C | LLM 自由对话全功能银行助手（Revolut AIR 风格，function calling 到模拟银行 API） | 全新 |
| D | 安全中台：把闸门/审计/熔断/注入防御做成可插拔中间件 + 攻击评测套件 | 全新 |
| E | 记忆驱动个人财务管家：Hindsight 记忆为核心卖点，场景少而精 | 全新 |
| F | 六场景全覆盖，但意图解析与槽位抽取交给 LLM（关键词只做安全兜底） | A 的变体 |

## 二、第二步：每个方案最强的反对理由

- **A**：「这不就是把银行 App 的功能加了个正则路由吗？AI 在哪？」——且黑盒实测
  证明关键词路由对真实语言脆弱（37.5% 误路由），现场评委随口一句话就可能翻车。
- **B**：赛题明确「至少 3 个场景（鼓励全覆盖）」，任务完成率占 40%；单场景上限
  就是丢分。而且「深度」叙事此前已被团队否过一次。
- **C**：注入防御、幻觉防护是赛题 30% 安全权重，LLM 自由对话几乎不可能在演示
  现场保证不翻车；demo 默认无 LLM key，方案直接不可运行；演示不可控 = 答辩灾难。
- **D**：评委看到的是框架不是产品，任务完成率维度（40%）无从打分；
  「不需要 AI」的质疑在这里最尖锐——规则引擎本来就不需要 LLM。
- **E**：记忆的卖点是「越用越懂用户并改变决策」，但记忆→决策的机制化联动至今
  只有路线图没有证据（见第九节未验证清单）；场景覆盖也不足。
- **F**：无 key 环境不可用；现场网络/配额风险；成本高。但它的启示被吸收：
  解析分层 + 必要追问机制（见第七步）。

## 五、第五步：更简单、更可靠、更有价值的替代方式检查

- **场景卡片 + 表单化输入**比自然语言可靠得多，但赛题第一句就是"说话就能办业务"，
  放弃 NL 等于放弃赛题。**否决**，保留 NL。
- **每个场景的确定性闸门**是否可以用 LLM 校验替代？不能——安全 30% 权重下，
  确定性代码是唯一可当场自证的防线。**保留**。
- **记忆四层可视化**对评委演示有价值吗？有，但它是"锦上添花"，不是主线。
  不删，但答辩时间分配不为其扩军。
- **日报流水线（brief/）**与赛题无直接关系，是团队协作产物，不进入答辩主线。

| 独立"产品推荐市场池"（理财内） | 浅层 mock 产品表只会增加演示面、不增加信任；推荐诉求已由 advise + 反事实备选对比覆盖 |

## 七、第七步：重组保留下来的方案（定位不被稀释）

保留 A 的骨架，吸收 B/F 的可取之处，**定位一句话不变**：

> 六场景全覆盖的银行 AI 智能体，理财做深成可信闭环，安全做厚到每个动作可证明。

吸收的内容（都指向同一个目标——**让"说话就能办业务"在真实语言下站得住**）：
- F 的启示：解析分层——关键词快速路径 + 确定性槽位校验 + 必要追问（不引入 LLM 路由）；
- B 的启示：理财深度路径对齐赛题表——申购/赎回/推荐动词补齐，深度叙事不变。

**明确拒绝的组合**：不在"六场景 + 理财深度路径"上再叠加"记忆管家"或"产品市场"叙事，
避免定位变成"什么都做一点"。

## 八、第八步：足以让最终方案失败的反例

**反例 1（最致命）**：评委在答辩现场说出一句 demo 脚本之外的话——
"帮我看看这个月花了多少钱"或"查一下我的余额"——系统误路由或答非所问。
40% 任务完成率的打分现场崩盘。

**反例 2**：评委拿赛题表逐项核对理财典型能力——"产品推荐与对比在哪？一键申购赎回在哪？"

**反例 3**：评委问"这不就是把银行 App 功能加了个正则路由吗？AI 在哪？"——
创新性 30% 无从谈起。

**反例 4**：反对者说"查余额、看账单这种事，银行 App 三步就点完了，根本不需要 AI"。

## 九、第九步：用真实证据回应反例

**反例 1 → 已被黑盒实测证实为真问题（修复前 6/16 失败）。** 回应方式不是写文案，
而是修代码：路由关键词扩充、余额绿色查询、卡列表/追问机制、相对日期解析、
收款人解析停词，并固化 18 个回归测试（tests/test_nl_robustness.py）。
当前全量 86/86 测试通过，16 句黑盒复查全部正确。**剩余风险如实说明**：关键词
覆盖仍是有界集合，未覆盖表达仍可能误路由——答辩口径不承诺"任何话都能听懂"。

**反例 2 → 属实，已修复。** 申购/认购/赎回动词接入执行链路（agent/core/intent.py），
「推荐」接入 advise 路径；风险评估本就有。赛题理财行现在全行可演示。
**未修复的诚实口径**：独立"产品对比市场池"被否决（第六步），答辩口径用
"建议卡 + 反事实备选对比"回应"对比"要求。

**反例 3 → 部分属实，分层回应。** 无 LLM key 时确实是规则引擎，但：
（a）演示走 launch.py 注入 key 的双引擎路径；（b）规则降级是特性不是缺陷——
"LLM proposes, Python disposes"的安全主体从来是确定性闸门；
（c）三根创新支柱（记忆投毒防御、六场景统一防线、五层演化记忆）与是否接 LLM 无关。
**不允许的口径**：把纯规则引擎包装成"AI 决策"。前端 engine 字段已如实展示当前引擎。

**反例 4 → 承认一半。** 单步查询银行 App 确实更快，Agent 的价值不在单步，而在
（a）跨场景编排（生日→锁定→订花 DAG 这类多系统协作）、（b）同一安全框架下
"每个动作都可证明其安全"的一致性、（c）对话式意图识别省去功能入口的学习成本。
答辩口径用场景 6 跨场景联动回应此问，不用"更流畅的聊天"硬撑。

## 附：保留 / 否决 / 证据总账

**保留的创新**：记忆投毒防御（写入门卫 + 信任分级 + 读取隔离）、确定性风控闸门
fail-closed 扩展到六场景、五层演化记忆（跨天证据、reflect 提炼）、六场景统一
安全框架（一条防线/一个路由/一套权限/一份审计/一个熔断器）、理财可信闭环
（意图→诊断→建议→闸门→推演→强验证→纸交易→审计→记忆）。

**否决的创新**：安全中台定位、记忆管家定位、LLM 自由对话、LLM 意图路由、
产品推荐市场池、订花真实 API、记忆→决策机制化联动、中断/回退完整实现（详见第六步）。

**已验证的关键假设**：六场景在确定性路由下可全部现场演示（86 个本地回归测试）；安全五项
在本地评测集上达标（54/54 拦截、0 误伤）；「自然语言入口脆弱」假设为真并已修复。

**仍无证据的假设**（诚实清单，禁止在答辩中当作已实现）：
1. 真实用户测试——本次只有模拟用户语句，没有真实用户参与；
2. 真实账单/订阅/转账数据源的接入表现（现为 demo fixture）；
3. 接 LLM key 的在线路径现场表现（评测为本地规则集结果）；
4. 对未知注入攻击的泛化能力；
5. 记忆改变决策的效果（机制化联动在路线图）。
